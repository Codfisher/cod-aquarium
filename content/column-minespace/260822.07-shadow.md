# Minespace - EP07：陰影

大家好，我是鱈魚。

這一章講陰影，是整個專案調最久的一塊。%(›´ω`‹ )%

一片白沙禪庭最怕的就是平。影子是唯一能把「太陽在哪裡」講清楚的東西。

## 先講一個很雷的坑

一開始陰影濃度是這樣設的。

```ts
shadowGenerator.darkness = 0.5
```

`darkness` 越大陰影越淡，0 是全擋、1 等於沒有影子。給 0.5 應該是「淡淡的影子」才對。

結果正午的白沙上完全看不到影子。%(⊙ o ⊙)%

不是變淡，是數學上根本不存在。

`StandardMaterial` 算漫射時有一道 clamp。

```text
finalDiffuse = clamp(平行光 + 環境光, 0.0, 1.0) * 貼圖
```

正午的白沙正對太陽，環境光 0.72 加上平行光 1.03，合計 1.75。影子裡擋掉一半也還有 1.24。

兩個數字都超過 1，clamp 之後一律變成 1.00。亮處與影子完全相同。%(´థ‸థ)%

太陽很斜的凌晨黃昏，合計掉到 1 以下，影子就回來了；月光強度只有 0.3，整晚都遠在天花板以下，所以夜裡的投影一直都在。

那正是「只有斜射時看得到日影、月影卻總是看得到」的原因。

```ts
shadowGenerator.darkness = 0.05
```

改成全擋之後，影子裡只剩環境光的 0.72，與亮處的 1.00 就分得開了。

留 0.05 是不讓它硬生生地黑掉，白沙上的影子該是柔和偏藍的一片。%( •̀ ω •́ )✧%

路人：「所以問題不在陰影，在 clamp？」
鱈魚：「對，我盯著 shadowGenerator 看了兩天。ﾟ(つд`ﾟ)」

這件事用講的很抽象，直接動手最快。

<demo-shadow-darkness />

一開始就是當初那組壞掉的設定。左上角會告訴你亮處與影中各算出多少，兩個數字都超過 1 的時候，畫面上就是完全沒有影子。%(´థ‸థ)%

把環境光往下拉，或是把陰影濃度拉到 0.05，影子立刻回來。

## 陰影範圍要跟著鏡頭

原本的投影範圍罩住整個世界，350 格見方，貼圖開到 4096。

那代表每一幀都要把全世界的幾何重畫進一張 4096 的深度圖裡，而其中絕大部分玩家根本看不到。霧在 220 格就糊掉了，走遠的東西也沒有影子可看。

```ts
const SHADOW_HALF_EXTENT = 40
const SHADOW_LIGHT_DISTANCE = 90

sunLight.autoUpdateExtends = false
sunLight.orthoLeft = -SHADOW_HALF_EXTENT
sunLight.orthoRight = SHADOW_HALF_EXTENT
sunLight.orthoTop = SHADOW_HALF_EXTENT
sunLight.orthoBottom = -SHADOW_HALF_EXTENT

sunLight.shadowMinZ = 10
sunLight.shadowMaxZ = SHADOW_LIGHT_DISTANCE + 80
```

改成一塊跟著鏡頭移動的小範圍，邊長只有 96 格，貼圖降到 2048。

每一格分到的像素從 11 個變成 21 個。成本降到四分之一，影子還更銳利。%ヽ(●`∀´●)ﾉ%

`autoUpdateExtends` 一定要關掉。讓它每幀依投影者重算的話，範圍會隨著視野裡的東西跳動，影子邊緣跟著抖。

關掉之後 `autoCalcShadowZBounds` 也會失效，深度範圍得自己給。

## 影子邊緣為什麼會爬

範圍跟著鏡頭走之後出現新問題，走路時影子邊緣會沿著行進方向不停爬動。

這個現象叫 shadow shimmering。

原因是投影矩陣一直在變，同一道邊緣每一幀落在不同的深度取樣點上。

解法是「投影中心必須對齊到貼圖的取樣格」，不能連續地跟著走。

問題是**對齊到哪個座標系**。%( ˘•ω•˘ )%

這裡曾經直接把鏡頭的世界座標 X、Y、Z 各自對齊取樣格，那是錯的。

陰影貼圖的格子長在光源空間上，而光源是斜的。世界座標對齊之後投影到光源空間並不會落在整數格上，邊緣照樣每一幀重新取樣。

正解是先把中心點投影到光源自己的三軸上，在那裡對齊，再轉回世界座標。

```ts
forward.copyFrom(light.direction).normalize()
Vector3.CrossToRef(Vector3.UpReadOnly, forward, right)
right.normalize()
Vector3.CrossToRef(forward, right, up)

const alongRight = Math.round(Vector3.Dot(camera.position, right) / texelSize) * texelSize
const alongUp = Math.round(Vector3.Dot(camera.position, up) / texelSize) * texelSize
const alongForward = Math.round(Vector3.Dot(camera.position, forward) / texelSize) * texelSize

center.set(
  right.x * alongRight + up.x * alongUp + forward.x * alongForward,
  right.y * alongRight + up.y * alongUp + forward.y * alongForward,
  right.z * alongRight + up.z * alongUp + forward.z * alongForward,
)

light.position.set(
  center.x - forward.x * SHADOW_LIGHT_DISTANCE,
  center.y - forward.y * SHADOW_LIGHT_DISTANCE,
  center.z - forward.z * SHADOW_LIGHT_DISTANCE,
)
```

三軸的建法必須與 Babylon 算陰影視圖矩陣時完全一致（`LookAtLH` 以世界的上方為參考），否則對齊的還是另一組格子。

### 深度那一軸也要對齊

橫向與縱向對齊是為了讓邊緣落在同一批取樣點上，這是老問題。

深度那一軸原本沒對齊，理由是「不影響取樣格的位置」。那是對的，但它影響存進去的深度值。

光源沿著光線連續前後移動時，同一個表面每一幀被記下來的深度都差一點點。而比較深度是有門檻的，那些剛好卡在門檻上的取樣點會在「被自己擋住」與「沒被擋住」之間反覆翻面。

看起來就是邊緣在閃。%(・∀・(・∀・(・∀・*)%

三軸一起對齊之後，只要人沒有跨過一格取樣格，整張陰影貼圖就是上一幀那一張，一個像素都不會變。

<demo-shadow-shimmer />

關掉對齊，盯著柱子影子的邊緣，它會一直沿著行進方向爬。%(´థ‸థ)%

第二個開關是我走過的那條錯路。改在世界座標上對齊之後爬動有變好一點，但沒有消失，因為格子長在光源空間上而光源是斜的。

### 取樣格大小要跟著貼圖尺寸走

```ts
/** 貼圖尺寸換了就重算，不然會拿舊的格子去對齊新的貼圖 */
if (mapSize !== knownMapSize) {
  knownMapSize = mapSize
  texelSize = (SHADOW_HALF_EXTENT * 2) / mapSize
}
```

低畫質那張只有一半寬，切畫質時不重算會對齊到錯的格子。

## bias 與 normalBias

自我遮蔽的條紋要靠這兩個處理。

```ts
shadowGenerator.bias = 0.0005
shadowGenerator.normalBias = 0.08
```

`bias` 是正規化深度，要換算成世界單位才有意義。深度範圍 340 格，0.0005 大約是 0.17 格。

原本用 0.0012（約半格）壓住方塊表面的條紋，代價是一格高的花草整個落在偏移量以內，投出來的影子被抹掉了。%(›´ω`‹ )%

`normalBias` 則是沿著法線推開投影者，對付平面的自我遮蔽特別有效，又不會像 `bias` 那樣連帶吃掉貼地的短影子。

但它也有陷阱。花草的法線被我們統一改成朝上了（見 EP02），推的方向剛好是往地底下。值一大整株草就沉進地面，影子自然消失。

所以只留剛好夠壓住條紋的量，其餘交給提高解析度。

## 接觸硬化

高畫質走 PCSS。

```ts
const CONTACT_HARDENING_LIGHT_SIZE = 0.05

function applyShadowFiltering(shadowGenerator: ShadowGenerator, quality: GraphicsQuality): void {
  if (quality === 'low') {
    shadowGenerator.usePercentageCloserFiltering = true
    shadowGenerator.filteringQuality = ShadowGenerator.QUALITY_LOW
    return
  }

  shadowGenerator.useContactHardeningShadow = true
  shadowGenerator.contactHardeningLightSizeUVRatio = CONTACT_HARDENING_LIGHT_SIZE
  shadowGenerator.filteringQuality = ShadowGenerator.QUALITY_MEDIUM
}
```

它會先找出擋在前面的是什麼、離得多遠，再依那段距離決定要模糊多寬。

影子因此在物體的根部是銳利的、離遠了才散開。鳥居的柱腳、樹幹的底部會真的「站」在地上，而不是浮在一片同樣柔軟的灰上。%(*´∀`)~♥%

`contactHardeningLightSizeUVRatio` 就是「太陽有多大」。太陽在天上只張開半度，給得太大，一根柱子離地兩格影子就散得看不出形狀；給得太小則與硬邊的 PCF 沒有分別。

濾波品質用中等就好。高等是 32 次遮蔽搜尋加 64 次比較，那個級距是給「畫面上只有幾樣東西」的展示場景用的。

<demo-shadow-filter />

這個範例把前面兩段一起收進來。bias 拉到 0，牆上立刻長出自我遮蔽的條紋；拉到底，地上那幾顆小石頭的短影子整個不見。%(・∀・(・∀・(・∀・*)%

切掉接觸硬化再切回來，注意柱子的根部。PCSS 那一邊是真的「站」在地上，PCF 那一邊整條影子軟得一樣。太陽大小拉大則會讓影子散到看不出形狀。

### 不要用指數陰影

投影範圍現在只罩住鏡頭附近 96 格，範圍外的地面照樣要決定自己有沒有被遮住。

PCF 與接觸硬化的著色器對範圍外會直接回傳「全亮」，這正是我們要的。指數陰影那條路沒有這個判斷，範圍外會取到邊界的深度值，於是遠處的沙地會浮出一圈莫名其妙的陰影。%(・∀・(・∀・(・∀・*)%

```ts
shadowGenerator.frustumEdgeFalloff = 0.2
```

這一項則是讓陰影在接近邊緣時逐漸淡掉，不然範圍內外之間會是一條筆直的分界線。

## 花草整個退出陰影

交叉立板的花草是兩片薄板，貼圖還是鏤空的。兩件事同時出問題。

投影方面，一片葉子在陰影貼圖上只佔不到一個取樣格。太陽一移動，整張貼圖重新光柵化，那些細節每一幀落在不同的格子上，有的幀畫得出來、有的幀整個消失，地上的影子就一直在閃。

接影方面，立板是直的，法線卻為了打光統一改成朝上，法線偏移的方向因此完全不對，自我遮蔽的髒污躲不掉。

```ts
const isThinPlant = blockDef?.shape === 'cross'

mesh.receiveShadows = blockDef?.receiveShadow !== false && !isThinPlant

const isTransparent = blockDef?.alpha !== undefined && blockDef.alpha < 1
if (!isTransparent && !isThinPlant && blockDef?.castShadow !== false) {
  this.shadowGenerator.addShadowCaster(mesh)
}
```

兩邊都退出去之後，花草只吃平行光與環境光，明暗穩定。

而且這正好是 Minecraft 本來的樣子，那裡的草從來不投影子。%(・∀・)%

半透明的水、冰、玻璃也不該擋光，順手一起排除。

## 陰影貼圖不能降更新率

這裡曾經設成隔一幀畫一次，想省下那一趟幾何重繪。理由是「世界是靜態的，太陽十分鐘才走完一整天，慢得不得了」。

那個理由是錯的，慢不等於不動。%( ˘•ω•˘ )%

比對用的光源矩陣是每一幀從光源當下的位置與方向重算的，深度資料卻停在上一次重畫的時刻。太陽一移動，兩者就對不起來，整片地面會浮出自我遮蔽的髒污，下一幀重畫後又消失。

看起來就是地面上有黑影在閃。

光源位置對齊取樣格也救不了，走路時每秒會跨過上百個取樣格。

## 像素對齊的陰影

最後這個是我最喜歡的效果。%(๑•̀ㅂ•́)و✧%

整套美術是十六格見方的像素畫，貼圖用最近鄰、法線也用最近鄰、刻意不開 FXAA，每一項都是為了保住那個網格。

但陰影是連續的柔邊，它是全場唯一不服從像素網格的東西。

做法是把陰影的取樣點量化到貼圖的像素格上。同一個像素格裡的所有片段都去問同一個位置有沒有被遮住，於是陰影的邊界只能沿著格線走，長出來的是階梯而不是曲線。

```glsl
vec4 minespacePixelShadowDelta = vec4(0.0);
#ifdef NORMAL
  {
    vec3 faceMask = 1.0 - step(0.5, abs(normalize(vNormalW)));
    vec3 snapped = (floor(vPositionW * pixelShadowParam.x) + 0.5) / pixelShadowParam.x;
    vec3 worldDelta = (snapped - vPositionW) * faceMask * pixelShadowParam.z;
    minespacePixelShadowDelta = pixelShadowMatrix * vec4(worldDelta, 0.0);
  }
#endif
```

`faceMask` 是「法線指向的那一軸給零，其餘兩軸給一」，最後那個 `vec4` 第四分量給零是因為位移是方向不是位置，平移那一欄不該吃到。

<demo-pixel-shadow />

切開關看影子的邊緣，柔邊變成階梯。「一格幾像素」拉小的話格子會變粗，那正是量化的格距。%( •̀ ω •́ )✧%

三個設計決定。

### 為什麼在世界座標上量化

直接量化陰影貼圖的取樣座標比較省事，但那個格子長在光源空間上，而光源是斜的。

對齊出來的階梯會沿著太陽的方向歪掉，而且太陽一轉整片階梯跟著轉。

貼圖的像素格是釘在世界的軸上的，要對齊就得在世界座標上對齊，再送進光源空間。

### 為什麼只量化面自己的兩軸

三軸都量化的話取樣點會離開表面，往上或往下浮個半格像素。

深度比較是有門檻的，浮出去那一點正好夠讓「這個表面被自己擋住」，於是整片牆會長出一格一格的自我遮蔽條紋。%(´థ‸థ)%

方塊世界的面都是貼著軸的，法線指向哪一軸，那一軸就不要動。取樣點因此永遠留在原本那個平面上，只在面內移動。

順帶一提，這裡用的是 `vNormalW` 不是 `normalW`。要的是這個面朝哪一軸，而 `normalW` 已經被法線貼圖擾動過，問它會問到石縫的斜面。

### 為什麼是加一段位移而不是重算

世界座標到光源裁切空間是仿射的，所以「量化後的位置」等於「原本的位置」加上「位移量經過同一個矩陣」。

原本那一份是內插好的 varying，直接拿來加就好，不必在片段著色器裡重算一次完整的變換。%( •̀ ω •́ )✧%

### 位置與深度要一起挪

最後把位移套進陰影比較那一行。

```ts
'!shadow=(computeShadow[A-Za-z0-9]*)\\((vPositionFromLight(\\d+)),(vDepthMetric\\3),([^;]*)\\);': `
  {
    vec4 minespaceShadowPosition = $2;
    float minespaceShadowDepth = $4;

    #ifdef DIRLIGHT$3
      minespaceShadowPosition += minespacePixelShadowDelta;
      minespaceShadowDepth += minespacePixelShadowDelta.z * pixelShadowParam.y;
    #endif

    shadow = $1(minespaceShadowPosition, minespaceShadowDepth, $5);
  }
`,
```

位置與深度缺一不可。

只挪位置的話，同一格裡的片段會拿著各自的真實深度去比對同一個取樣點的深度，格子的遠端就會判定成「被自己擋住」。那正是要避免的條紋。

只換平行光那一盞也是必要的。這個位移是拿太陽的陰影矩陣算出來的，套到別盞燈的座標上是錯的。

三種濾波（PCSS、PCF、硬邊）的函式名字不同、參數也不同，所以正規式只認前兩個參數，剩下的原封不動接回去。

::: tip
正規式為什麼要切這麼多群組，請見 EP04 的「每個 `$n` 只准出現一次」。
:::

深度換算的係數則從光源自己身上算。

```ts
const depthSpan = sunLight.getDepthMinZ(camera) + sunLight.getDepthMaxZ(camera)
pixelShadowState.depthScale = depthSpan === 0 ? 0 : 1 / depthSpan
```

平行光的這兩個值是固定的，但照著光源自己報的數字算，日後換成別種投影也不會錯。
