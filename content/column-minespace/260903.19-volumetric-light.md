# Minespace - EP19：體積光束

大家好，我是鱈魚。

系列的最後一章，講那道從樹縫裡灑下來的光。%( •̀ ω •́ )✧%

## 光束是什麼

真空裡的光看不見。眼睛能看到東西，是因為光打在那個東西上再彈進眼睛。

空氣不是真空。裡面有水氣、灰塵、分子，光走過去會被它們散開，其中一小部分剛好散進眼睛。所以望向陽光的時候，那一整段空氣本身就是亮的。

而只要有東西擋住陽光，被擋住的那一段空氣就不會亮。亮與不亮的交界畫出來，就是一道光束。%(๑•̀ㅂ•́)و✧%

換句話說，畫光束要回答的問題只有一個，**視線經過的那一段空氣，有多少曬得到太陽**。

## 便宜的那條路

最省的做法是螢幕空間的放射狀模糊。先找出太陽在畫面上的位置，再從每個像素往那個點一路取樣疊加，亮的地方會被拖出一條尾巴。

<demo-beam-screen />

效果不錯，成本也低。麻煩在於**它需要太陽在畫面裡**。

太陽一轉到背後，投影出來的原點落在畫面之外，那個「往太陽的方向」就沒有意義了，整個效果只能關掉。

於是這座庭園裡最想看到的那一幕反而看不到。站在鳥居底下背對夕陽，光從身後穿過柱子與松枝灑進來，那正是太陽不在畫面裡的時候。

鱈魚：「那就規定玩家一定要看著太陽。」
路人：「你要不要順便規定他幾點上線。」

## 沿著視線行進

換一條路。從鏡頭往每一個像素射一條線，沿路一步一步走，每一步問「這一點的空氣曬得到太陽嗎」，曬得到就累加一點亮度。

太陽在哪個方向完全不影響這個做法成不成立。被遮住的地方自然就暗下來，光束因此是從真的幾何縫隙裡透出來的。

<demo-beam-raymarch />

### 第一步：這條視線指向哪裡

後製拿到的是螢幕座標，要先反推回世界空間的方向。

```glsl
vec4 farPoint = inverseViewProjection * vec4(vUV * 2.0 - 1.0, 1.0, 1.0);
vec3 rayDirection = normalize(farPoint.xyz / farPoint.w - cameraPosition);
```

把畫面座標推到遠平面，轉回世界座標，減掉鏡頭位置就是方向。反矩陣由 CPU 每幀算一次送進來。

```ts
scene.getTransformMatrix().invertToRef(inverseViewProjection)
```

### 第二步：走到撞上實體為止

行進不能穿過牆壁，所以要先知道這條線走多遠會撞到東西。答案在場景深度圖裡。

```glsl
float viewZ = texture2D(depthSampler, vUV).r;
float forwardRatio = max(dot(rayDirection, cameraForward), 0.001);
float rayLength = min(viewZ / forwardRatio, maxDistance);
```

那個除法是必要的。深度圖存的是視空間的 Z，也就是「沿著鏡頭正前方多遠」，而這條射線是斜的。除以兩者的夾角才換算得回沿著射線的距離，少了這一步，越靠畫面邊緣的光束會越早被截斷。

上限給九十格。給太遠的話，同樣的步數會被攤得很稀，光束糊成一片平均的霧；何況霧本來在一百格就開始收，再遠的光束也早就被吃掉了。

### 第三步：起點要抖動

每個像素都從同一個位置起步的話，取樣點會在空間裡排成一層一層等距的殼，畫面上就是一圈一圈的同心紋。

```glsl
float jitter = fract(sin(dot(gl_FragCoord.xy, vec2(12.9898, 78.233))) * 43758.5453);
float travelled = stepLength * jitter;
```

加半步以內的隨機位移之後，那些紋被打散成雜訊，而雜訊在這種糊開的效果裡看不出來。與上一章打散色階是同一招。%( ˘•ω•˘ )%

## 那份「曬得到嗎」從哪裡來

這是整套機制最花工夫的地方。

場景本來就有一張陰影圖，但那張在高畫質以上是分層的（CSM）。貼圖是一疊圖層，每一層有自己的矩陣，要在著色器裡挑層、算各層的邊界，那是一整套獨立的機制。而光束只需要「這一點照不照得到太陽」這個最單純的問題。

體素全局光那張粗網格也不行。一格粗格是水平四格、垂直兩格，一叢五格寬的樹冠只佔一到兩格，而且葉子稀疏，擋不出任何邊界分明的陰影體積。量出來的數字很直接，地表往上每一層四千九百格裡有四千八百格以上照得到太陽。可見度處處都是一，光束就沒有東西可以顯現。

所以光束自己畫一張。

### 一台不參與算繪的鏡頭

```ts
const shadowCamera = new TargetCamera('volumetric-shadow-camera', Vector3.Zero(), scene, false)
shadowCamera.mode = Camera.ORTHOGRAPHIC_CAMERA
shadowCamera.orthoLeft = -SHADOW_HALF_EXTENT
shadowCamera.orthoRight = SHADOW_HALF_EXTENT
shadowCamera.orthoTop = SHADOW_HALF_EXTENT
shadowCamera.orthoBottom = -SHADOW_HALF_EXTENT
```

太陽是平行光，投影必須是正交的，透視投影會讓影子近大遠小。

這台鏡頭不會被加進 `scene.activeCameras`，所以它不會真的畫到畫面上，只是拿來定義「從太陽看過去是什麼樣子」。

範圍給五十六格，略大於光束行進的上限。行進走到一半出了圖的話，後半段會突然全部變成「照得到」。

### 存視空間的 Z

```ts
const depthRenderer = new DepthRenderer(
  scene,
  Constants.TEXTURETYPE_FLOAT,
  shadowCamera,
  false,
  Texture.NEAREST_SAMPLINGMODE,
  true,
  'volumetric-shadow-depth',
)
```

最後那個 `true` 是「存視空間的 Z」。另一條路存的是零到一的正規化深度，比較時得把近遠平面再乘回來，而那組數字散在鏡頭上，日後有人動了範圍這裡會靜靜地算錯。存原始的距離，著色器那邊拿同一個視矩陣算一次就比得了。

底色也要改。

```ts
/**
 * 沒有東西的地方要當成無限遠
 */
depthMap.clearColor = new Color4(shadowCamera.maxZ, 0, 0, 1)
```

預設底色是零，那等於「實體就貼在太陽上」，整片天空會被判成遮住了自己，空氣因此全部落在陰影裡。

還有一行很容易漏。

```ts
/** 這張圖不跟著主鏡頭走 */
depthRenderer.useOnlyInActiveCamera = false
scene.customRenderTargets.push(depthMap)
```

預設只有在「正在算繪的就是它綁的那台鏡頭」時才畫，而這台鏡頭永遠不會是主鏡頭。

### 投影中心對齊取樣格

這張圖每幀要跟著鏡頭挪，而挪動的方式決定光束的邊界會不會抖。

```ts
forward.copyFrom(sunDirection).normalize()
Vector3.CrossToRef(Vector3.UpReadOnly, forward, right)
right.normalize()
Vector3.CrossToRef(forward, right, up)

const alongRight = Math.round(Vector3.Dot(position, right) / texelSize) * texelSize
const alongUp = Math.round(Vector3.Dot(position, up) / texelSize) * texelSize
const alongForward = Math.round(Vector3.Dot(position, forward) / texelSize) * texelSize
```

連續跟著走的話，投影矩陣一直在變，同一道邊緣每一幀落在不同的取樣點上，空氣裡的光束邊界會沿著走路的方向不停爬動。

關鍵在於**對齊的座標系必須是光源自己的三軸**。世界座標對齊之後投影到光源空間並不會落在整數格上，而光源是斜的。三軸都對齊之後，只要人沒有跨過一格取樣格，整張圖就是上一幀那一張。

這與地面陰影對齊取樣格是同一件事，講陰影那一章有更完整的說明。

### 查表

```glsl
float minespaceSunVisibility(vec3 worldPosition) {
  vec4 clipPosition = volumetricShadowViewProjection * vec4(worldPosition, 1.0);
  vec2 uv = (clipPosition.xy / clipPosition.w) * 0.5 + 0.5;

  /** 走出這張圖就當作照得到 */
  if (uv.x < 0.0 || uv.x > 1.0 || uv.y < 0.0 || uv.y > 1.0) {
    return 1.0;
  }

  float occluderDistance = texture2D(volumetricShadowSampler, uv).r;
  float sampleDistance = (volumetricShadowView * vec4(worldPosition, 1.0)).z;

  return sampleDistance <= occluderDistance + volumetricShadowBias ? 1.0 : 0.0;
}
```

出了圖的地方判成照得到。判成陰影的話，遠處會憑空冒出一片方形的暗。

容差給半格多一點。這張圖的取樣點本來就在空氣裡、不貼著任何表面，所以可以給得比一般的地面陰影寬鬆。

## 相位函數

到這裡東西都齊了，但直接加上去的話，正午整片畫面會泛白。

原因不在給得太強，而在**加上去的東西不分方向**。戶外滿視野的空氣都曬得到太陽，於是每一個像素都被加上差不多的亮度。那是一層白幕。

真實的空氣散射是強烈前向的。光束看得見，是因為視線朝著光源看過去，那些光才散得進眼睛；背對太陽時空氣裡照樣有光在散射，只是散射的方向不朝著你。

描述這件事的東西叫相位函數，這裡用的是 Henyey-Greenstein。

```glsl
float scatterPhase(float cosAngle) {
  float g = SCATTER_ANISOTROPY;
  float gg = g * g;
  float denominator = 1.0 + gg - 2.0 * g * cosAngle;

  return (1.0 - gg) / (4.0 * 3.14159265 * pow(max(denominator, 0.0001), 1.5));
}
```

參數 `g` 是不對稱係數。零代表各個方向散得一樣多，趨近一則是幾乎只往原方向繼續走。

<demo-beam-phase />

加上這一項之後，亮度自己就集中到太陽那一側，正午背對太陽的畫面幾乎不受影響。於是它不必再靠「只在晨昏開啟」來避免泛白，全天候都成立。**這一項是整個效果成立的關鍵。**%( •̀ ω •́ )✧%

### 還要補一個底

純粹的前向散射集中得很兇。以 0.45 的不對稱係數算，視線與光線垂直時就已經剩不到一成。

空氣裡本來就有一部分是各向同性的散射，那是多次散射的結果。所以補一個底。

```glsl
const float SCATTER_BASE = 0.18;

float forwardLobe = scatterPhase(cosAngle) / scatterPhase(1.0);
float phaseValue = SCATTER_BASE + (1.0 - SCATTER_BASE) * forwardLobe;
```

除以正對時的值是為了正規化，讓最強的那個方向大約是一，強度那個常數才是說得準的「最亮到什麼程度」。

## 取沿路的平均

累積完之後怎麼收尾，這裡有個選擇。

散射的量正比於路徑長度，那是物理上對的。看著腳邊的地面只穿過兩三格空氣，望向遠處的松林才穿過幾十格。

但這座場景裡有樹。

<demo-beam-average />

樹葉是鏤空的，葉片本身很近、而縫隙後面的東西很遠。同一片樹冠上相鄰兩個像素的行進距離可能差上三倍，跟著距離走的話那道落差會整條印在縫上，樹冠看起來像被吃掉。

而且那條隨距離增長的曲線本來就是重複工，霧與大氣透視已經在做「越遠越濁」這件事了。體積光真正只有它做得到的，是「這一段空氣在不在陰影裡」，而那一項與距離無關。

```glsl
float rawVisibility = accumulated / stepCount;

float nearFade = smoothstep(0.0, NEAR_FADE_DISTANCE, rayLength);
accumulated = rawVisibility * nearFade;
```

改取平均之後，跨過深度邊界時前半段的取樣是共用的，平均值幾乎連續，落差自然就沒了。

只留一段很短的近距離淡入，免得貼著鏡頭的表面也蒙上一層。貼著鏡頭的表面前面幾乎沒有空氣，本來就不該有散射。

## 亮部保護

還有兩個地方會被推爆。

**天空**。太陽貼近地平線時，望向它的視線幾乎是平的，行進的九十格全是照得到太陽的空氣，累積值頂到滿檔。而那一塊的天色早就貼在色調映射的上限上。

天色本身在那一層就已經調過霞光了，光束再疊上去是同一件事做兩遍。

**被曬到的白沙**。它在 ACES 的膝點上，加什麼都會把周圍一起推過去、把亮部的層次壓平。

判斷方式很重要。拿深度來猜「這是不是天空」會出事，因為深度圖裡有沒有這個網格，會變成畫面的一部分。所以改成直接問亮度。

```glsl
float sceneLuma = dot(sceneColor, vec3(0.2126, 0.7152, 0.0722));
float brightRatio = smoothstep(BRIGHT_START, BRIGHT_FULL, sceneLuma);

/** 「又遠又亮」才算天空，兩個條件缺一不可 */
float farRatio = smoothstep(maxDistance * 0.95, maxDistance * 1.05, viewZ);
float skyRatio = farRatio * brightRatio;

float headroom = mix(1.0, SKY_FLOOR, skyRatio) * mix(1.0, BRIGHT_FLOOR, brightRatio);
```

天空要「又遠又亮」兩個條件同時成立，收到剩半成。只看亮度的話，被曬到的白沙一樣很亮，收得夠兇到能壓住天空時，地面上的光束會一起消失。

亮面那一項與距離無關，只收一半，光束打在沙地上仍然看得見。

## 幾個工程上的細節

### 迴圈上限必須是編譯期常數

GLSL 的迴圈次數不能是 uniform，所以步數得走兩層。

```ts
const postProcess = new PostProcess(
  'minespace-volumetric-light',
  SHADER_NAME,
  // ...
  `#define MAX_STEP_COUNT ${stepCount}`,
)
```

define 決定「最多幾步」，uniform 決定「這一刻實際走幾步」。

```glsl
for (int index = 0; index < MAX_STEP_COUNT; index++) {
  if (float(index) >= stepCount) {
    break;
  }
  // ...
}
```

步數給三十二。這是全螢幕逐像素的迴圈，成本與步數成正比；而光束的結果沿路平均過，本來就是糊的，從四十八收到三十二看不出差別，省下的卻是三分之一的取樣。

### 不需要的時候要整個卸下來

```ts
setAttached(
  devToggle.volumetricLight
  && currentStrength > 0.001
  && !!sceneDepthState.texture,
)
```

留著而不綁貼圖是會出事的。著色器裡引用了兩個取樣器，只要那兩個材質單元是不完整的，整個繪製呼叫就無效，畫面上剩下的是清除色。

驅動看的是「這支著色器用到了那個取樣器」，不管它有沒有真的執行到。所以只有兩種狀態，要嘛掛上去而且每一幀把該綁的都綁齊，要嘛整個拿掉。

### 插在後製鏈的最前面

```ts
camera.attachPostProcess(postProcess, 0)
```

後製鏈的順序就是套用的順序。光束要在色調映射之前疊上去，才會跟著整個畫面一起被曝光曲線壓過；擺在後面則是疊在成品上，亮部會直接爆掉。

## 完整實作

流程整理一次。

1. 另開一台正交鏡頭對準太陽，每幀畫一張逐方塊解析度的深度圖
2. 投影中心對齊到光源三軸上的取樣格，光束邊界才不會爬動
3. 後製反推每個像素的視線方向，用場景深度圖決定走多遠
4. 起點抖動半步以內，取樣殼打散成雜訊
5. 沿路每一步查那張陰影圖，累積可見度
6. 除以步數取平均，乘上相位函數，乘上亮部保護，乘上強度
7. 加在原本的畫面上，插在後製鏈的第一個位置

這一整套只有最奢的那一級才跑得起來。其餘各級要嘛不做，要嘛用便宜的螢幕空間版本。

## 系列收束

Minespace 從第一章的方塊寫到這裡，十九章。

回頭看，這些效果用的其實是同一批招式。

**造假**。法線改成朝上、陰影量化到像素格、全局光壓成粗網格、散射用一條經驗公式近似。沒有一項是物理正確的，但看起來對。

**注入**。`MaterialPluginBase` 讓你在 `StandardMaterial` 的著色器裡加東西，不必重寫整套光照。雲影、葉片透光、大氣透視、體素全局光都走這條路。

**收邊**。霧、深度、混合模式、繪製順序、取樣器綁不綁得齊，畫面上那些「怪怪的」幾乎都出在這幾件事上。

**量測**。幀率只告訴你慢，不告訴你慢在哪。而「看不到」有兩種，一種是沒算，一種是算了但被色調映射壓平了，這兩種要查的地方完全不同。

**節流**。世界不可編輯，所以全局光只在太陽轉夠多的時候重烘；陰影圖對齊取樣格，所以人沒跨格就整張沿用。省下來的都是每一幀的錢。

而最花時間的往往不是效果本身，是那些藏在預設值裡的東西。%( ˘•ω˘ )%

- 那張圖是另一台正交鏡頭畫的，逐方塊解析度，投影中心對齊取樣格
- 相位函數讓亮度集中到望向太陽的那一側，這一項是效果成立的關鍵
- 取沿路平均而不是積分，深度不連續的地方才不會裂開
- 又遠又亮才算天空，亮部保護要看亮度而不是深度
- 迴圈上限是編譯期常數，所以步數走 define 與 uniform 兩層
