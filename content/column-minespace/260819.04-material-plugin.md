# Minespace - EP04：材質外掛與著色器注入

大家好，我是鱈魚。

這一章是整個專欄的技術核心。%(๑•̀ㅂ•́)و✧%

Minespace 有五個效果是直接改 `StandardMaterial` 的著色器做出來的，分別是大氣透視、雲影、葉片透光、像素對齊陰影、風的擺動。

它們全部走同一條路，`MaterialPluginBase`。

## 為什麼不自己寫一份材質

最直覺的做法是繼承 `ShaderMaterial` 自己寫一支著色器。

但方塊照樣要吃平行光、環境光、霧氣、陰影、鏤空裁切、實例顏色。自己寫一份等於把 `StandardMaterial` 那一整套重寫一遍，然後每次 Babylon 改版都要跟著追。%(›´ω`‹ )%

材質外掛的做法是「在原本的著色器裡插幾段程式碼」，其餘照舊。

路人：「聽起來很像 monkey patch。」
鱈魚：「就是 monkey patch，只是官方有給位置。%( ˘•ω•˘ )%」

## 最小的外掛長什麼樣

```ts
class AerialPerspectivePlugin extends MaterialPluginBase {
  constructor(material: Material) {
    super(material, 'MinespaceAerialPerspective', 200, {}, true, true)
  }

  getClassName(): string {
    return 'AerialPerspectivePlugin'
  }

  getUniforms() {
    return {
      ubo: [
        { name: 'aerialMidColor', size: 3, type: 'vec3' },
        { name: 'aerialGround', size: 3, type: 'vec3' },
      ],
    }
  }

  bindForSubMesh(uniformBuffer: UniformBuffer): void {
    uniformBuffer.updateFloat3('aerialMidColor', airState.red, airState.green, airState.blue)
    uniformBuffer.updateFloat3('aerialGround', GROUND_HAZE_TOP, GROUND_HAZE_FALLOFF, airState.groundBoost)
  }

  getCustomCode(shaderType: string): { [pointName: string]: string } | null {
    if (shaderType !== 'fragment')
      return null

    return {
      // 要插的 GLSL 寫在這裡
    }
  }
}
```

`super` 那幾個參數依序是材質、外掛名稱、優先權、defines、`addToPluginList`、`enable`。

最後那個 `enable` 是「一律啟用」。這個外掛沒有任何開關屬性，不主動啟用的話它永遠不會生效。%(・∀・(・∀・(・∀・*)%

需要開關的外掛則相反，預設不啟用、由外面打開。關著的外掛連程式碼都不會被編進著色器，不是算完再乘上零。

```ts
class LeafTranslucencyPlugin extends MaterialPluginBase {
  private amount = 0

  constructor(material: Material) {
    /** 倒數第二個參數是「預設不啟用」 */
    super(material, PLUGIN_NAME, 220, {}, true, false)
  }

  setAmount(amount: number): void {
    if (this.amount === amount)
      return

    this.amount = amount
    this._enable(amount > 0)
  }
}
```

## 註冊必須搶在所有材質之前

```ts
export function registerAerialPerspective(): void {
  if (isRegistered)
    return

  isRegistered = true
  RegisterMaterialPlugin('MinespaceAerialPerspective', (material) => {
    if (!(material instanceof StandardMaterial))
      return null

    return new AerialPerspectivePlugin(material)
  })
}
```

外掛是靠「材質被建立」這個事件自己接上去的，註冊晚一步，先建好的那幾份材質就永遠收不到。

畫面上會看到部分方塊有效果、部分沒有，而且很難查。%(´థ‸థ)%

所以場景一開始就全部掛好。

```ts
createScene({ engine }) {
  registerAerialPerspective()
  registerCloudShadow()
  registerLeafTranslucency()
  registerPixelShadow()

  const scene = new Scene(engine)
  // ...
}
```

只認 `StandardMaterial` 是刻意的。天空與雲用的是自己寫的著色器材質，本來就沒有那些程式碼可以改。

## 一份全域狀態

兩百多份材質各存一套參數的話，改天色時得走過每一份。

所以做法是開一個模組層級的物件，每一幀寫一次，材質綁定時自己來讀。

```ts
const airState = {
  /** 近中距離那層空氣的顏色，每幀覆寫 */
  red: 0.95,
  green: 0.95,
  blue: 0.94,
  groundBoost: GROUND_HAZE_BOOST,
}

export function updateAerialAir(
  fogColor: Color3,
  skyMidColor: Color3,
  clearRatio: number,
  isEnabled = true,
): void {
  airState.groundBoost = isEnabled ? GROUND_HAZE_BOOST : 0

  const strength = isEnabled ? MID_AIR_STRENGTH * clamp01(clearRatio) : 0

  airState.red = fogColor.r + (skyMidColor.r - fogColor.r) * strength
  airState.green = fogColor.g + (skyMidColor.g - fogColor.g) * strength
  airState.blue = fogColor.b + (skyMidColor.b - fogColor.b) * strength
}
```

Minespace 裡的五個外掛全部是這個寫法。

## 兩種注入方式

### 具名的注入點

Babylon 的著色器裡預留了一堆 `#define CUSTOM_XXX` 位置，直接對著名字塞就好。

```ts
getCustomCode(shaderType: string) {
  if (shaderType !== 'fragment')
    return null

  return {
    CUSTOM_FRAGMENT_DEFINITIONS: `
      vec3 minespaceLeafTranslucency(vec3 viewDirection, vec3 surfaceNormal) {
        // ...
      }
    `,
    CUSTOM_FRAGMENT_BEFORE_FOG: `
      color.rgb += minespaceLeafTranslucency(viewDirectionW, normalW) * baseColor.rgb;
    `,
  }
}
```

常用的有這幾個。

| 注入點 | 位置 |
| --- | --- |
| `CUSTOM_VERTEX_DEFINITIONS` | 頂點著色器的函式與變數宣告 |
| `CUSTOM_VERTEX_UPDATE_POSITION` | 頂點位置算出來之後 |
| `CUSTOM_FRAGMENT_DEFINITIONS` | 片段著色器的函式與變數宣告 |
| `CUSTOM_FRAGMENT_BEFORE_LIGHTS` | 光照計算之前 |
| `CUSTOM_FRAGMENT_BEFORE_FOG` | 套用霧氣之前 |
| `CUSTOM_FRAGMENT_BEFORE_FRAGCOLOR` | 寫入最終顏色之前 |

`CUSTOM_FRAGMENT_BEFORE_FOG` 是個好例子。葉片透光加在霧之前，遠處的樹冠透出來的光才會跟著被霧吃掉；加在霧之後的話，霧裡會浮出一片發亮的葉子。%(・∀・(・∀・(・∀・*)%

### 正規式替換

有時候要動的那一行沒有注入點可用，例如霧的混色。

Babylon 支援用 `!` 開頭的 key 當正規式。

```ts
return {
  '!color\\.rgb\\s*=\\s*mix\\(\\s*vFogColor\\s*,\\s*color\\.rgb\\s*,\\s*fog\\s*\\);': `
    float aerialAmount = clamp(1.0 - fog, 0.0, 1.0);
    float aerialLow = clamp((aerialGround.x - vPositionW.y) * aerialGround.y, 0.0, 1.0);
    aerialAmount = clamp(aerialAmount * (1.0 + aerialLow * aerialGround.z), 0.0, 1.0);
    color.rgb = mix(color.rgb, mix(aerialMidColor, vFogColor, aerialAmount), aerialAmount);
  `,
}
```

原本那一行是 `color.rgb = mix(vFogColor, color.rgb, fog)`，也就是「越遠越靠近同一個顏色」。

換掉之後變成兩段，先依距離調出這一段空氣該是什麼顏色，再依距離決定蓋多濃。

有兩件事值得注意。

一是替換發生在所有 `#include` 都展開之後（Babylon 走的是 `processCodeAfterIncludes` 那條路），所以找得到 include 進來的程式碼。

二是找不到就靜靜地不做事。哪天 Babylon 改了那一行的寫法，畫面會退回原本的單色霧，不會壞掉。%( •̀ ω •́ )✧%

## 三個踩過的坑

### 坑一：每個 `$n` 只准出現一次

正規式可以捕獲群組，用 `$1`、`$2` 帶回原本的內容。

但 Babylon 代換捕獲群組用的是這一行。

```js
newCode.replace('$' + i, match[i])
```

字串比對，一個編號只換掉最前面那一個。

後面的原封不動留在著色器裡變成 `$` 字元，整支著色器編不過。%(´థ‸థ)%

所以像素陰影那段寧可多切幾個群組，也不要重複用同一個編號。

```ts
'!shadow=(computeShadow[A-Za-z0-9]*)\\((vPositionFromLight(\\d+)),(vDepthMetric\\3),([^;]*)\\);': `
  {
    vec4 minespaceShadowPosition = $2;
    float minespaceShadowDepth = $4;

    #ifdef DIRLIGHT$3
      minespaceShadowPosition += minespacePixelShadowDelta;
      minespaceShadowDepth += minespacePixelShadowDelta.z * pixelShadowParam.y;
    #endif

    shadow = $1(minespaceShadowPosition, minespaceShadowDepth, $5);
  }
`,
```

取樣點、深度連同編號各自獨立成群，就是為了守住這條規則。

順帶一提，`$3` 是燈的編號。這一行在 include 展開後是每一盞燈各一份，正規式帶著 `g` 旗標會全部換過，靠編號把 `#ifdef DIRLIGHT0`、`#ifdef DIRLIGHT1` 帶進條件裡。

### 坑二：注入的 GLSL 裡不要寫註解

這個坑找了很久。%(›´ω`‹ )%

Babylon 的前處理器用這條正規式掃每一行。

```js
/(#ifdef)|(#else)|(#elif)|(#endif)|(#ifndef)|(#if)/
```

它沒有錨定行首，也不先把註解拿掉。

所以註解裡只要提到條件編譯指令的名字，就會被當成真的指令，條件層數從此對不起來，游標一路跑到檔尾，後面整段著色器憑空消失。%(⊙ o ⊙)%

鱈魚：「我只是想寫個註解說明這裡在做什麼而已。ﾟ(つд`ﾟ)」
路人：「所以註解就寫在 TypeScript 那邊吧。」

對，要解釋就寫在 `getCustomCode` 外面，那裡的字不會進到著色器。

### 坑三：不要重複宣告 uniform

`getUniforms` 可以同時給 `ubo` 陣列與 `vertex` / `fragment` 字串。

```ts
getUniforms() {
  return {
    ubo: [
      { name: 'cloudShadowParam', size: 4, type: 'vec4' },
      { name: 'cloudShadowProjection', size: 4, type: 'vec4' },
    ],
    /** 這一段只有不支援統一緩衝區時才派得上用場 */
    fragment: `
      uniform vec4 cloudShadowParam;
      uniform vec4 cloudShadowProjection;
    `,
  }
}
```

片段著色器這樣寫是安全的，因為支援統一緩衝區時 `ADDITIONAL_FRAGMENT_DECLARATION` 那個位置根本不存在，這串字會靜靜地被丟掉。

頂點著色器就不一樣了。風的擺動那個外掛只登記 `ubo`，完全不給 `vertex` 字串。

```ts
getUniforms() {
  return {
    ubo: [
      { name: 'windTime', size: 1, type: 'float' },
      { name: 'windAmplitude', size: 1, type: 'float' },
      // ...
    ],
  }
}
```

兩個都給的話 Babylon 會照單全收，同一個名字宣告兩次，著色器編譯直接失敗。

而編譯失敗的材質不會報錯，只會整批不畫。畫面上看到的就是「所有的草突然消失」。%(・∀・(・∀・(・∀・*)%

## 完整範例：大氣透視

把上面的東西湊起來，就是 Minespace 的第一個外掛。

場景內建的霧只有一個顏色，不管多遠一律往那個顏色收。那條路走到底會出現一種現實裡不存在的畫面，遠處的東西比它背後的天空還要淡。

天不可能比空氣本身更暗。%( ˘•ω•˘ )%

真正的空氣是分段的。看穿一小段是透明的、一段是藍的、再遠才近乎白。藍色來自大氣散射，白色是散射早已飽和之後的結果。

所以把霧拆成兩層，中距離往當下的天色偏，遠距離才收進霧色。

```glsl
float aerialAmount = clamp(1.0 - fog, 0.0, 1.0);
float aerialLow = clamp((aerialGround.x - vPositionW.y) * aerialGround.y, 0.0, 1.0);
aerialAmount = clamp(aerialAmount * (1.0 + aerialLow * aerialGround.z), 0.0, 1.0);
color.rgb = mix(color.rgb, mix(aerialMidColor, vFogColor, aerialAmount), aerialAmount);
```

中午是藍、清晨是丁香紫、黃昏是橘。顏色不必另外調，直接拿日夜循環已經算好的中空天色來用就對了。%(*´∀`)~♥%

下面這個範例真的掛了一份外掛上去，開關與滑桿都是即時的。

<demo-aerial-perspective />

關掉的時候注意遠處那幾座石塔，它們比背後的天空還要白。天不可能比空氣本身更暗，那正是單色霧走到底的樣子。%( ˘•ω•˘ )%

第二行順便做了高度霧。空氣是有重量的，濁的那一層積在低處，這是為什麼從山上往下看，山谷總是比山脊模糊。

```ts
/** 貼地那一層空氣的頂，抓在沙面上十格 */
const GROUND_HAZE_TOP = SAND_LEVEL + 10
/** 倒數是「幾格內從沒有變成滿」 */
const GROUND_HAZE_FALLOFF = 1 / 12
/** 這是倍率不是加法，近處的東西完全不受影響 */
const GROUND_HAZE_BOOST = 0.6
```

用倍率而不是加法很重要。直接相加的話，腳邊的方塊會憑空罩上一層灰。

## 除錯開關怎麼做

著色器那段程式碼已經編進材質裡了，拆不掉。

所以除錯開關的做法是「把參數調成效果不存在的值」。

```ts
/**
 * 把中距離的空氣色設成與霧色相同、高度加厚設成零之後，
 * 兩層混色的結果就與原本那一行 mix(vFogColor, color, fog) 完全相同
 */
airState.groundBoost = isEnabled ? GROUND_HAZE_BOOST : 0
```

雲影那邊也一樣，強度給零就直接回傳 1.0。

```glsl
float minespaceCloudShade() {
  if (cloudShadowParam.x <= 0.0) {
    return 1.0;
  }
  // ...
}
```

- `MaterialPluginBase` 讓你在 `StandardMaterial` 的著色器裡插程式碼，不必重寫整套光照
- `RegisterMaterialPlugin` 必須搶在任何材質建立之前呼叫
- 用模組層級的狀態物件每幀寫一次，兩百多份材質綁定時自己來讀
- 沒有注入點就用 `!` 開頭的正規式替換，找不到會靜靜地不做事
- 每個 `$n` 只准出現一次、注入的 GLSL 裡不要寫註解、uniform 不要重複宣告
