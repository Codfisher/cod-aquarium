# Minespace - EP02：體素渲染與 Thin Instance

大家好，我是鱈魚。

上一章把場景骨架架起來了，這一章來看整個方塊世界是怎麼畫出來的。%੭ ˙ᗜ˙ )੭%

Minespace 的世界是 280 格見方，高度好幾十格，實際填出來的方塊有幾十萬顆。

如果每一顆方塊都是一個 mesh，那大概可以直接關掉瀏覽器了。%(›´ω`‹ )%

## Thin Instance

Babylon 的 `thinInstance` 就是為這件事準備的。

同一份頂點資料，配上一整條變換矩陣的緩衝區，GPU 一次畫完幾萬顆，成本只有一個 draw call。

```ts
mesh.thinInstanceSetBuffer('matrix', matrixBuffer, 16, true)
```

矩陣是 4×4，所以 stride 給 16。

第四個參數是重點，它的意思是「這份緩衝區是靜態的」。

這裡原本傳 `false`，等於告訴 Babylon 之後還會改它，於是 GPU 緩衝區以 `DYNAMIC_DRAW` 配置。

但 Minespace 的世界不可編輯，這些矩陣是 Worker 一次算好的，設完就再也不動。

代價不是一點點，驅動層對動態緩衝區會另外做搬運與反交錯。官方論壇有一個兩百五十萬個面的實測，只改這個旗標就從 15 幀變成 60 幀。%(⊙ o ⊙)%

路人：「一個布林值差四倍？」
鱈魚：「一個布林值差四倍。%( ˘•ω•˘ )%」

先看看 thin instance 到底省了什麼，把方塊數拉到底試試。

<demo-thin-instance />

左邊的繪製呼叫跟著方塊數一路往上，右邊永遠停在個位數。%(⊙ o ⊙)%

Minespace 的世界有幾十萬顆方塊，走左邊那條路連開場都撐不過去。

## 一種方塊一個網格

原本的架構是「一個區塊一份」，二十五個區塊各自替自己用到的方塊建網格。

同一種石頭在世界各處就有二十五份網格，網格數八百多，每一幀主畫面與陰影各畫一次，等於一千七百次 draw call。

但方塊全部是靜態的，切成區塊的唯一理由是讓 Worker 能平行運算，算完之後沒有必要繼續分開。

所以改成把各區塊的實例矩陣接成一條，同一種方塊全世界共用一個網格。

```ts
/** 把一串緩衝區接成一條 */
function mergeBufferList(bufferList: Float32Array[] | undefined): Float32Array | null {
  if (!bufferList || bufferList.length === 0)
    return null

  const total = bufferList.reduce((sum, buffer) => sum + buffer.length, 0)
  if (total === 0)
    return null

  const merged = new Float32Array(total)
  let offset = 0
  for (const buffer of bufferList) {
    merged.set(buffer, offset)
    offset += buffer.length
  }

  return merged
}
```

draw call 直接砍掉七成。%ヽ(●`∀´●)ﾉ%

代價是失去逐區塊的視錐剔除，但這個世界只有 280 格見方、霧又開到 220 格，本來就幾乎整片都在視野內，剔除省不到什麼。

## 需要時才建網格

另一個更誇張的問題。

這裡原本在建構時就替「所有有貼圖的方塊」建好網格，一種都不漏。

但一個區塊裡通常只出現十來種方塊，整個世界一百多種、二十五個區塊，算下來會建出七千三百多個網格，其中八成八一個實例都沒有。

空網格照樣要進每一幀的剔除與排序，白白吃掉大量時間。%(´థ‸థ)%

```ts
private ensureBlockMeshes(blockId: BlockId): void {
  if (this.builtBlockSet.has(blockId))
    return

  this.builtBlockSet.add(blockId)

  const blockDef = BLOCK_DEFS[blockId]
  if (!blockDef || blockDef.isHidden || !blockDef.textures)
    return

  if (isDecorationBlock(blockId)) {
    this.initDecorationMeshes(blockId, blockDef)
  }
  else if (needsPerFaceRendering(blockDef.textures)) {
    this.initPerFaceMeshes(blockId, blockDef.textures, blockDef.logAxis)
  }
  else {
    this.initSingleMaterialMesh(blockId, blockDef, blockDef.textures)
  }
}
```

改成等 Worker 算完、知道實際用到哪些方塊之後才建，網格數從 7300 降到 880。

## 兩個必須成對的旗標

網格建好之後還有兩個旗標要設。

```ts
/** 邊界盒已經在設定緩衝區時算好了 */
entry.mesh.doNotSyncBoundingInfo = true
entry.mesh.alwaysSelectAsActiveMesh = true
```

這兩個必須一起出現，`doNotSyncBoundingInfo` 單獨用會讓網格整個消失。

邊界盒不再更新，視錐剔除卻照樣拿它去判斷，判成「不在畫面裡」就整批不畫了。%(・∀・(・∀・(・∀・*)%

而對 thin instance 來說剔除本來就幫不上忙。一顆網格的邊界盒是它所有實例的聯集，在體素世界裡通常橫跨整座場景，永遠剔不掉，那幾百次測試是白做的。

直接說「一律當成看得見」，省下測試也順便修掉消失的風險。

順帶一提，網格生成之後就再也不會動，所以世界矩陣也可以凍結。

```ts
mesh.freezeWorldMatrix()
mesh.isPickable = false
```

還有一個容易忘的。

```ts
/**
 * Babylon 預設每一次 pointermove 都會發一條射線去找游標下的網格
 * 這個場景用的是指標鎖定，游標下有什麼完全沒有意義
 */
scene.skipPointerMovePicking = true
```

## 讓每一塊取同一個亮度

Minecraft 的方塊看起來是平塗的，一整面就是一個亮度。

但 Babylon 的盒子每一面法線各自朝外，光照下來會有連續的明暗變化，水面與花草看起來會很怪。

解法很暴力，把法線全部改成朝上。

```ts
function applyUpwardNormals(mesh: Mesh): void {
  const normalList = mesh.getVerticesData(VertexBuffer.NormalKind)
  if (!normalList)
    return

  for (let index = 0; index < normalList.length; index += 3) {
    normalList[index] = 0
    normalList[index + 1] = 1
    normalList[index + 2] = 0
  }

  mesh.setVerticesData(VertexBuffer.NormalKind, normalList)
}
```

這樣每一面都會拿到跟地面頂面相同的光照。水面因此不會有深淺不一的側面，花草也不會出現一面亮一面暗的怪異切分。

<demo-upward-normals />

關掉開關就看得到那個「怪異切分」，同一株草被斜射的陽光切成一亮一暗兩半，像被人從中間對折過。%(・∀・(・∀・(・∀・*)%

路人：「這樣不是把光照弄壞了嗎？」
鱈魚：「對，這是刻意造假，代價後面會還。%( ˘•ω•˘ )%」

代價是切線空間跟著失真。法線貼圖存的是「相對於表面的偏移」，得有正確的切線座標系才解得回來，立著的葉片卻宣稱自己朝上，算出來的偏移方向完全是錯的。

所以這種材質一律不掛法線貼圖，這件事會在 EP03 再提一次。

## 讓瀑布四面往同一邊流

這個坑很有趣。%(・ω・)%

Babylon 的盒子每一面各有各的 UV 方向。+Z 面的 v 由上往下，-Z 與 -X 面反過來由下往上，+X 面更是把 u 與 v 對調，v 跑的是水平方向。

靜態貼圖看不出差別，但流水是逐格播放的動畫，動畫沿著 v 前進，於是同一道瀑布的四個面各流各的，其中兩面看起來是往旁邊流。%(´థ‸థ)%

<demo-uv-align />

讓它自己轉一圈，關掉重算之後有兩面的水是橫著跑的。%(・∀・(・∀・(・∀・*)%

解法是依頂點座標重算側面的 UV。

```ts
function alignSideFaceUvs(mesh: Mesh, height: number): void {
  const positionList = mesh.getVerticesData(VertexBuffer.PositionKind)
  const uvList = mesh.getVerticesData(VertexBuffer.UVKind)
  if (!positionList || !uvList)
    return

  /** 頂點 0～15 是四個側面，16 之後是頂面與底面 */
  const sideVertexCount = 16
  for (let vertexIndex = 0; vertexIndex < sideVertexCount; vertexIndex++) {
    const x = positionList[vertexIndex * 3]!
    const y = positionList[vertexIndex * 3 + 1]!
    const z = positionList[vertexIndex * 3 + 2]!
    /** 後兩個面朝向 X 軸，水平方向要改看 Z */
    const isFacingX = vertexIndex >= 8

    uvList[vertexIndex * 2] = (isFacingX ? z : x) + 0.5
    uvList[vertexIndex * 2 + 1] = 0.5 - y / height
  }

  mesh.setVerticesData(VertexBuffer.UVKind, uvList)
}
```

必須在 `bakeCurrentTransformIntoVertices` 之前呼叫，座標還是以盒子中心為原點時才算得準。

## 不是正方體的方塊

禪庭裡有半磚、階梯、圍籬、玻璃片、紙門、風鈴、花盆、榻榻米。

這些全部用小片的盒子與立板拼出來，再把同一份實例矩陣套到每一片上。

```ts
switch (blockDef.shape) {
  case 'cross': {
    /** 交叉立板的花草 */
    addPlane('cross-a', 1, { x: 0, y: Math.PI / 4 }, { x: 0, y: 0, z: 0 }, material)
    addPlane('cross-b', 1, { x: 0, y: -Math.PI / 4 }, { x: 0, y: 0, z: 0 }, material)
    break
  }
  case 'slab': {
    addBox('slab', { width: 1, height: 0.5, depth: 1 }, { x: 0, y: -0.25, z: 0 }, material)
    break
  }
  case 'post': {
    const thickness = blockDef.shapeThickness ?? 0.3
    addBox('post', { width: thickness, height: 1, depth: thickness }, { x: 0, y: 0, z: 0 }, material)
    break
  }
  // ...還有 stairs、fence、pane、layer、panel、hanging、pot
}
```

一個 key 可能對應好幾片網格，例如花盆由盆身與植物兩片組成，它們共用同一份實例矩陣。

十種外型排成一排長這樣，右後方那一池水則是下一段的主角。

<demo-block-shapes />

「圍籬依鄰居連接」關掉之後，兩端那幾根橫桿就懸空指向沒有東西的地方了。%(・∀・(・∀・(・∀・*)%

### 會依鄰居連接的方塊

圍籬與玻璃片比較特別，它們要看鄰居才知道往哪邊延伸。

```ts
export const CONNECT_DIRECTION_LIST = [
  { key: 'px', offsetX: 1, offsetZ: 0 },
  { key: 'nx', offsetX: -1, offsetZ: 0 },
  { key: 'pz', offsetX: 0, offsetZ: 1 },
  { key: 'nz', offsetX: 0, offsetZ: -1 },
] as const
```

柱子固定畫，四個方向的橫桿則各自獨立成一份網格，由 Worker 判斷哪一側有鄰居才發送對應的實例。

否則每根柱子都會長出四根懸空的橫桿。%(・∀・(・∀・(・∀・*)%

玻璃片踩過一個坑。原本柱子 0.22 厚、橫向的板只有 0.1，柱子胖了一圈，一整面窗看過去是一根一根凸出來的白柱，看起來非常雜亂。

厚度改成整根一致 0.125 就乾淨了。

## 水面矮八分之一格

Minecraft 的水面比方塊頂面矮八分之一格，岸邊因此會露出一小截泥土或沙的側面。

水才像是灌進地形裡，而不是一顆一顆水方塊疊出來的。

```ts
const surfaceMesh = MeshBuilder.CreateBox(
  `${name}_surface`,
  { width: 1, height: 1 - LIQUID_SURFACE_DROP, depth: 1 },
  this.scene,
)
surfaceMesh.position.y = -LIQUID_SURFACE_DROP / 2
surfaceMesh.bakeCurrentTransformIntoVertices()
```

只有最上層那一格用矮的網格，水底下的格子仍舊是滿格，兩層之間不會出現縫隙。

上面那個範例的水池就可以切這一項。關掉之後水面與岸齊平，整池看起來是一顆一顆水方塊疊出來的；打開才會露出那一小截沙的側面。%( •̀ ω •́ )✧%

## 把環境遮蔽烘進實例顏色

方塊的立體感有一半來自環境遮蔽，也就是角落比較暗那件事。

Babylon 的 thin instance 支援每個實例一個顏色，著色器會拿去乘上貼圖顏色。

```ts
if (shadeBuffer && shadeBuffer.length / 4 === matrixBuffer.length / 16) {
  entry.mesh.thinInstanceSetBuffer('color', shadeBuffer, 4, true)
}
```

遮蔽由 Worker 算好之後直接烘進緩衝區，執行期沒有任何額外成本。%( •̀ ω •́ )✧%

<demo-ambient-occlusion />

關掉之後整片牆平得像貼紙，角落與凹坑的層次全部消失。這個範例的遮蔽是最土法煉鋼的「逐格數鄰居」，但道理與本體一樣。%(๑•̀ㅂ•́)و✧%

順帶一提，燈火照亮的範圍也是烘在同一份顏色裡的。這件事在 EP06 講日夜循環時會再出現一次，因為它跟夜裡的補光有直接關係。

有些方塊沒有遮蔽資料，接成一條之後長度必須對得起來，所以缺的那一段要補上不影響顏色的白。

```ts
const instanceCount = buffer.length / 16
shadeList.push(
  shadeBuffer && shadeBuffer.length / 4 === instanceCount
    ? shadeBuffer
    : new Float32Array(instanceCount * 4).fill(1),
)
```
