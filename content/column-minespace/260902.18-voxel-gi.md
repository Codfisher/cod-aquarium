# Minespace - EP18：體素全局光

大家好，我是鱈魚。

一般的即時光照只算直射光。太陽照到這個面，這個面就亮；沒照到，就交給環境光補一個固定的值。

現實裡不是這樣。光打在紅牆上會彈開，彈出去的光帶著紅牆的顏色，落在旁邊的地板上。所以牆角永遠泛著鄰居的顏色，而環境光那個固定的值給不了這件事。%( ˘•ω•˘ )%

這一章講怎麼把那道間接光算出來。

## 完整的做法有多貴

正規的全局光要沿著每一條光路追蹤反彈，那是離線算圖的規格，一幀幾秒到幾分鐘。

即時的做法一律在偷工，差別只在偷哪裡。這裡選的是**把空間切粗**。

世界是二百八十格見方、四十格高，一格一格算根本不用想。但如果水平四格、垂直兩格併成一個單元呢？格數瞬間掉到三千分之一，而間接光本來就是一團很鬆的東西，粗到這個地步在畫面上幾乎看不出來。

鱈魚：「那再粗一點不是更省？」
路人：「粗到整個庭園只剩一格，你就得到一顆環境光了。」

說得對，那就是這條路的兩個端點。這一章要做的就是在中間找一個位置。

## 第一步：把世界降採樣成粗網格

第一步是掃過整個世界，把每一粗格裡的方塊收成兩個數字。

```ts
export interface VoxelGiGrid {
  gridX: number;
  gridY: number;
  gridZ: number;
  /** 1 為這格大致是實心的（擋光、也反光），0 為大致開放（光在裡面流動） */
  solidList: Uint8Array;
  /** 每格的概略反照色，長度是格數乘三 */
  albedoList: Float32Array;
  /** 每格能看到多少天空 */
  skyVisibilityList: Float32Array;
}
```

掃法很單純，數這一格裡有幾個實心方塊、把它們的反照色加起來。

```ts
const blockId = worldState[coordinateToIndex(x, y, z)] as BlockId
if (blockId === BlockId.AIR || isPassableBlock(blockId))
  continue

solidCountList[cellIndex]! += 1

const albedo = getBlockAlbedo(blockId)
albedoSumList[cellIndex * 3]! += albedo[0]
albedoSumList[cellIndex * 3 + 1]! += albedo[1]
albedoSumList[cellIndex * 3 + 2]! += albedo[2]
```

掃完之後，實心與否取多數決。

```ts
/** 過半是實心才算實心，邊界格常常一半空氣一半石頭 */
solidList[i] = solidCount * 2 > totalCountList[i]! ? 1 : 0
```

<demo-gi-grid />

### 水平粗、垂直細

格距那兩個數字刻意不一樣。

```ts
export const QUALITY_PRESET_MAP = {
  high: {
    giCellSizeXZ: 4,
    giCellSizeY: 2,
  },
}
```

世界只有四十格高。等向的粗細會讓垂直方向只剩十格解析度，而洞穴口與林冠交界那種地方，一兩格內就從露天變成陰暗。垂直切細一倍才抓得住這種變化，而且總格數也還不會爆。

### 反照色從哪裡來

這裡有個現實的問題，這個世界沒有一張「方塊到顏色」的對照表，顏色只活在貼圖的 PNG 裡。

真要準的話得逐張貼圖取平均色。但全局光要的只是「附近有沒有綠色的草、紅色的花」這種粗略提示，沒必要做到貼圖等級。

```ts
export function getBlockAlbedo(blockId: BlockId): [number, number, number] {
  if (isWaterBlock(blockId))
    return WATER_ALBEDO
  if (isLavaBlock(blockId))
    return LAVA_ALBEDO

  const tint = BLOCK_DEFS[blockId]?.textures?.tint
  return tint ?? NEUTRAL_ALBEDO
}
```

方塊定義裡本來就有一組 `tint`，那是給灰階貼圖上色用的，草地、花朵、樹葉都有。沒有 tint 的多半是石頭、木頭、沙，那些反光本來就偏中性灰，退回一個灰階即可。

液體另外給。水會把大半的光吸收掉，反彈出去的偏藍綠而且偏暗；岩漿自己在燒，反彈出去的是橘紅。

## 第二步：天空可見度

傳播要有起點，而起點是陽光。

問題是「這一格曬得到太陽嗎」。正規的答案要沿著太陽方向做一次三維射線行進，那很貴。這裡換一個近似，只看**頭頂壓了幾層實心**。

```ts
for (let cx = 0; cx < gridX; cx++) {
  for (let cz = 0; cz < gridZ; cz++) {
    let solidAbove = 0
    for (let cy = gridY - 1; cy >= 0; cy--) {
      const index = (cx * gridY + cy) * gridZ + cz
      skyVisibilityList[index] = Math.max(0, 1 - solidAbove * SKY_BLOCK_FACTOR)
      if (solidList[index] === 1) {
        solidAbove++
      }
    }
  }
}
```

由上往下走一趟，每過一層實心就把可見度收掉三成。三到四層粗格（也就是六到八格方塊）之後歸零。

這一步少算了「西曬的牆比東邊亮」這種方向性。全局光本來就只是個提示，這個簡化在畫面上幾乎看不出來，換到的是一整趟三維射線行進。%(´,,•ω•,,)%

## 第三步：光線傳播

接下來是這套機制的核心。

規則只有一條，**只有開放格存光，實心格不存**。實心格在每一輪裡負責反射，把開放鄰居送過來的光乘上自己的反照色再吐回去。

一輪分成兩趟。

第一趟，每個實心格收集六個開放鄰居目前的光，取平均，再加上自己的發光量（如果那格有燈）。

```ts
for (const [dx, dy, dz] of NEIGHBOR_OFFSET_LIST) {
  const neighborIndex = cellIndex(x + dx, y + dy, z + dz)
  if (solidList[neighborIndex] === 1)
    continue

  sumR += light[neighborIndex * 3]!
  openNeighborCount++
}

incident[index * 3] = (openNeighborCount > 0 ? sumR / openNeighborCount : 0)
  + emissiveIncidentList[index * 3]!
```

第二趟反過來，每個開放格收集六個實心鄰居反射回來的光，疊到自己身上。

```ts
addR += incident[neighborIndex * 3]! * albedoR * BOUNCE_STRENGTH
```

**乘上的是接收方那格的反照色**，這一步就是顏色滲出去的地方。紅牆吐出來的光帶著紅牆的紅，貼著紅牆的空氣於是泛紅，那團泛紅的空氣再照到地板上。%(๑•̀ㅂ•́)و✧%

這種「每一輪從鄰居收一次，直到收斂」的解法叫 Jacobi 迭代，是解擴散方程最直白的一種。

### 每一輪要折損多少

```ts
const BOUNCE_STRENGTH = 0.35
```

現實裡牆面不會把打在它身上的光原封不動吐回去。給太高會越滾越亮，因為每一輪都在疊加；給太低則四輪跑完幾乎沒有效果。

<demo-gi-bounce />

輪數也由畫質設定表決定，從兩輪到六輪。輪數越多，光滲得越遠。

### 最後要扣掉種子

烘完之後有一件很容易忘的事。

一開始種下去的直射光種子，是為了讓傳播有東西可以擴散。但直射光早就由既有的光照處理過了，全局光只該補上「從鄰居傳播過來」的那一份。

```ts
/** 只留傳播進來的那一份，扣掉一開始種下去的直射光種子 */
const r = Math.min(1, Math.max(0, light[index * 3]! - directLight[index * 3]!))
```

不扣的話，被太陽照到的地方會亮兩次。

## 第四步：交給打工仔

這一整套是純粹的陣列運算，跟畫面完全無關，正好丟給 Web Worker。

```ts
const worker = new Worker(
  new URL('./voxel-gi-worker.ts', import.meta.url),
  { type: 'module' },
)
```

送資料的時候有個關鍵，**世界只送一次**。

```ts
function init(param: Omit<VoxelGiInitMessage, 'type'>): void {
  const message: VoxelGiInitMessage = { type: 'init', ...param }
  worker.postMessage(message, [
    message.solidList.buffer,
    message.albedoList.buffer,
    message.skyVisibilityList.buffer,
  ])
}
```

`postMessage` 的第二個參數是轉移清單。列在裡面的 `ArrayBuffer` 會整個把所有權交出去，不複製，原本那一側從此讀不到。這叫 transferable，幾十萬格的陣列因此是零拷貝送過去的。

之所以敢這樣送，是因為世界生成完之後主執行緒不會再讀這份降採樣資料。所有權交出去反而更乾淨。

之後每次重烘只送三個數字。

```ts
worker.bake({
  sunColor: [sunColor.r, sunColor.g, sunColor.b],
  sunStrength,
  bouncePassCount: preset.value.giBouncePassCount,
})
```

回來的那一份也是轉移的。

```ts
workerSelf.postMessage(response, [textureData.buffer])
```

## 第五步：什麼時候該重烘

這個世界不可編輯。方塊的位置、顏色、燈火的位置從頭到尾不會變。

會變的只有太陽。

而太陽在一天裡幾乎每一刻都在動一點點，逐幀重烘不必要也跑不動。所以做法是每半秒檢查一次，只有太陽的方向偏移夠多才真的送出請求。

```ts
const REBAKE_ANGLE_THRESHOLD = 0.018

function update(sunDirection: Vector3) {
  const hasMovedEnough = !lastBakedDirection
    || Vector3.Distance(lastBakedDirection, sunDirection) > REBAKE_ANGLE_THRESHOLD
  if (!hasMovedEnough)
    return

  requestBake(sunDirection)
}
```

門檻大約是一度。日夜循環正常速度下每幾秒才會踩到一次，時間加速時自然烘得更勤。

還要記得擋住重入。

```ts
/** 上一次請求還沒回來，這一輪先跳過，別把 worker 的信箱塞爆 */
if (isBaking)
  return

isBaking = true
```

路人：「烘到一半太陽轉走了怎麼辦？」
鱈魚：「那一份照樣收下，反正下一次檢查很快就到。」

## 第六步：攤平成一張二維的圖集

烘出來的是三維資料，最自然的結構是 3D 貼圖。

不過這份程式碼裡所有既有的烘焙資料（雲影的圖樣、水位圖）用的都是 2D 貼圖，而新引入的 `sampler3D` 會與那些取樣器撞在同一個材質單元上，整批繪製呼叫作廢。既然攤成 2D 圖集本來就是光影包的標準做法，那就走已經驗證過的路。

排法是**每一層 Y 切片一塊磚，磚並排成一張二維的圖**。磚內的兩軸是 X 與 Z，跨磚才是 Y。

```ts
const tilesPerRow = Math.ceil(Math.sqrt(grid.gridY))
const tileRowCount = Math.ceil(grid.gridY / tilesPerRow)
const atlasWidth = tilesPerRow * grid.gridX
const atlasHeight = tileRowCount * grid.gridZ
```

開平方根是為了讓整張圖接近正方形。排成一長條也能用，只是那會做出一張又寬又扁的貼圖，容易撞上顯卡的單邊尺寸上限。

<demo-gi-atlas />

寫出去的時候要照圖集的像素順序走，格子原本的順序在這一步派不上用場。

```ts
for (let y = 0; y < gridY; y++) {
  const tileX = y % tilesPerRow
  const tileY = Math.floor(y / tilesPerRow)

  for (let z = 0; z < gridZ; z++) {
    const atlasX = tileX * gridX + x
    const atlasY = tileY * gridZ + z
    const pixel = (atlasY * atlasWidth + atlasX) * 4
    // ...
  }
}
```

### 水平雙線性，垂直自己來

貼圖的取樣模式給雙線性。

```ts
giTexture = RawTexture.CreateRGBATexture(
  new Uint8Array(atlasWidth * atlasHeight * 4),
  atlasWidth,
  atlasHeight,
  scene,
  false,
  false,
  Texture.BILINEAR_SAMPLINGMODE,
)
```

直覺上這裡會怕，磚與磚在圖上是相鄰的，但在世界裡卻是不同的 Y 層，雙線性會不會把兩層混在一起？

不會。取樣座標是 `tileOrigin + cell + 0.5`，而 `cell` 已經夾在 `[0, gridX - 1]`，換算成紋素中心正好是 `[0.5, gridX - 0.5]`。雙線性的取樣範圍剛好貼齊磚的邊界，一格都不會跨出去。%( •̀ ω •́ )✧%

而最近鄰的代價是實打實的。同一個粗格內（水平四格見方）的間接光完全一樣、格與格之間硬切，地面上因此浮出一塊一塊的矩形。白沙是高明度的平面，最藏不住這種階梯。

垂直方向就得自己來了，因為只有著色器那一份知道哪兩塊磚才是真的相鄰。

```glsl
/** 上下兩層各取一次再內插，垂直方向才不會一階一階跳 */
float slice0 = floor(cell.y);
float slice1 = min(slice0 + 1.0, voxelGiGrid.y - 1.0);

return mix(
  minespaceSampleVoxelSlice(cell.xz, slice0),
  minespaceSampleVoxelSlice(cell.xz, slice1),
  cell.y - slice0
);
```

代價是一次取樣變兩次。

## 第七步：讀回來

取樣函式的第一行是整段裡最容易寫錯的地方。

```glsl
vec4 minespaceSampleVoxelGi(vec3 worldPosition) {
  /**
   * 減掉半格，整數點才落在格子中心
   */
  vec3 cell = worldPosition / voxelGiCellSize - 0.5;
  cell = clamp(cell, vec3(0.0), voxelGiGrid - 1.0);
  // ...
}
```

世界座標除以格距得到的座標，整數點落在格子的**邊界**上；而紋素的整數點落在紋素**中心**。兩者差半格。

少了 `- 0.5`，內插的重心整份偏移了半個粗格，也就是兩格方塊。牆角的間接光會固定偏向某一側。

<demo-gi-sampling />

取樣的結果加在霧之前，乘上表面自己的顏色。

```glsl
CUSTOM_FRAGMENT_BEFORE_FOG: `
  color.rgb += minespaceVoxelGi(vPositionW) * baseColor.rgb;
`,
```

乘 `baseColor` 是為了讓這道光帶著表面自己的顏色，而不是憑空疊一層純白。加在霧之前則是因為它補的是間接漫射光，理當跟直射光一樣被霧吃掉。

這一段掛進 `StandardMaterial` 的機制是材質外掛，完整說明見 EP05。這裡只補一件事，取樣的那段 GLSL 是一份匯出的字串，材質外掛與光束的後製都貼同一份。

```ts
export const VOXEL_GI_SAMPLE_GLSL = `...`
```

兩邊讀的是同一張圖，磚的排法一旦對不上就會取到別層的資料，而那種錯在畫面上是看不出來的，只會覺得「顏色怪怪的」。共用一份就不存在對不上這回事。%( ˘•ω•˘ )%

## 完整實作

流程整理一次。

1. 世界生成完，掃一次降採樣成粗網格，順便算天空可見度
2. 三份陣列用 transferable 送進 Worker，只送這一次
3. 每半秒檢查太陽方向，偏移超過一度才送出重烘請求
4. Worker 跑幾輪 Jacobi 傳播，扣掉直射光種子，照圖集順序寫成 RGBA
5. 主執行緒收到就 `giTexture.update(data)`
6. 材質外掛每個片元取樣一次，乘上表面顏色，加在霧之前

最後那道總量開關。

```ts
const GI_INTENSITY = 0.22
```

這個數字原本是 0.5，那讓白沙庭園在正午整片浮起來。這座場景的地是高明度的白沙，正午的線性亮度本來就已經頂在 ACES 的膝點上，貼著天花板的地方再加東西只會把周圍一起推過去，亮部之間的層次全被壓平。

間接光要看得出來的是暗處。%(´,,•ω•,,)%

## 總結 🐟

- 間接光的本質是「牆角會反射鄰居的顏色」，環境光那個固定值給不了
- 把世界降採樣成粗網格，每格只記實心與否與概略反照色，格數掉到三千分之一
- 傳播是 Jacobi 式的擴散，實心格收鄰居的光、乘上自己的反照色再吐回去
- 烘焙丟給 Web Worker，世界用 transferable 零拷貝送一次，之後只送太陽
- 世界不可編輯，所以只有太陽角度變夠多時才重烘
- 三維資料攤平成 2D 圖集，水平走雙線性、垂直自己取兩層內插
- 取樣座標要減半格，整數點才落在格子中心
