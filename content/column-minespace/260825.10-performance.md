# Minespace - EP10：效能、稽核與一個沒解掉的問題

大家好，我是鱈魚。

專欄來到最後一章。%(๑•̀ㅂ•́)و✧%

前面九章講的都是「怎麼做出來」，這一章講「怎麼讓它跑得動」，最後再誠實記錄一個到現在還沒修好的效果。

## 幀率是最沒用的數字

同樣是三十幀，卡在 CPU 送繪製呼叫、卡在 GPU 填畫素、卡在我們自己每幀跑的 JS，是三件完全不同的事。

處方也完全相反，猜錯就是白做一輪。%(›´ω`‹ )%

所以 Minespace 有一支效能探針，不挑重點量，是全部都量。

```ts
export interface PerformanceReading {
  drawCallCount: number;
  activeMeshCount: number;
  triangleCount: number;
  /** 整幀花了幾毫秒（CPU 這一側） */
  frameMs: number;
  /** GPU 畫這一幀花了幾毫秒 */
  gpuMs: number;
  interFrameMs: number;
  meshSelectionMs: number;
  renderTargetMs: number;
  particleMs: number;
  shaderCompileMs: number;
  /** 所有 onBeforeRender 觀察者加起來花了幾毫秒 */
  observerMs: number;
}
```

`frameMs` 與 `gpuMs` 一比就知道該往哪修。CPU 高、GPU 低是繪製呼叫或 JS 太重，反過來則是像素太多。

::: tip
`gpuMs` 讀不到時是 0。這需要 `EXT_disjoint_timer_query`，有些瀏覽器基於時間側通道的顧慮預設關掉它。
:::

裝上去長這樣，數字是真的在跑的。

<demo-performance-probe />

切換兩種畫法再拉方塊數，繪製呼叫與「挑選網格」那兩欄的差別最明顯。%(๑•̀ㅂ•́)و✧%

獨立網格那一路，CPU 幀時間會跟著方塊數一路爬，GPU 卻幾乎不動，這就是典型的「卡在繪製呼叫」。

### 替每個系統掛名

光看總數還是不知道是誰。

```ts
export function measureSection(name: string, run: () => void): void {
  if (!isProbing) {
    run()
    return
  }

  const start = performance.now()
  run()
  sectionElapsedMap.set(name, (sectionElapsedMap.get(name) ?? 0) + performance.now() - start)
}
```

沒開啟探針時只是多一次函式呼叫與一個布林判斷，這個成本小到可以永遠留在正式程式碼裡。

而它換來的是「出事時馬上知道是誰」。%( •̀ ω •́ )✧%

用起來就像這樣。

```ts
const observer = scene.onBeforeRenderObservable.add(() => {
  measureSection('風', () => {
    const deltaSecond = scene.getEngine().getDeltaTime() / 1000
    // ...
  })
})
```

風、雲飄移、方塊動畫、陰影追蹤、空氣顆粒、晨霧，每一個都有自己的名字。

最後再拿「所有 `onBeforeRender` 觀察者的總時間」與各系統的總和對帳。兩者若有落差，就是還有沒掛上名字的東西。%(๑•̀ㅂ•́)و✧%

## 這一路砍掉的東西

回頭整理一下前九章提過的優化，順序大致就是實際動手的順序。

| 項目 | 做了什麼 | 結果 |
| --- | --- | --- |
| 空網格 | 需要時才建網格 | 7300 → 880 顆 |
| 逐區塊網格 | 同一種方塊全世界共用一個 | draw call 砍七成 |
| 實例緩衝區 | 第四個參數改成靜態 | 論壇實測 15 → 60 幀 |
| 邊界盒 | 停止同步、一律當成看得見 | 省下幾百次無效測試 |
| 陰影範圍 | 4096 罩全世界 → 2048 罩 96 格 | 成本剩四分之一且更銳利 |
| 泛光 | 直接關掉 | 三趟全螢幕運算歸零 |
| 拾取 | `skipPointerMovePicking` | 滑鼠不再每次發射線 |
| 水面倒影 | 走遠就 `refreshRate = 0` | 同一刻至多一面在畫 |
| 光束 | 只在晨昏且正對太陽時存在 | 平常不多畫一趟世界 |

最有趣的是前三項，它們全部不是「效果變差」換來的，純粹是原本的寫法太浪費。%(・∀・)%

## 畫質分檔

Minespace 只分兩檔，高與低。

```ts
export type GraphicsQuality = 'high' | 'low'

export function _useGraphicsQuality() {
  const isMobile = useMediaQuery('(pointer: coarse)')

  const storedQuality = useStorage<GraphicsQuality | null>('minespace-graphics-quality', null)

  const quality = computed<GraphicsQuality>({
    get: () => storedQuality.value ?? (isMobile.value ? 'low' : 'high'),
    set: (value) => {
      storedQuality.value = value
    },
  })

  return { isMobile, quality }
}

export const useGraphicsQuality = createSharedComposable(_useGraphicsQuality)
```

這裡有一個很值得說的細節。%( •̀ ω •́ )✧%

沒選過時存的是 `null`，不是預設值。

直接把裝置判斷的結果當預設存進去是不行的。`useMediaQuery` 要等媒體查詢回報才知道答案，第一拍可能還是 `false`。

手機上那一拍會把「高」寫進儲存並從此固定下來，之後再也回不到裝置該有的預設。%(´థ‸థ)%

存 `null` 表示「使用者還沒表示意見」，這時每次都重新問裝置；一旦動過選單才寫進去。

兩種狀態分開，誤判就不會被記成選擇。

### 兩檔各差在哪

| 項目 | 高 | 低 |
| --- | --- | --- |
| 硬體縮放 | 裝置像素比上限 1.5 | 三分之一 |
| 多重取樣 | 4 個樣本 | 關閉 |
| 陰影貼圖 | 2048 | 1024 |
| 陰影濾波 | 接觸硬化（PCSS）中等 | PCF 低 |
| 水面倒影 | 走近時畫 | 完全不做 |
| 光暈柔性淡出 | 開 | 關 |
| 晨昏光束 | 開 | 關 |

硬體縮放那一項也是量出來的。

```ts
function getHardwareScalingLevel(quality: GraphicsQuality, devicePixelRatio: number): number {
  if (quality === 'low') {
    return 3 / devicePixelRatio
  }

  return 1 / Math.min(devicePixelRatio, 1.5)
}
```

高畫質原本直接跟著裝置像素比走。在兩倍的螢幕上那代表要畫四倍的像素。

幀率掉下來之後轉動視角會一段一段跳，因為視角轉多少是由滑鼠位移決定的，與幀率無關。幀率一低，同樣的角度就被切成更少、更大的步進。%(・∀・(・∀・(・∀・*)%

<demo-hardware-scaling />

左上角會顯示實際畫了多少像素。從 1.0 拉到 1.5，像素量掉一半以上，但盯著方塊的稜線看，差別小得可憐。%( ˘•ω˘ )%

拉到 3 以上就是低畫質那一檔的樣子了，那時候該關掉的東西也都關掉了。

倍率壓在 1.5 以內之後，畫質幾乎看不出差別，像素量卻少了將近一半。

### 切畫質時要跟著動的東西

畫質是可以隨時切的，而切換不會重建場景。所以那些吃畫質的東西必須用 `watch` 而不是只讀一次。

```ts
const { quality } = useGraphicsQuality()
const softFade = createHaloSoftFade({ scene, camera })
const stopQualityWatch = watch(
  quality,
  (currentQuality) => softFade.setEnabled(currentQuality !== 'low'),
  { immediate: true },
)
```

只讀一次的話，切到低畫質那一趟深度預繪會一直留著。%( ˘•ω˘ )%

## 一個用登記制取代記性的做法

這件事我覺得很值得推廣。%(๑•̀ㅂ•́)و✧%

前面提過，世界邊界那道白幕靠的是霧。能見度收到六格，凡是照距離吃霧的東西一律自己糊掉，跨過邊界的前後兩側都是同一片白。

會壞事的只有一種東西，自己跳出霧的那些。

天空、太陽月亮、雲、燈暈都不吃霧，因為它們本來就不該按距離褪色。代價是邊界那道簾子對它們一律無效，每一個都得另外接一條收乾淨的路。

這件事過去是靠記性的，而漏掉的症狀是「走到邊界還看得到某個東西」，通常要等到有人真的走過去才會發現。%(›´ω`‹ )%

所以改成登記制。

```ts
/** 能吃霧的東西：網格與粒子系統都有這兩個欄位 */
interface FogAware {
  applyFog: boolean;
  name: string;
}

const handledMap = new WeakMap<FogAware, string>()

/**
 * 宣告這個東西不吃霧，並說明它在世界邊界怎麼收
 *
 * edgeHandling 那句話是寫給下一個人看的，想不出來就表示還沒接
 */
export function optOutOfFog(target: FogAware, edgeHandling: string): void {
  target.applyFog = false
  handledMap.set(target, edgeHandling)
}
```

用起來像這樣。

```ts
optOutOfFog(skyDome, '天色本身就是白幕的顏色，由 sky-gradient 每幀收成霧色')
optOutOfFog(disc, '交給 atmosphere.skyBodyFade 淡出，貼近邊界時歸零')
optOutOfFog(cloudMesh, '交給 use-weather 的 cloudFadeRatio 淡到全透明')
```

那句說明是重點。它強迫你在關掉霧的當下就回答「到邊界時是誰把它收掉」，想不出來就表示還沒接。

然後開發模式掃一遍場景。

```ts
export function auditFogOptOut(scene: Scene): void {
  const missingList: string[] = []

  const targetList: object[] = [...scene.meshes, ...scene.particleSystems]

  for (const target of targetList) {
    if (!isFogAware(target))
      continue
    if (target.applyFog)
      continue
    if (handledMap.has(target))
      continue

    missingList.push(target.name)
  }

  if (missingList.length === 0)
    return

  const nameList = missingList.map((name) => `  - ${name}`).join('\n')

  console.warn(
    `[fog-opt-out] 這些東西不吃霧，但沒交代到了世界邊界要怎麼收：\n${nameList}\n`
    + `改用 optOutOfFog(目標, '到邊界時怎麼收') 登記，或讓它吃霧`,
  )
}
```

它不會攔阻任何事，只負責讓人在加東西的當下就知道「這個到邊界不會自己消失」。%ヽ(●`∀´●)ﾉ%

用 `WeakMap` 是為了讓場景丟掉時這裡不會拖著它們不放。

同樣的想法也用在大氣狀態上。

```ts
/**
 * 離世界邊界有多近，0 為平常、1 為貼著邊界
 *
 * 之所以要放在這裡而不是各自呼叫 getEdgeFogRatio：
 * 新加的東西要先知道「有這個函式」才想得到要用它。
 * 擺成一個現成的狀態欄位，讀它比記得呼叫某個函式可靠得多
 */
edgeRatio: number;
```

## 一個到現在還沒修好的效果

最後來講雲影。%( ˘•ω˘ )%

天上飄著一整片雲，地面卻從早到晚是同一個亮度。少了這一層，白沙庭園那一大片高明度的地會平得像一張紙。

太陽角度在變，但「這一塊比較暗」這件事從來沒發生過。

### 設計是這樣的

Babylon 的 `projectionTexture` 只有聚光燈有，平行光沒有這個東西，所以只能走材質外掛，在著色器裡自己算。

而且雲影必須與真正的雲對得起來。這個世界是循環的，雲的圖樣正是為此才做成剛好一個世界寬。雲影若用另一個週期，跨過邊界的那一瞬間地上的暗塊會整片換一副樣子。

既然週期非得一樣，不如直接拿同一份圖樣。

```ts
export function setCloudShadowPattern(
  scene: Scene,
  cellList: boolean[],
  patternCount: number,
  cellSize: number,
  cloudHeight: number,
): void {
  const coverList = blurPattern(cellList, patternCount)
  // 把 18×18 個布林值糊一糊烘成一張小圖
}
```

模糊過的圖樣才有中間值。原始圖樣是一格十四格寬的布林值，直接雙線性取樣會拉出菱形的塊。

順帶一提這也是物理上對的。太陽有半度的張角，雲在一百格高投下來的影子，邊緣本來就有好幾格寬的半影。%( •̀ ω •́ )✧%

著色器沿著光線往上找。

```glsl
float minespaceCloudShade() {
  if (cloudShadowParam.x <= 0.0) {
    return 1.0;
  }

  vec2 cloudPoint = vPositionW.xz
    - (cloudShadowProjection.z - vPositionW.y) * cloudShadowProjection.xy
    - vec2(cloudShadowProjection.w, 0.0);

  float cover = texture2D(cloudShadowSampler, cloudPoint * cloudShadowParam.y).r;

  return 1.0 - cloudShadowParam.x * smoothstep(cloudShadowParam.z, cloudShadowParam.w, cover);
}
```

再乘進平行光那一盞。雲擋住的是太陽，不是天空，所以環境光與洞裡那幾盞燈都不該跟著暗。

高光同樣要收。少了那一行，一朵雲飄過水鏡池的時候，池面照樣閃著一道刺眼的反光，而那道光的來源明明正被遮著。

### 然後它就是不會動

畫面上看不到任何雲影。%(´థ‸థ)%

查了一輪，範圍已經縮到最後一小塊。已經逐項驗證過、可以排除的有五項。

**一、著色器注入是好的。** 攔下真正送進 GPU 的原始碼確認過，`minespaceCloudShade` 的定義在、`cloudShade` 有被賦值、也確實乘進了 `computeLighting`。呼叫次數三次（一個函式定義加兩處呼叫），對得上場景的燈組。

**二、資料是對的。** 強度 0.5、雲高 104、取樣縮放 0.00397、斜率與飄移都在動，圖樣貼圖也建出來了。

**三、uniform 真的送得到著色器。** 把函式改成 `return 1.0 - cloudShadowParam.x;`（跳過圖樣與座標）之後，整片地面明顯變暗，而且開關一切換就恢復。

**四、外掛機制沒問題。** `halo-soft-fade` 用一模一樣的寫法，同樣的 `getSamplers`、同樣的 `super` 參數、同樣的 `setTexture`，而它是好的。

**五、模組被載入兩次**（場景跑在 whyframe 的 iframe 裡，外層頁面與 iframe 各一份），但活著的那一份數值全對，而且兩者是不同 realm，`globalThis` 也共用不了。

剩下唯一的嫌疑是 `cloudShadowSampler` 那一次取樣讀出來恆為零。

把 `cover` 直接當遮蔽量用（跳過 `smoothstep`）、甚至把取樣縮放拉到每十二格重複一次讓圖樣鋪滿整個視野，地面都毫無變化。

所以不是門檻卡太高，也不是圖樣太稀疏，是那張圖根本沒被取樣到，或者取到的是全黑。

下次從這裡接，確認 `RawTexture` 有沒有真的綁上那個取樣器（`isReady`、通道格式、`UniformBuffer.setTexture` 有沒有找到位置），或者換成 `material.diffuseTexture` 之類已知會綁的路徑對照看看。

路人：「所以你把一個沒做完的東西寫進文章？」
鱈魚：「對，因為排查過程比結論值錢。%( ˘•ω•˘ )%」

### 排查心得

這件事最大的收穫是一個方法。

**攔下真正送進 GPU 的原始碼，不要離線模擬。**

Babylon 的著色器經過 include 展開、前處理器、外掛注入、defines 代換好幾層，中間任何一步出問題，你在編輯器裡看到的字串跟 GPU 收到的字串就不一樣。

```js
const original = WebGLRenderingContext.prototype.shaderSource
WebGLRenderingContext.prototype.shaderSource = function (shader, source) {
  if (source.includes('minespaceCloudShade')) {
    console.log(source)
  }
  return original.call(this, shader, source)
}
```

在主控台攔一下 `shaderSource` 就知道實機到底編了什麼。這一招把「注入失敗」這個嫌疑一次排除掉，省下很多瞎猜。%(๑•̀ㅂ•́)و✧%

順帶一提，最終 GLSL 裡沒有 `#ifdef` 是正常的，前處理器早就把條件解掉了。第一次看到還以為是條件編譯壞了。

回頭看，Minespace 的視覺大致就這幾件事。

- **批次**。Thin Instance 把幾十萬顆方塊壓成幾百次繪製呼叫，這是一切的前提
- **造假**。法線改成朝上、陰影量化到像素格、透光用一次點積近似次表面散射，全部都不是物理正確，但看起來對
- **注入**。`MaterialPluginBase` 讓你在 `StandardMaterial` 的著色器裡加東西，不必重寫整套光照
- **收邊**。霧、深度、混合模式、繪製順序，畫面上那些「怪怪的」幾乎都出在這四件事上
- **量測**。幀率不會告訴你慢在哪，掛名計時會

而最花時間的往往不是效果本身，是那些藏在預設值裡的東西。材質的 `ambientColor` 預設是黑的、粒子預設不吃霧、`darkness` 給 0.5 在強光下等於沒有影子。

這些都不會報錯，只會讓畫面「有點不對但說不上來」。%( ˘•ω˘ )%
