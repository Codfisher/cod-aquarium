# Minespace - EP10：效能、稽核與一條查歪的冤枉路

大家好，我是鱈魚。

專欄來到最後一章。%(๑•̀ㅂ•́)و✧%

前面九章講的都是「怎麼做出來」，這一章講「怎麼讓它跑得動」，最後再誠實記錄一次查錯查到完全歪掉的經驗。

## 幀率是最沒用的數字

同樣是三十幀，卡在 CPU 送繪製呼叫、卡在 GPU 填畫素、卡在我們自己每幀跑的 JS，是三件完全不同的事。

處方也完全相反，猜錯就是白做一輪。%(›´ω`‹ )%

所以 Minespace 有一支效能探針，不挑重點量，是全部都量。

```ts
export interface PerformanceReading {
  drawCallCount: number;
  activeMeshCount: number;
  triangleCount: number;
  /** 整幀花了幾毫秒（CPU 這一側） */
  frameMs: number;
  /** GPU 畫這一幀花了幾毫秒 */
  gpuMs: number;
  interFrameMs: number;
  meshSelectionMs: number;
  renderTargetMs: number;
  particleMs: number;
  shaderCompileMs: number;
  /** 所有 onBeforeRender 觀察者加起來花了幾毫秒 */
  observerMs: number;
}
```

`frameMs` 與 `gpuMs` 一比就知道該往哪修。CPU 高、GPU 低是繪製呼叫或 JS 太重，反過來則是像素太多。

::: tip
`gpuMs` 讀不到時是 0。這需要 `EXT_disjoint_timer_query`，有些瀏覽器基於時間側通道的顧慮預設關掉它。
:::

裝上去長這樣，數字是真的在跑的。

<demo-performance-probe />

切換兩種畫法再拉方塊數，繪製呼叫與「挑選網格」那兩欄的差別最明顯。%(๑•̀ㅂ•́)و✧%

獨立網格那一路，CPU 幀時間會跟著方塊數一路爬，GPU 卻幾乎不動，這就是典型的「卡在繪製呼叫」。

### 替每個系統掛名

光看總數還是不知道是誰。

```ts
export function measureSection(name: string, run: () => void): void {
  if (!isProbing) {
    run()
    return
  }

  const start = performance.now()
  run()
  sectionElapsedMap.set(name, (sectionElapsedMap.get(name) ?? 0) + performance.now() - start)
}
```

沒開啟探針時只是多一次函式呼叫與一個布林判斷，這個成本小到可以永遠留在正式程式碼裡。

而它換來的是「出事時馬上知道是誰」。%( •̀ ω •́ )✧%

用起來就像這樣。

```ts
const observer = scene.onBeforeRenderObservable.add(() => {
  measureSection('風', () => {
    const deltaSecond = scene.getEngine().getDeltaTime() / 1000
    // ...
  })
})
```

風、雲飄移、方塊動畫、陰影追蹤、空氣顆粒、晨霧，每一個都有自己的名字。

最後再拿「所有 `onBeforeRender` 觀察者的總時間」與各系統的總和對帳。兩者若有落差，就是還有沒掛上名字的東西。%(๑•̀ㅂ•́)و✧%

## 這一路砍掉的東西

回頭整理一下前九章提過的優化，順序大致就是實際動手的順序。

| 項目 | 做了什麼 | 結果 |
| --- | --- | --- |
| 空網格 | 需要時才建網格 | 7300 → 880 顆 |
| 逐區塊網格 | 同一種方塊全世界共用一個 | draw call 砍七成 |
| 實例緩衝區 | 第四個參數改成靜態 | 論壇實測 15 → 60 幀 |
| 邊界盒 | 停止同步、一律當成看得見 | 省下幾百次無效測試 |
| 陰影範圍 | 4096 罩全世界 → 2048 罩 96 格 | 成本剩四分之一且更銳利 |
| 泛光 | 直接關掉 | 三趟全螢幕運算歸零 |
| 拾取 | `skipPointerMovePicking` | 滑鼠不再每次發射線 |
| 水面倒影 | 走遠就 `refreshRate = 0` | 同一刻至多一面在畫 |
| 光束 | 只在晨昏且正對太陽時存在 | 平常不多畫一趟世界 |

最有趣的是前三項，它們全部不是「效果變差」換來的，純粹是原本的寫法太浪費。%(・∀・)%

## 畫質分檔

Minespace 只分兩檔，高與低。

```ts
export type GraphicsQuality = 'high' | 'low'

export function _useGraphicsQuality() {
  const isMobile = useMediaQuery('(pointer: coarse)')

  const storedQuality = useStorage<GraphicsQuality | null>('minespace-graphics-quality', null)

  const quality = computed<GraphicsQuality>({
    get: () => storedQuality.value ?? (isMobile.value ? 'low' : 'high'),
    set: (value) => {
      storedQuality.value = value
    },
  })

  return { isMobile, quality }
}

export const useGraphicsQuality = createSharedComposable(_useGraphicsQuality)
```

這裡有一個很值得說的細節。%( •̀ ω •́ )✧%

沒選過時存的是 `null`，不是預設值。

直接把裝置判斷的結果當預設存進去是不行的。`useMediaQuery` 要等媒體查詢回報才知道答案，第一拍可能還是 `false`。

手機上那一拍會把「高」寫進儲存並從此固定下來，之後再也回不到裝置該有的預設。%(´థ‸థ)%

存 `null` 表示「使用者還沒表示意見」，這時每次都重新問裝置；一旦動過選單才寫進去。

兩種狀態分開，誤判就不會被記成選擇。

### 兩檔各差在哪

| 項目 | 高 | 低 |
| --- | --- | --- |
| 硬體縮放 | 裝置像素比上限 1.5 | 三分之一 |
| 多重取樣 | 4 個樣本 | 關閉 |
| 陰影貼圖 | 2048 | 1024 |
| 陰影濾波 | 接觸硬化（PCSS）中等 | PCF 低 |
| 水面倒影 | 走近時畫 | 完全不做 |
| 光暈柔性淡出 | 開 | 關 |
| 晨昏光束 | 開 | 關 |

硬體縮放那一項也是量出來的。

```ts
function getHardwareScalingLevel(quality: GraphicsQuality, devicePixelRatio: number): number {
  if (quality === 'low') {
    return 3 / devicePixelRatio
  }

  return 1 / Math.min(devicePixelRatio, 1.5)
}
```

高畫質原本直接跟著裝置像素比走。在兩倍的螢幕上那代表要畫四倍的像素。

幀率掉下來之後轉動視角會一段一段跳，因為視角轉多少是由滑鼠位移決定的，與幀率無關。幀率一低，同樣的角度就被切成更少、更大的步進。%(・∀・(・∀・(・∀・*)%

<demo-hardware-scaling />

左上角會顯示實際畫了多少像素。從 1.0 拉到 1.5，像素量掉一半以上，但盯著方塊的稜線看，差別小得可憐。%( ˘•ω˘ )%

拉到 3 以上就是低畫質那一檔的樣子了，那時候該關掉的東西也都關掉了。

倍率壓在 1.5 以內之後，畫質幾乎看不出差別，像素量卻少了將近一半。

### 切畫質時要跟著動的東西

畫質是可以隨時切的，而切換不會重建場景。所以那些吃畫質的東西必須用 `watch` 而不是只讀一次。

```ts
const { quality } = useGraphicsQuality()
const softFade = createHaloSoftFade({ scene, camera })
const stopQualityWatch = watch(
  quality,
  (currentQuality) => softFade.setEnabled(currentQuality !== 'low'),
  { immediate: true },
)
```

只讀一次的話，切到低畫質那一趟深度預繪會一直留著。%( ˘•ω˘ )%

## 一個用登記制取代記性的做法

這件事我覺得很值得推廣。%(๑•̀ㅂ•́)و✧%

前面提過，世界邊界那道白幕靠的是霧。能見度收到六格，凡是照距離吃霧的東西一律自己糊掉，跨過邊界的前後兩側都是同一片白。

會壞事的只有一種東西，自己跳出霧的那些。

天空、太陽月亮、雲、燈暈都不吃霧，因為它們本來就不該按距離褪色。代價是邊界那道簾子對它們一律無效，每一個都得另外接一條收乾淨的路。

這件事過去是靠記性的，而漏掉的症狀是「走到邊界還看得到某個東西」，通常要等到有人真的走過去才會發現。%(›´ω`‹ )%

所以改成登記制。

```ts
/** 能吃霧的東西：網格與粒子系統都有這兩個欄位 */
interface FogAware {
  applyFog: boolean;
  name: string;
}

const handledMap = new WeakMap<FogAware, string>()

/**
 * 宣告這個東西不吃霧，並說明它在世界邊界怎麼收
 *
 * edgeHandling 那句話是寫給下一個人看的，想不出來就表示還沒接
 */
export function optOutOfFog(target: FogAware, edgeHandling: string): void {
  target.applyFog = false
  handledMap.set(target, edgeHandling)
}
```

用起來像這樣。

```ts
optOutOfFog(skyDome, '天色本身就是白幕的顏色，由 sky-gradient 每幀收成霧色')
optOutOfFog(disc, '交給 atmosphere.skyBodyFade 淡出，貼近邊界時歸零')
optOutOfFog(cloudMesh, '交給 use-weather 的 cloudFadeRatio 淡到全透明')
```

那句說明是重點。它強迫你在關掉霧的當下就回答「到邊界時是誰把它收掉」，想不出來就表示還沒接。

然後開發模式掃一遍場景。

```ts
export function auditFogOptOut(scene: Scene): void {
  const missingList: string[] = []

  const targetList: object[] = [...scene.meshes, ...scene.particleSystems]

  for (const target of targetList) {
    if (!isFogAware(target))
      continue
    if (target.applyFog)
      continue
    if (handledMap.has(target))
      continue

    missingList.push(target.name)
  }

  if (missingList.length === 0)
    return

  const nameList = missingList.map((name) => `  - ${name}`).join('\n')

  console.warn(
    `[fog-opt-out] 這些東西不吃霧，但沒交代到了世界邊界要怎麼收：\n${nameList}\n`
    + `改用 optOutOfFog(目標, '到邊界時怎麼收') 登記，或讓它吃霧`,
  )
}
```

它不會攔阻任何事，只負責讓人在加東西的當下就知道「這個到邊界不會自己消失」。%ヽ(●`∀´●)ﾉ%

用 `WeakMap` 是為了讓場景丟掉時這裡不會拖著它們不放。

同樣的想法也用在大氣狀態上。

```ts
/**
 * 離世界邊界有多近，0 為平常、1 為貼著邊界
 *
 * 之所以要放在這裡而不是各自呼叫 getEdgeFogRatio：
 * 新加的東西要先知道「有這個函式」才想得到要用它。
 * 擺成一個現成的狀態欄位，讀它比記得呼叫某個函式可靠得多
 */
edgeRatio: number
```

## 雲影，還有一條查歪的冤枉路

最後來講雲影。%( ˘•ω˘ )%

天上飄著雲，地面卻從早到晚是同一個亮度。少了這一層，白沙庭園那一大片高明度的地會平得像一張紙。

太陽角度在變，但「這一塊比較暗」這件事從來沒發生過。

這個效果在專欄寫到一半的時候還是壞的，那時的結論是「取樣器沒綁上」。結論錯了，而錯得很有教育意義，所以這一節先講怎麼做，再講那條冤枉路。

### 平行光沒有投影貼圖

一般引擎的做法是給太陽掛一張捲動的雲圖，叫 light cookie。

Babylon 的 `projectionTexture` 只有聚光燈有，平行光沒有這個東西，所以只能走材質外掛，在著色器裡自己算。%(›´ω`‹ )%

而且雲影必須與真正的雲對得起來。這個世界是循環的，雲的圖樣正是為此才做成剛好一個世界寬。雲影若用另一個週期，跨過邊界的那一瞬間地上的暗塊會整片換一副樣子。

既然週期非得一樣，不如直接拿同一份圖樣。與其在著色器裡另外鋪一張噪聲，那會是另一副雲。

```ts
export function setCloudShadowPattern(
  scene: Scene,
  cellList: boolean[],
  patternCount: number,
  cellSize: number,
  cloudHeight: number,
): void {
  const coverList = blurPattern(cellList, patternCount)
  // 把 20 × 20 個布林值糊一糊烘成一張小圖
}
```

一次貼圖取樣，換到的是「地上那塊暗確實是頭頂那朵雲的」。%(๑•̀ㅂ•́)و✧%

### 糊過的圖樣還要拉回滿格

模糊過的圖樣才有中間值。原始圖樣是一格十四格寬的布林值，直接雙線性取樣會拉出菱形的塊。

但三乘三取平均有個陷阱。要留住 1.0，那一格的八個鄰居得全是雲；糊兩輪就要五格寬，而多數雲不到那麼大。

```ts
const peak = Math.max(...valueList)
if (peak <= 0) {
  return valueList
}

return valueList.map((value) => value / peak)
```

沒有這幾行，最濃的一格只剩零點七幾，而遮到滿的門檻訂在 0.78，最深的雲影永遠踩不到。整個效果會被壓成一層看不太出來的灰。%(´థ‸థ)%

拉回去之後，「雲最厚的地方」對上的就是「影子最深的程度」。這兩個數字本來就該是同一件事，雲多雲少都不必再回頭改門檻。

### 半影不該有二十格寬

雲影做出來之後看起來還是不太對，像一團髒污多過像影子。

去量了一下「從一成暗到九成暗」跨了多少距離，答案是二十格。而一朵雲的影子總共才五十來格寬，半影吃掉了將近一半。%(´థ‸థ)%

原因是模糊跑在雲的圖樣上，而一格雲有十四格寬。糊兩輪就是糊掉兩個紋素，也就是二十八格。

解法是把貼圖切細，模糊的半徑就與雲的大小脫鉤了。

```ts
function upsamplePattern(cellList: boolean[], size: number, factor: number): number[] {
  const fineSize = size * factor

  return Array.from({ length: fineSize * fineSize }, (_, index) => {
    const x = Math.floor((index % fineSize) / factor)
    const z = Math.floor(Math.floor(index / fineSize) / factor)
    return cellList[z * size + x] ? 1 : 0
  })
}
```

一格雲切成四個紋素，每個紋素三點五格，同樣糊兩輪，半影收到四格。貼圖從 1.6 KB 長到 25 KB。

| 做法 | 半影寬度 |
| --- | --- |
| 20 × 20，糊兩輪 | 20.3 格 |
| 40 × 40，糊兩輪 | 10.0 格 |
| **80 × 80，糊兩輪** | **4.0 格** |

取樣座標一個字都不用改。座標是拿世界座標除以「圖樣涵蓋的世界寬度」算出來的，那個寬度與貼圖有幾個紋素無關。%(๑•̀ㅂ•́)و✧%

邊緣清楚之後看得出雲的方格輪廓，那是對的。天上那朵雲本來就是方塊堆的，影子理當跟著有稜有角。

::: tip
這裡原本寫著一句「太陽有半度的張角，邊緣本來就有好幾格寬的半影」，用來替那團模糊背書。

那句話是錯的，而且錯得很遠。雲在地面上方約七十四格，半度張角投下來的半影是 74 × tan(0.53°)，也就是**零點七格**，連一格都不到。

真正該糊的理由不是太陽的大小，是雲自己的邊本來就不是一刀切的，厚度往邊緣遞減，遮光量跟著遞減。那幾格半影模擬的是這件事。

聽起來很有道理的物理解釋，還是要算一次。%( ˘•ω˘ )%
:::

### 沿著光線往上找

著色器要回答的問題是「頭頂那個位置有沒有雲」。

雲在一百零四格高，光沿著太陽的方向斜射下來，所以先依高度差把座標推回雲層，再扣掉雲此刻飄了多遠。

```glsl
float minespaceCloudCover() {
  if (cloudShadowParam.x <= 0.0) {
    return 0.0;
  }

  vec2 cloudPoint = vPositionW.xz
    - (cloudShadowProjection.z - vPositionW.y) * cloudShadowProjection.xy
    - vec2(cloudShadowProjection.w, 0.0);

  float cover = texture2D(cloudShadowSampler, cloudPoint * cloudShadowParam.y).r;

  return smoothstep(cloudShadowParam.z, cloudShadowParam.w, cover);
}
```

取樣器用重複定址，座標推到圖樣外面會自己繞回來。這與循環世界是同一件事。

太陽壓到地平線附近時要把整個效果收掉。仰角趨近零，那個往回推的距離會爆掉，整片地會被一格雲的顏色蓋滿。與其加保護，不如在還看得出形狀時就淡出。

覆蓋率一幀只算一次，擺在光照之前。它裡面有一次貼圖取樣，而等一下兩盞燈都要用到它。

```ts
return {
  CUSTOM_FRAGMENT_BEFORE_LIGHTS: `
    float minespaceCloudCoverValue = minespaceCloudCover();
  `,
}
```

### 平行光收得最深

```ts
return {
  '!info=computeLighting\\(viewDirectionW,normalW,([^,]+),(diffuse(\\d+)\\.rgb),([^,]+),(diffuse\\3\\.a),glossiness\\);': `
    {
      float cloudShade = 1.0;
      #ifdef DIRLIGHT$3
        cloudShade = 1.0 - cloudShadowParam.x * minespaceCloudCoverValue;
      #endif

      info = computeLighting(viewDirectionW, normalW, $1, $2 * cloudShade, $4 * cloudShade, $5, glossiness);
    }
  `,
}
```

`DIRLIGHT` 這個條件就是在挑「這一盞是不是平行光」，而整個場景裡只有日月那一盞是。平行光以外的那幾盞，整段條件編譯會被拿掉，`cloudShade` 就是常數 1.0，乘法會被編譯器摺掉，不花錢。

漫射與高光都要乘。少了高光那一項，一朵雲飄過水鏡池的時候，池面照樣閃著一道刺眼的反光，而那道光的來源明明正被遮著。%(・∀・)%

### 天光也要收一截

這一段原本沒有，而且當初還特地寫了一句「雲擋住的是太陽，不是天空」當理由。

那句話只對了一半。積雲罩在頭頂時擋掉的除了那顆太陽，還有頭頂那一大塊天空，站在雲底下天光確實也少了一截。

```ts
return {
  '!info=computeHemisphericLighting\\(viewDirectionW,normalW,([^,]+),(diffuse(\\d+)\\.rgb),([^,]+),([^,]+),glossiness\\);': `
    {
      float cloudSkyShade = 1.0 - cloudShadowParam.x * 0.5833 * minespaceCloudCoverValue;

      info = computeHemisphericLighting(viewDirectionW, normalW, $1, $2 * cloudSkyShade, $4, $5 * cloudSkyShade, glossiness);
    }
  `,
}
```

這一行是半球光專用的，條件編譯已經把它框在 `HEMILIGHT` 裡面，不必再自己加一層條件。

而真正逼著這一段長出來的不是物理，是色調映射。那件事留到後面講。%( ˘•ω˘ )%

::: warning
注入的那段 GLSL 裡不要寫註解。

Babylon 的前處理器用 `/(#ifdef)|(#else)|(#elif)|(#endif)|(#ifndef)|(#if)/` 掃每一行，沒有錨定行首，也不先把註解拿掉。註解裡只要提到條件編譯指令的名字，就會被當成真的指令，條件層數從此對不起來，後面整段著色器會憑空消失。%(´థ‸థ)%
:::

### 那條冤枉路

以上都寫完之後，畫面上完全看不到雲影。

當時查了一輪，逐項排除到只剩一個嫌疑，還把過程寫進了程式碼註解裡。

**一、著色器注入是好的。** 攔下真正送進 GPU 的原始碼確認過，雲影那個函式的定義在、`cloudShade` 有被賦值、也確實乘進了 `computeLighting`。

**二、uniform 真的送得到著色器。** 把函式改成 `return 1.0 - cloudShadowParam.x;`，整片地面明顯變暗，開關一切換就恢復。

**三、外掛機制沒問題。** `halo-soft-fade` 用一模一樣的寫法，而它是好的。

結論就這樣下了，剩下唯一的嫌疑是 `cloudShadowSampler` 那一次取樣讀出來恆為零。

於是接下來的時間全花在 `RawTexture` 有沒有真的綁上、`isReady` 是不是 false、通道格式對不對、`UniformBuffer.setTexture` 有沒有找到位置。

一個都沒查出問題，因為那條路上根本沒有問題。%(´థ‸థ)%

### 真正的兇手在雲那邊

回頭去看雲的圖樣，答案一秒就出來了。

那時候的雲是細胞自動機長的，再加一道「削掉過大的雲團」。前面 EP06 講過，那兩道疊起來是收斂到空的，全世界只剩十二格雲。

十二格。而且全擠在同一條 Z 帶上。

雲只往 +X 飄，所以那條帶以外的地面，從開場到關掉分頁都不會有雲經過。%(´థ‸థ)%

加上前面說的模糊沒拉回滿格，就算真的站在雲底下，那塊暗也淡到看不出來。

路人：「所以著色器從頭到尾都是好的？」
鱈魚：「對，我對著一支正常的著色器查到天荒地老。%( ˘•ω•˘ )%」

### 還有一個兇手，藏在色調映射裡

把雲補回來、門檻修好之後，雲影還是看不太出來。%(´థ‸థ)%

這次學乖了，先量再猜。拿真實的模組跑一個乾淨的場景，把場景實際的光照參數照抄進去，然後讀回畫素值。

| 條件 | 地面亮度 |
| --- | --- |
| 只有平行光，不做色調映射 | 164 ～ 255 |
| 加上天光，不做色調映射 | 255 ～ 255 |
| 加上天光 + ACES，白沙 | 209 ～ 209 |
| 加上天光 + ACES，一般方塊 | 180 ～ 209 |

第二行就是答案。**平行光加天光加環境色，白沙的線性亮度是 1.75。** 那早就衝過 ACES 的膝點了，整片地貼在天花板上。

貼在天花板的地方，你把平行光砍掉一半，數字從 1.75 掉到 1.23，映射出來還是同一格。%( ˘•ω˘ )%

而這個效果存在的理由，本來就是「白沙庭園那一大片高明度的地會平得像一張紙」。最需要它的那片地，剛好就是唯一照不出它的地方。

所以天光也得收。兩邊一起把總量壓到膝點以下，那塊暗才掉得出來。

| 平行光 / 天光收掉幾成 | 白沙 | 一般方塊 |
| --- | --- | --- |
| 0.60 / 0.30 | 204 ～ 209 | 142 ～ 209 |
| **0.72 / 0.42** | **174 ～ 209** | **108 ～ 209** |
| 0.82 / 0.55 | 130 ～ 209 | 75 ～ 209 |

最後選了 0.72 與 0.42。

這兩個數字比物理上該有的大，而它們是照著這座場景的曝光配出來的，不是通用值。哪天曝光調低、畫面離開了膝點，這兩個數字就該一起往回收。%( •̀ ω •́ )✧%

### 學到的三件事

第一件，**分不出「沒綁上」與「綁上了但圖是空的」的時候，先讓資料變成常數。**

拿一張全白的 `RawTexture` 去比對，地面該整片黑掉。黑了就是機制沒問題，剩下的全是資料的事。這一步只要五分鐘，當初卻跳過了。

跳過的原因也很老實，因為那時候已經先入為主認定是取樣器的問題，就一路往那個方向查下去。%(›´ω`‹ )%

第二件，**攔下真正送進 GPU 的原始碼，不要離線模擬。**

這一招雖然沒抓到兇手，但它排除掉的東西是真的。Babylon 的著色器經過 include 展開、前處理器、外掛注入、defines 代換好幾層，中間任何一步出問題，你在編輯器裡看到的字串跟 GPU 收到的字串就不一樣。

```js
const original = WebGLRenderingContext.prototype.shaderSource
WebGLRenderingContext.prototype.shaderSource = function (shader, source) {
  if (source.includes('minespaceCloudCover')) {
    console.log(source)
  }
  return original.call(this, shader, source)
}
```

在主控台攔一下 `shaderSource` 就知道實機到底編了什麼。%(๑•̀ㅂ•́)و✧%

順帶一提，最終 GLSL 裡沒有 `#ifdef` 是正常的，前處理器早就把條件解掉了。第一次看到還以為是條件編譯壞了。

第三件，**畫面上看不到效果，不代表效果沒算。**

貼在色調映射天花板上的地方，你加什麼都不會動。加東西之前先確認那塊地還在曲線的線性段裡，否則就是對著一個吃不進去的地方一直加。%( ˘•ω˘ )%

而要確認這件事，靠眼睛是不行的，要讀畫素值。上面那兩張表跑起來各只花幾分鐘，卻是整件事裡唯一真正推進度的東西。

修完之後，地面大約有兩成四的面積會被雲影掃過，最深的地方在白沙上是 174 對 209、在一般方塊上是 108 對 209，半影四格寬。太陽角度一變，那塊暗也跟著挪。%(*´∀`)~♥%

## 專欄總結 🐟

十章寫完了。%(*´∀`)~♥%

以上程式碼可以[在此取得](https://github.com/Codfisher/cod-aquarium/tree/main/content/aquarium/minespace)，場景本身在[這裡](/aquarium/minespace/)。

回頭看，Minespace 的視覺大致就這幾件事。

- **批次**。Thin Instance 把幾十萬顆方塊壓成幾百次繪製呼叫，這是一切的前提
- **造假**。法線改成朝上、陰影量化到像素格、透光用一次點積近似次表面散射，全部都不是物理正確，但看起來對
- **注入**。`MaterialPluginBase` 讓你在 `StandardMaterial` 的著色器裡加東西，不必重寫整套光照
- **收邊**。霧、深度、混合模式、繪製順序，畫面上那些「怪怪的」幾乎都出在這四件事上
- **量測**。幀率不會告訴你慢在哪，掛名計時會
- **先驗證資料**。看不到東西的時候，先把輸入換成常數，再去懷疑機制
- **讀畫素值**。「看不到」有兩種，一種是沒算，一種是算了但被色調映射壓平了

而最花時間的往往不是效果本身，是那些藏在預設值裡的東西。材質的 `ambientColor` 預設是黑的、粒子預設不吃霧、`darkness` 給 0.5 在強光下等於沒有影子。

這些都不會報錯，只會讓畫面「有點不對但說不上來」。%( ˘•ω˘ )%
