# Minespace - EP09：天氣與粒子

大家好，我是鱈魚。

這一章來看會動的空氣。%੭ ˙ᗜ˙ )੭%

Minespace 的天氣不是全域的，每一座箱庭有自己的天氣。聽雨亭永遠在下雨、吹雪野永遠在颳暴風雪、地獄谷永遠是滾燙的熱氣。

走進去才會遇到。

## 大氣狀態要疊起來

三個系統會同時想改場景的霧與光。

日夜循環寫入「這個時刻的基準」、天氣在基準之上疊雨與霧、漫遊控制器最後再疊上洞穴與水面。

三邊各自直接改 `scene` 的話會互相蓋掉。走進洞裡的變暗會被下一幀的陰天覆寫，日夜的光色又會被兩者一起洗掉。%(´థ‸థ)%

所以中間插一份共用狀態。

```ts
export interface AtmosphereState {
  fogColor: Color3;
  fogStart: number;
  fogEnd: number;
  /** 平行光的強度倍率，陰天會壓低 */
  lightRatio: number;
  /** 天光的強度倍率 */
  ambientRatio: number;
  /** 直射陽光還剩幾成，高光專用 */
  specularRatio: number;
  flashRatio: number;
  // ...
}
```

三個倍率分開是有原因的。

### 陰天不是變暗，是光的來源換了

太陽被雲蓋住，整片天空自己變成一盞巨大的柔光燈。

兩者若共用同一個倍率，把平行光壓到影子消失時，天光會跟著一起掉，整個世界暗成傍晚。

```ts
export const RAIN_ATMOSPHERE = {
  fogColor: new Color3(0.62, 0.66, 0.72),
  fogStart: 4,
  fogEnd: 26,
  /** 厚雲之後已經沒有一個「方向」可言 */
  lightRatio: 0.12,
  /** 落到地面的總光量其實掉得不多，只是沒有方向了 */
  ambientRatio: 1.05,
  specularRatio: 0.05,
} as const
```

畫面才會是「陰而亮」而不是「傍晚」。%( •̀ ω •́ )✧%

### 高光要單獨收

漫射與高光該分開算。雲層把太陽打散之後，天空整片還是亮的，漫射光只是變柔、沒有消失。

但高光需要一個「又小又亮的點」才照得出來，那正是雲最先抹掉的東西。

少了這一項，暴雨裡的濕地面照樣會被太陽打出一道刺眼的反光，水面也還在閃。明明頭頂連太陽的位置都看不出來。%(・∀・(・∀・(・∀・*)%

### 暴風雪與雨的差別不是更暗，是更白

```ts
export const SNOW_ATMOSPHERE = {
  /** 比晴天的霧更白，接近純白但留一點冷 */
  fogColor: new Color3(0.88, 0.91, 0.95),
  fogStart: EDGE_FOG_START,
  fogEnd: EDGE_FOG_END,
  lightRatio: 0.1,
  /** 雪把光從地面反回來，天光比任何一種天氣都高 */
  ambientRatio: 1.15,
  specularRatio: 0.04,
} as const
```

雨天是一層冷灰壓在頭上，看得遠但看得暗；暴風雪相反，空氣裡飛滿了反光的雪，畫面是亮的，但十來格外什麼都沒有。

那叫白矇。

這裡試過 17 格、也試過 11 格，兩個都還「看得見這是一座庭園」。而暴風雪的定義正是看不見。

整個專案裡唯一真正做到「什麼都看不到」的是世界邊界那道簾子，所以吹雪野直接照抄那組數字，半格外開始褪色、六格外一片空白。

三盞石燈籠因此一次只看得到一盞，而且是先看到暈、再看到燈。%(*´∀`)~♥%

五座箱庭的大氣切一輪就很清楚了。

<demo-atmosphere-preset />

左上角會顯示三個倍率。切到聽雨亭，影子幾乎不見但畫面沒有變暗，那就是「陰而亮」；切到地獄谷，霧色整個換成岩漿那池光的橘紅。

順便注意中間那池水。晴天時水面有一道刺眼的反光，切到聽雨亭或吹雪野就整個鈍掉了，那正是高光要單獨收的理由。%( •̀ ω •́ )✧%

## 雨

雨雲跟著玩家走，只在頭頂一小塊區域生成粒子，遠處的雨交給霧氣表現。

```ts
const particleSystem = new ParticleSystem('rain', maxParticleCount, scene)
particleSystem.particleTexture = createRainTexture(scene)
particleSystem.applyFog = true
particleSystem.emitter = emitterPosition
particleSystem.renderingGroupId = WEATHER_RENDERING_GROUP
particleSystem.billboardMode = ParticleSystem.BILLBOARDMODE_Y
```

`BILLBOARDMODE_Y` 是關鍵。預設的公告板會讓雨絲整片跟著鏡頭轉，抬頭一看全部躺平。鎖在 Y 軸雨才會一直是垂直落下的樣子。

`renderingGroupId` 也不能省。陰天罩是罩在鏡頭外的一層灰，雨勢一大它的不透明度就接近全滿。雨絲若畫在它前面，抬頭與望向天邊的那些雨會被整片灰蓋掉。

看起來就是「沒在下雨，地上卻有水花」。%(・∀・(・∀・(・∀・*)%

### 屋頂底下不該下雨

粒子系統本身沒有碰撞，雨絲一路落到壽命結束為止，中間有沒有屋頂一概不管。

露天時看不太出來，但一走進聽雨亭就露餡，雨會直接穿過屋瓦下到室內。%(›´ω`‹ )%

解法是覆寫 `updateFunction`。

```ts
const updateParticles = particleSystem.updateFunction
particleSystem.updateFunction = (particleList) => {
  updateParticles.call(particleSystem, particleList)

  for (const particle of particleList) {
    const impactY = readImpactY(
      Math.floor(particle.position.x + 0.5),
      Math.floor(particle.position.z + 0.5),
    )
    if (Number.isNaN(impactY) || particle.position.y > impactY)
      continue

    particle.age = particle.lifeTime
  }
}
```

每一幀檢查雨滴有沒有落到它那一格柱的表面以下，是的話就把年齡推到壽命，這一幀就回收。

於是屋子裡不會有雨、樹冠底下的雨會稀疏一點，而站在屋裡往外看，開口外面照樣在下。

這正是「聽雨而自己是乾的」成立的條件。%(*´∀`)~♥%

<demo-rain />

把「雨滴打到東西就停」關掉，雨會直接穿過屋瓦下到亭子裡，水花也會在屋頂底下濺起來。%(・∀・(・∀・(・∀・*)%

雨勢拉小則看得到水花的門檻，零星幾條雨絲的時候腳邊是不濺水的。

### 射線要快取

落點是射線問來的，每幀要打好幾十道。

```ts
const impactYMap = new Map<number, number>()

function readImpactY(blockX: number, blockZ: number): number {
  const key = blockX * WORLD_SIZE + blockZ
  const cached = impactYMap.get(key)
  if (cached !== undefined)
    return cached

  const impactY = castRainRay(blockX, blockZ) ?? Number.NaN
  impactYMap.set(key, impactY)

  return impactY
}
```

地形生成後不再變動，查過就記著。`null` 以 `NaN` 記著，代表那一格柱是空的。

### 水花要貼著地

```ts
splashSystem.startPositionFunction = (_worldMatrix, positionToUpdate) => {
  if (splashSpotCount === 0)
    return

  const offset = Math.floor(Math.random() * splashSpotCount) * 3
  positionToUpdate.set(
    splashSpotList[offset] ?? 0,
    splashSpotList[offset + 1] ?? 0,
    splashSpotList[offset + 2] ?? 0,
  )
}
```

發射盒是相對發射點的，跟著玩家就會跟著跳。改成每一顆都挑一個射線落點，玩家跳起來、走上坡、站在水邊，水花都還是貼著地。

而落點的數量順便就是「頭頂開不開闊」的取樣數。

```ts
const openRatio = splashSpotCount / SPLASH_SPOT_COUNT
const splashRatio = Math.max(0, ratio - SPLASH_START_RATIO) / (1 - SPLASH_START_RATIO) * openRatio
```

打得到地面的比例越低，水花就越少。屋簷下與樹蔭裡自然就不會濺水。%( •̀ ω •́ )✧%

## 雪

雪與雨是同一套骨架，差別全在物理。

雨是被重力拉下來的線，雪是浮在空氣裡被吹著走的片。

所以雪沒有水花、沒有拉長的比例，重力只有雨的四十分之一，而橫向的風比垂直的重力還大。

### 一個踩過的坑

橫向的風原本掛在 `gravity` 上給了 -9。

但重力是加速度不是速度。四秒之後橫向位移是 ½ × 9 × 4²，也就是七十幾格。%(⊙ o ⊙)%

而這座箱庭的能見度只有十七格，雪片因此在還沒降下來之前就已經衝出視野。

看起來就是「在高空飄走了，地面附近什麼都沒有」。

```ts
particleSystem.gravity = new Vector3(0, -1, 0)
/** 往下的分量與橫向的分量差不多，那個斜率就是雪被吹斜的角度 */
particleSystem.direction1 = new Vector3(-1, -0.9, 0.2)
particleSystem.direction2 = new Vector3(-0.72, -0.66, 0.5)
particleSystem.minEmitPower = 6
particleSystem.maxEmitPower = 8.5
```

真正的風是等速的。初速一次給足，重力只留下微弱的下沉。

<demo-snow-wind />

左邊那台幾乎看不到雪經過眼前，全部在高空就飛走了；右邊才是斜著穿過視線的暴風雪。%(๑•̀ㅂ•́)و✧%

### 生成盒要往上風推

這是雪與雨最不一樣的地方。

雨幾乎垂直落下，生成盒對準鏡頭就好。雪是斜著飛的，盒子若也對準鏡頭，有一半的雪一出生就往下風飄走，根本不會經過眼前。

```ts
const WIND_UPWIND_OFFSET_X = 3
const WIND_UPWIND_OFFSET_Z = -1
```

偏移量是算出來的。雪從生成高度落到地面約兩秒半，這段時間橫向會走八格左右，所以把整個盒子往上風推，雪片下降到視線高度時剛好穿過鏡頭這一帶。%(๑•̀ㅂ•́)و✧%

### 加速不能讓雪變稀

```ts
const EMIT_RATE_HEADROOM = 2
```

這個系統的密度不是發射率決定的，是粒子上限決定的。發射率一旦高到能把池子填滿，畫面上就永遠是上限那麼多片。

風加快之後每一片穿過泡泡、落到地面的時間都變短，池子空得更快。倍率就是留給這件事的餘裕。

沒有它，加速的代價會是雪變稀，「颳得更兇」看起來反而像「雪下得更小」。%(・∀・(・∀・(・∀・*)%

## 落葉

金葉苑的落葉是最花時間調的粒子。%( ˘•ω˘ )%

### 用噪音當風

```ts
const noiseTexture = new NoiseProceduralTexture('autumn-leaf-noise', 128, scene)
noiseTexture.animationSpeedFactor = 0.35
noiseTexture.brightness = 0.5
noiseTexture.octaves = 4
noiseTexture.persistence = 1.6
particleSystem.noiseTexture = noiseTexture
particleSystem.noiseStrength = new Vector3(6, 2, 6)
```

只有初速的話，每片葉子都是一條筆直的斜線。掛上一張會動的噪音貼圖當作亂流，路徑就彎彎曲曲了。

`animationSpeedFactor` 調的是噪音場自己翻動的速度，不是葉子的速度。轉得太快，葉子等於每一瞬間都被推往不同方向，看起來是在抖。

橫向推力要給大一點，這是「翻轉看得出來」的關鍵，後面會說。

### 速度上限才是主要旋鈕

```ts
particleSystem.addLimitVelocityGradient(0, 3)
particleSystem.addLimitVelocityGradient(1, 3)
particleSystem.limitVelocityDamping = 0.35
```

重力與亂流都是往速度上累加的，不設限的話葉子只會越飄越快。

速度一超過上限就打對折，於是很快就穩定在上限附近，之後既不加速也不停下來。那正是空氣阻力下的等速下墜。%( •̀ ω •́ )✧%

阻尼要放鬆一點。拉得太緊，亂流每次把葉子推出去都立刻被壓平，擺盪的幅度出不來。

### 翻轉的節奏

```ts
const angularRhythmList: [number, number][] = [
  /** 剛從枝頭鬆脫，帶著各自的初速 */
  [0, 6],
  /** 攤平滑翔，幾乎不轉 */
  [0.18, 1],
  /** 失速，猛翻幾圈 */
  [0.34, 8],
  [0.52, 2],
  [0.71, 7],
  /** 快落地時慢下來 */
  [0.88, 1.5],
  [1, 5],
]
for (const [life, speed] of angularRhythmList) {
  particleSystem.addAngularSpeedGradient(life, -speed, speed)
}
```

固定的轉速會變成一個等速轉動的機械零件。

真正的落葉是有節奏的，攤平滑翔一段、忽然失速猛翻幾圈、再攤開、再翻。

每一段又給正負兩端，同一時刻不同葉子的轉向與快慢都不一樣，甚至會在半途反轉。那正是葉子吃到一陣風、翻回去的樣子。%(*´∀`)~♥%

一旦用了梯度，`minAngularSpeed` / `maxAngularSpeed` 就會被忽略。

### 關掉公告板

```ts
particleSystem.isBillboardBased = false
```

粒子預設是廣告板，永遠正面朝著鏡頭，`angularSpeed` 只能讓它在畫面上打轉，看起來像一枚在原地旋轉的貼紙。

關掉之後，葉片會依自己的行進方向立在空間裡，一邊被風推著改變方向、一邊繞著自己的軸翻面。

於是有時看到整片葉面、有時只看到側面那一條線，那才是葉子在飄。%ヽ(●`∀´●)ﾉ%

<demo-leaf-billboard />

預設就是開著廣告板的樣子，一堆在原地轉的貼紙。關掉它，葉子立刻立體起來。%(*´∀`)~♥%

把橫向推力拉到 0 再看一次，方向永遠指著地面，葉片只會繞著垂直軸打轉，那看起來是閃爍不是翻滾。

這也是為什麼橫向推力要拉到與下墜速度同一個量級。若下墜速度遠大於橫向速度，方向就永遠指著地面，葉片一直維持同一個姿態，只會繞著垂直軸打轉。

那看起來是閃爍，不是翻滾。

### 要預熱

```ts
particleSystem.preWarmCycles = 150
particleSystem.preWarmStepOffset = 20
```

不預熱的話，第一次望向林子會看到葉子整批從樹冠同時出發，像有人把一桶葉子倒下來。%(・∀・(・∀・(・∀・*)%

## 空氣裡的顆粒

這個場景的空氣一直是空的。霧是一層數學，光束是一道後製，兩者之間什麼都沒有。

人之所以「看得見」陽光，正是因為空氣裡有東西擋在光路上。沒有那些顆粒，光是不可見的。%( ˘•ω˘ )%

```ts
const SPREAD_RADIUS = 11
const RECENTER_INTERVAL = 0.25
```

做法是把發射器綁在鏡頭上，只在身邊十來格內撒顆粒。

顆粒撒出去之後就留在世界座標上，人往前走，它們自然被留在身後，幾秒之後壽命到了再從新的位置生出來。

於是走到哪裡身邊都有東西在飄，卻不會有「一團顆粒黏著鏡頭跑」那種假。%( •̀ ω •́ )✧%

發射點不必每一幀跟。顆粒是撒在鏡頭周圍二十二格見方的盒子裡的，走路一秒也才五六格，四分之一秒對齊一次完全看不出落差。

### 三種空氣共用一組系統

```ts
/** 洞裡換一種空氣，顏色就地插值，連活著的顆粒都會跟著換色 */
Color4.LerpToRef(POLLEN_COLOR, CAVE_COLOR, caveRatio, moteSystem.color1)
Color4.LerpToRef(POLLEN_COLOR_FADED, CAVE_COLOR_FADED, caveRatio, moteSystem.color2)

/** 白天才有花粉，洞裡則永遠是暗的但有燈火，塵照樣看得見 */
const litRatio = Math.max(dayRatio, caveRatio * 0.7)
moteSystem.emitRate = MOTE_EMIT_RATE * litRatio * visibleRatio

/** 螢火只在地表的夜裡出來 */
const nightRatio = Math.max(0, 1 - dayRatio / FIREFLY_DAY_THRESHOLD)
fireflySystem.emitRate = FIREFLY_EMIT_RATE * nightRatio * (1 - caveRatio) * visibleRatio
```

白天是被太陽照亮的花粉、夜裡換成幾點螢火、洞裡則是冷灰的塵。

螢火走相加混合，這也是它繞開材質那道亮度上限的方式。

```ts
fireflySystem.blendMode = ParticleSystem.BLENDMODE_ADD

/** 一生的亮度：亮起、撐住、熄掉 */
fireflySystem.addColorGradient(0, FIREFLY_COLOR_DIM, FIREFLY_COLOR_DIM)
fireflySystem.addColorGradient(0.25, FIREFLY_COLOR, FIREFLY_COLOR)
fireflySystem.addColorGradient(0.6, FIREFLY_COLOR, FIREFLY_COLOR)
fireflySystem.addColorGradient(1, FIREFLY_COLOR_DIM, FIREFLY_COLOR_DIM)
```

螢火不是持續亮著的燈，牠是一明一滅的。用一整條壽命走完一次明滅，一群螢火各自的壽命又不一樣，整片看過去就是此起彼落地閃。%(*´∀`)~♥%

`visibleRatio` 必須自己一個參數，不能折進 `dayRatio`。螢火是拿 `1 - dayRatio` 反推的，把邊界折進去等於告訴牠們天黑了，大白天走到邊界反而會召出一群螢火。%(・∀・(・∀・(・∀・*)%

拉白晝程度看花粉與螢火換班。下面兩節要講的兩個開關也在這裡，先玩一下再往下看。

## 粒子一定要吃霧

這是最容易漏掉的一行。%(๑•̀ㅂ•́)و✧%

```ts
particleSystem.applyFog = true
```

Babylon 的粒子預設不套用場景霧氣。少了這一行，遠處的葉子會維持飽滿的金黃浮在一片白霧前面，像貼在螢幕上的貼紙。

整個場景靠霧把遠方藏起來，粒子是唯一的漏網之魚。

世界邊界更是非開不可。停止發射只管得到還沒生出來的那些，已經飄在空中的要等壽命走完，而那段時間人早就走到邊界了。

只有霧管得到它們。

上面那個範例把「粒子吃霧」關掉就看得到，四周白成一片時顆粒依然清清楚楚地浮在白幕前面。%(´థ‸థ)%

## 粒子也要跟著日夜明暗

粒子不吃場景光照，顏色是寫死在系統上的常數。

入夜之後整個世界暗下來，只有落葉、雨絲與霧氣還維持著大白天的亮度。這是整套日夜循環最容易露餡的地方。%(´థ‸థ)%

```ts
export function createParticleDimmer(systemList: ParticleSystem[]): ParticleDimmer {
  const backupList: SystemBackup[] = systemList.map((system) => ({
    system,
    color1: [system.color1.r, system.color1.g, system.color1.b],
    color2: [system.color2.r, system.color2.g, system.color2.b],
    colorDead: [system.colorDead.r, system.colorDead.g, system.colorDead.b],
    gradientList: (system.getColorGradients() ?? []).map((entry) => ({
      entry,
      color1: [entry.color1.r, entry.color1.g, entry.color1.b],
      color2: entry.color2 ? [entry.color2.r, entry.color2.g, entry.color2.b] : null,
    })),
  }))
  // ...
}
```

兩個重點。

一是記住原本的顏色，每次都拿原色去乘。在現值上再乘一次的話，調個幾次就會越調越黑，再也回不來。

二是用了顏色梯度的系統，`color1` / `color2` 就形同虛設。粒子每一幀是從梯度上取色的，所以要改的是梯度本身。

而且只縮放顏色、透明度原封不動。alpha 是粒子一生的淡入淡出在用的，動到它葉子會憑空出現或消失。

同一個範例把「跟著日夜明暗」關掉，再把白晝程度拉到 0。整個世界暗下來了，只有那些顆粒還維持著大白天的亮度浮在暗景前面。%(›´ω`‹ )%

## 雨後的濕潤

雨本身只是幾千條掉下來的線，落地就沒了。真正讓人相信剛下過雨的是雨停之後那段地還是濕的時間。

少了它，走出聽雨亭的那一步，整個世界會在一瞬間乾透。%(›´ω`‹ )%

```ts
const WET_DIFFUSE_RATIO = 0.68
const WET_SPECULAR = 0.42
const WET_SPECULAR_POWER = 20
```

兩件事同時做，漫射壓暗、高光提亮並散開。

濕的表面看起來比乾的暗，這是它最容易辨認的特徵。水填進了表面的孔隙，進去的光在裡面多反射幾次才出得來，途中被吸收掉的部分就是那道暗。

高光則相反，水在上面鋪成一層平滑的膜，原本被粗糙表面打散的反射全部聚回同一個方向。

兩者缺一都不成立。只壓暗會變成髒，只加高光會變成上了一層蠟。%( •̀ ω •́ )✧%

<demo-wetness />

把濕潤度拉滿，再分別關掉其中一項。只剩壓暗那一邊看起來就是髒掉，只剩高光那一邊則像上了一層蠟。%(・∀・)%

```ts
material.specularColor.set(
  lerp(specular[0], WET_SPECULAR, wet),
  lerp(specular[1], WET_SPECULAR, wet),
  lerp(specular[2], WET_SPECULAR, wet),
)
```

高光要往同一個目標值收，不是照原值放大。

原本的高光是每種方塊各自調過的，有的 0.08、有的乾脆是零。照倍率放大的話，原本是零的那幾種永遠濕不起來，而水膜是蓋在表面上的一層，底下是什麼材質並不影響它有多亮。

哪些材質淋得濕則在建網格的當下決定。

```ts
const isTransparent = blockDef.alpha !== undefined && blockDef.alpha < 1
if (isTransparent || blockDef.cutout || (blockDef.emissive ?? 0) > 0)
  return

this.wetMaterialSet.add(material)
```

半透明的水、冰與玻璃本來就是濕的，再壓暗一次只會變成一塊髒玻璃；鏤空的花草沒有高光可言，壓暗漫射只會讓整片草黑掉；會自己發亮的燈火則是光源，光源不會因為淋雨而變暗。

## 晨昏的光束

最後補一個後製效果。

```ts
const godRays = new VolumetricLightScatteringPostProcess(
  'god-rays',
  { postProcessRatio: 1, passRatio: 0.25 },
  camera,
  sunDisc,
  60,
  Texture.BILINEAR_SAMPLINGMODE,
  scene.getEngine(),
  false,
  scene,
)
```

做法是螢幕空間的放射狀模糊。先把場景畫成一張只有太陽是亮的黑白圖，再沿著「太陽在畫面上的位置」往外一路取樣疊加。

擋在太陽前面的樹與鳥居會在那張圖上留下黑影，於是光束自然就從枝葉的縫隙裡透出來。%(*´∀`)~♥%

<demo-god-rays />

光束是從鳥居的橫樑與樹冠的縫隙鑽出來的，關掉之後那些縫就只是縫。%( •̀ ω •́ )✧%

有三件事要處理。

### 太陽的位置要自己算

```ts
godRays.useCustomMeshPosition = true
godRays.customMeshPosition = new Vector3()

// 每幀更新
godRays.customMeshPosition
  .copyFrom(camera.position)
  .addInPlace(sunDisc.position)
```

太陽那片網格開著 `infiniteDistance`，它的 `position` 存的是「相對鏡頭的偏移」而不是世界座標。

交給後製自己去讀，投影出來的原點會落在世界原點附近，光束的方向整個是錯的。

### 罩住整片天的東西要排除

```ts
const excludedNameList = [
  SKYBOX_NAME, STAR_FIELD_NAME, OVERCAST_NAME, CLOUD_LAYER_NAME,
  SUN_GLOW_NAME, MOON_DISC_NAME, MOON_GLOW_NAME,
]
```

遮蔽圖裡除了太陽以外全部畫成黑色，天空罩、星空盒與陰天罩都是包住鏡頭的盒子。留著它們，太陽會被自己的背景蓋掉，一道光束都出不來。%(・∀・(・∀・(・∀・*)%

### 只在該出現的時候存在

那張遮蔽圖要把整個世界重畫一次，所以平常不該存在。

```ts
sample.godRayRatio = sample.sunVisibility * (1 - smoothRange(sample.sunHeight, 0.06, 0.42))
```

太陽貼近地平線時才有，那是光線斜著穿過整片林子的角度。太陽一升高，光線幾乎垂直落下，光束就沒有東西可以穿了。

再加上「人有沒有正對著太陽」。太陽跑到背後時，投影出來的原點落在畫面之外，光束會變成從螢幕邊緣掃進來的一道怪東西。

關閉時連那張遮蔽圖都要從算繪清單裡拿掉。

```ts
camera.detachPostProcess(godRays)
if (scatteringTexture) {
  const index = camera.customRenderTargets.indexOf(scatteringTexture)
  if (index !== -1) {
    camera.customRenderTargets.splice(index, 1)
  }
}
```

只 detach 後製是不夠的，遮蔽圖是掛在鏡頭上的，拿掉才真的省下那一次重畫。

順帶一提，插回去時要插在最前面。

```ts
camera.attachPostProcess(godRays, 0)
```

後製鏈的順序就是套用的順序。光束要在色調映射之前疊上去，才會跟著整個畫面一起被曝光曲線壓過；擺在後面則是疊在成品上，亮部會直接爆掉。

### 一個 Babylon 的小疏漏

```ts
const disposeGodRays = godRays.dispose.bind(godRays)
godRays.dispose = (disposeCamera?: Camera) => {
  disposeGodRays(disposeCamera ?? camera)
}
```

`VolumetricLightScatteringPostProcess.dispose` 的第一行是 `camera.getScene().customRenderTargets.indexOf(...)`，它無條件讀 `camera`，而基底類別的 `dispose` 那個參數本來是選填的。

場景自己回收後製時是不帶參數呼叫的，`camera` 於是是 `undefined`，整個 `engine.dispose` 當場中斷在這裡，後面該收的東西全部沒收到。%(´థ‸థ)%

只要頁面卸載或熱更新就會踩到。改不了它的原始碼，但可以把相機綁死在這個實例上。
