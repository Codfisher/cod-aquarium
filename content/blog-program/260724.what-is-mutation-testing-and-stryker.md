# 你的測試真的有在測試嗎？來聊聊突變測試與 Stryker

大家好，我是鱈魚。

大家有沒有遇過這種狀況，開心地寫完一堆單元測試，跑起來全部亮綠燈，覆蓋率還高達 100%，於是心滿意足地收工回家。

問題來了，覆蓋率 100% 到底代表什麼？它只代表你的測試「有經過」那幾行程式，可完全不代表那幾行「有被好好驗證」。%(´,,•ω•,,)%

<br/>

鱈魚：「所以我盯著覆蓋率報告傻笑半天，其實是在自我感覺良好？%(ﾟдﾟ；)%」

路人：「差不多是這樣沒錯。%( ˘•ω•˘ )%」

<br/>

那有沒有一種指標，能真正告訴我「測試到底擋不擋得住 bug」？

有的，這就是「突變測試」（Mutation Testing）。%(ﾉ>ω<)ﾉ%

## 什麼是突變測試

突變測試的概念其實很壞，但也很聰明。

它會故意把你的程式碼改壞，製造出一堆有 bug 的版本，這些被改壞的版本就叫做「突變體」（Mutant）。

改壞的方式五花八門，例如：

- 把 `>=` 改成 `>`
- 把 `+` 改成 `-`
- 把 `&&` 改成 `||`
- 直接把某行程式刪掉

接著它會拿你原本的測試，去跑每一個突變體。

<br/>

這時候有兩種結果：

- **突變體被殺死（Killed）**：測試失敗了，代表測試成功抓到這個被改壞的地方，這是好事。
- **突變體存活（Survived）**：測試竟然還是全綠，代表程式被改壞了測試卻沒發現，這就是漏洞。

<br/>

最後它會把「被殺死的比例」算成一個「突變分數」（Mutation Score）：

```text
突變分數 = 被殺死的突變體 / 總突變體數量
```

覆蓋率回答的是「這行有沒有被跑過」，突變分數回答的是「這行如果寫錯了，你的測試攔不攔得住」。後者，才是測試真正的實力。%(ゝ∀・)b%

## 一個看似測得很周全的案例

光講概念太乾了，我們直接來看程式。%( •̀ ω •́ )✧%

假設有個計算運費的函數，規則稍微複雜一點：

- 一般會員：滿 1000 免運，否則收 60 元
- VIP 門檻較低：滿 500 免運，否則收 30 元

`shipping.ts`

```ts
interface Order {
  amount: number;
  isVip: boolean;
}

export function getShippingFee(order: Order): number {
  const threshold = order.isVip ? 500 : 1000
  const base = order.isVip ? 30 : 60
  return order.amount >= threshold ? 0 : base
}
```

接著我們很盡責地寫測試，一般會員與 VIP 各測「免運」跟「要付運費」兩種，這裡用 [Vitest](https://vitest.dev/) 示範：

`shipping.test.ts`

```ts
import { describe, expect, it } from 'vitest'
import { getShippingFee } from './shipping'

describe('getShippingFee', () => {
  it('一般會員金額足夠免運', () => {
    expect(getShippingFee({ amount: 1500, isVip: false })).toBe(0)
  })

  it('一般會員金額不足要收運費', () => {
    expect(getShippingFee({ amount: 800, isVip: false })).toBe(60)
  })

  it('VIP 門檻較低，同樣金額就免運', () => {
    expect(getShippingFee({ amount: 800, isVip: true })).toBe(0)
  })

  it('VIP 金額不足，收較低運費', () => {
    expect(getShippingFee({ amount: 300, isVip: true })).toBe(30)
  })
})
```

跑一下測試，全綠。覆蓋率一看，100%，完美。%ᕕ( ᐛ )ᕗ%

一般會員、VIP、免運、要運費，四種組合全測過了，這測試怎麼看都挺周全，可以安心下班了吧。

<br/>

鱈魚：「這次我可是連 VIP 都想到了，穩如泰山。%(๑•̀ㅂ•́)و✧%」

路人：「穩嗎？我怎麼看到一條大裂縫。%( ｀ー´)%」

## 讓 Stryker 上場踢館

嘴巴說得再滿都沒用，我們請突變測試來驗貨。

JavaScript / TypeScript 世界最有名的突變測試工具，就是 [Stryker](https://stryker-mutator.io/)。名字取自漫威裡專門獵殺變種人的反派 Stryker，用來獵殺程式裡的突變體，這命名真的超有品味。%(๑•̀ㅂ•́)و✧%

<br/>

因為我們用 Vitest，所以搭配 Vitest runner，先安裝套件：

```bash
npm install --save-dev @stryker-mutator/core @stryker-mutator/vitest-runner
```

接著加上設定檔：

`stryker.config.json`

```json
{
  "$schema": "./node_modules/@stryker-mutator/core/schema/stryker-schema.json",
  "testRunner": "vitest",
  "mutate": ["src/**/*.ts", "!src/**/*.test.ts"]
}
```

然後執行：

```bash
npx stryker run
```

Stryker 會自動把程式改壞成一堆突變體，逐一丟給測試跑。%( • ̀ω•́ )✧%

<br/>

一跑完，笑容瞬間僵住，四種組合全測過的測試，竟然放跑了一隻突變體：

```text
#1. [Survived] EqualityOperator
src/shipping.ts:9:10
- return order.amount >= threshold ? 0 : base
+ return order.amount > threshold ? 0 : base
```

Stryker 把 `>=` 改成 `>`，測試全都沒反應，突變分數自然也不是滿分。%(⊙ω⊙)%

這個改動只影響一種情況，就是金額「剛好等於門檻」的時候。原本剛好 1000 元的一般會員可以免運，改成 `>` 之後就要多付 60 元，這在電商可是會直接引爆客訴的財損 bug。

<br/>

問題是，我們挑的金額是 1500、800、300，全都離門檻線遠遠的，用 `>=` 還是 `>` 算出來都一樣，測試自然分辨不出差別。

## 它到底在幫你什麼（誠實版）

看到這裡，可能有人要翻白眼了。

<br/>

路人：「這種門檻本來就該測邊界啊，我細心一點不就好了，哪需要什麼突變測試。%(´・ω・`)%」

鱈魚：「你說得對，而且這正是突變測試最常被誤會的地方。%(￣▽￣)%」

<br/>

老實說，突變測試不會幫你抓到「你測不到」的 bug。它改出來的每一隻突變體，事後看都對應著「一個你本來就寫得出來的測試」。這隻存活的突變體也一樣，你只要夠細心，本來就測得到。

所以它真正的價值，從來不是「變出神秘的 bug」，而是底下這兩件事。

<br/>

**第一，它是比覆蓋率誠實的指標。** 覆蓋率只回答「這行有沒有被跑過」，讓你自我感覺良好；突變分數回答的是「這行如果寫錯了，測試攔不攔得住」，這才是測試真正的實力。

**第二，它的戰場是規模。** 你當然不會漏一個運費函數的門檻，但當專案裡有上千個判斷式、或你接手一份看不懂的 legacy 測試時，根本沒辦法用肉眼一條一條確認。突變測試會系統性地幫你把「漏掉的那幾條」標出來，讓你不必再賭自己的細心和運氣。

<br/>

換句話說，它不是取代你的細心，而是驗證你的細心到底有沒有落實，以及在規模底下還撐不撐得住。%(๑•̀ㅂ•́)و✧%

<br/>

認清這點，補起來就簡單了，我們把兩條門檻線都踩一下：

```ts
it('一般會員剛好 1000 免運', () => {
  expect(getShippingFee({ amount: 1000, isVip: false })).toBe(0) // [!code ++]
})

it('VIP 剛好 500 免運', () => {
  expect(getShippingFee({ amount: 500, isVip: true })).toBe(0) // [!code ++]
})
```

再跑一次 Stryker，這隻突變體立刻被殺死，突變分數也跟著補回來。剩下的零星突變體，就照同樣的節奏一隻一隻補起來。%੭ ˙ᗜ˙ )੭%

## 常見的 mutator 對照表

剛剛 Stryker 對 `getShippingFee` 動的那一刀（`>=` 改成 `>`），只是它眾多招式裡的其中一種。

它到底還會怎麼改壞你的程式？這裡整理一張常見的 mutator 對照表，讓大家心裡有個底：

| Mutator | 做什麼 | 範例（原始 → 變異） |
|---------|--------|---------------------|
| ArithmeticOperator | 算術運算子對調 | `a + b` → `a - b`、`a * b` → `a / b` |
| EqualityOperator | 比較運算子對調 | `a < b` → `a <= b`、`a === b` → `a !== b` |
| LogicalOperator | 邏輯運算子對調 | `a && b` → `a \|\| b` |
| BooleanLiteral | 布林值翻轉 | `true` → `false`、`!a` → `a` |
| ConditionalExpression | 條件式強制真假 | `if (a > b)` → `if (true)` 或 `if (false)` |
| StringLiteral | 字串內容抽換 | `'hi'` → `''` |
| UnaryOperator | 一元運算子翻轉 | `-a` → `+a` |
| UpdateOperator | 遞增遞減對調 | `a++` → `a--` |
| BlockStatement | 清空整個程式區塊 | `{ ... }` → `{}` |
| ArrayDeclaration | 清空陣列內容 | `[1, 2, 3]` → `[]` |
| OptionalChaining | 拿掉可選鏈 | `foo?.bar` → `foo.bar` |

招式還真不少對吧？完整清單可以參考 [Stryker 官方文件](https://stryker-mutator.io/docs/mutation-testing-elements/supported-mutators/)。%( •̀ ω •́ )✧%

## 突變一定要殺掉嗎？

前面一直說「存活的突變體代表漏洞」，但這句話其實有例外。

有些突變體，你根本**殺不死**；有些則是**殺了也沒意義**。%( ˘•ω•˘ )%

### 殺不死的：等價突變體

先看一段把庫存正規化的函數，負數一律當作 0：

`normalize.ts`

```ts
export function normalizeStock(count: number): number {
  // 庫存不會是負數，負數一律當作 0
  if (count < 0) {
    return 0
  }
  return count
}
```

我們把正數、0、負數三種情況都測好測滿：

```ts
expect(normalizeStock(5)).toBe(5)
expect(normalizeStock(0)).toBe(0)
expect(normalizeStock(-3)).toBe(0)
```

看起來滴水不漏，但 Stryker 就是有辦法生出一隻活的：

```text
[Survived] EqualityOperator
src/normalize.ts:3:7
- if (count < 0) {
+ if (count <= 0) {
```

它把 `count < 0` 改成 `count <= 0`，唯一有差別的地方，是 `count` 剛好等於 0 的時候。

可是你仔細想想，`count` 是 0 時，原本走 `else` 回傳 `count`（也就是 0），改成 `<=` 之後走 `if` 回傳 `0`，兩邊算出來都是 0，結果一模一樣。%(・∀・)%

<br/>

所以不管丟什麼進去，這兩種寫法的行為**完全相同**。這種「改了程式碼卻沒改行為」的突變體，就叫做「等價突變體」（Equivalent Mutant）。

它本質上不是 bug，任何測試都不可能讓它失敗，你再怎麼補測試都殺不死它。而且要判斷一隻突變體是不是等價的，本身是個無解的難題，工具也幫不了你，只能靠人眼看。%( ´_ゝ`)%

### 殺得死，但不值得殺

另一種情況，是那些「殺得死，但殺了也沒意義」的突變體，最典型的就是 log 訊息：

```ts
export function checkout(order: Order): void {
  logger.info(`結帳開始，訂單編號 ${order.id}`) // Stryker 會把字串改成 ''
  // ...實際結帳邏輯
}
```

Stryker 會把那串 log 改成空字串，然後它就這麼活了下來，因為根本沒有測試在乎 log 印了什麼。

但你真的要為了殺它，特地寫一個「檢查 log 有沒有印出這串字」的測試嗎？這種測試又脆弱又沒營養，訊息改個標點就壞給你看。這種突變體，放它一馬就好。%(ゝ∀・)b%

<br/>

如果這些雜訊看了礙眼，Stryker 也能用 `// Stryker disable next-line all` 註解，或在設定檔排除特定 mutator，直接把它們消音。

<br/>

所以看到存活突變體，先別急著補測試，先問自己兩個問題，這隻殺得死嗎？值得殺嗎？

這也是為什麼突變分數不用硬追求 100%，追到最後，你往往只是在跟一堆等價突變體和 log 訊息鬼打牆。%( ´•̥̥̥ ω •̥̥̥` )%

## 用是很好用，但也別上頭

突變測試雖然強，但它有個明顯的缺點，就是慢，而且是「有感」的慢。

因為它要把程式改壞成幾十、幾百個突變體，每一個都得重跑一次測試，時間自然成倍疊上去。空口無憑，我拿本文的範例實際量了一下（Node 22 + Vitest 3 + Stryker 9，11 條測試程序並行）：

| 規模 | 突變體數量 | 一般測試 | 突變測試 |
|------|-----------|---------|---------|
| 單一函數 | 5 | 約 1.8 秒 | 約 6～7 秒（首次冷啟動要 26 秒）|
| 五個函數 | 58 | 約 4.8 秒 | 約 28 秒 |

光是五個小函數，時間就從 5 秒膨脹到 28 秒，足足六倍，而且純突變執行階段會隨突變體數量幾乎線性成長。真實專案動輒上萬個突變體，跑一輪從幾分鐘到幾小時都有可能。%(°ㅂ°)%

<br/>

所以實務上通常不會拿它跟一般單元測試一樣，每次 commit 都跑全部。

比較常見的做法，是只針對核心邏輯、金流計算這類特別重要的模組使用，或是放在 CI 排程裡定期跑一次就好。

<br/>

抓大放小，把力氣花在真正重要的邏輯上，才是聰明的用法。%(๑•̀ㅂ•́)و✧%

## 總結 🐟

- **覆蓋率會騙人**，它只回答「這行被跑過沒」，不回答「這行寫錯了測試攔不攔得住」。
- **突變測試在測試你的測試**，故意把程式改壞，看測試抓不抓得到，最後給你一個比覆蓋率誠實的「突變分數」。
- 它抓的不是你測不到的 bug，而是像稽核一樣，把你**漏測的死角**系統性地標出來，戰場是規模與 legacy。
- JavaScript / TypeScript 可以用 **Stryker**，搭配 Vitest runner 幾乎無痛上手。
- 突變測試很吃效能，而且存活突變體不一定都要殺（**等價突變體**殺不死、log 訊息不值得殺），鎖定核心邏輯、放進 CI 排程，分數別硬追 100%。
