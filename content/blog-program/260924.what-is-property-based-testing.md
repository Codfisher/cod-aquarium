## 什麼是 Property-Based Testing

平常寫的測試叫做範例測試（Example-Based Testing），自己挑一組輸入、自己算好答案，再比對函式的輸出跟答案一不一樣。

```ts
it('100 元拆成 3 期', () => {
  expect(splitPayment(100, 3)).toEqual([33.34, 33.33, 33.33])
})
```

Property-Based Testing 反過來，不寫答案，只寫「不管輸入是什麼都要成立」的規則，工具會自己產生上百組輸入，想辦法打破這條規則。

```ts
import { fc, test } from '@fast-check/vitest'

// 金額用「分」產生再除以 100，保證最多兩位小數
const totalArbitrary = fc.integer({ min: 0, max: 10_000_000 }).map((cents) => cents / 100)
const countArbitrary = fc.integer({ min: 1, max: 36 })

test.prop([totalArbitrary, countArbitrary])('拆完加回去，不多一分也不少一分', (total, count) => {
  const centsList = splitPayment(total, count).map((value) => Math.round(value * 100))

  expect(centsList.reduce((sum, cents) => sum + cents, 0)).toBe(Math.round(total * 100))
})
```

property 在這裡指數學上的「性質」，例如加法的交換律，所以我習慣叫它**性質測試**，免得跟物件的屬性搞混。

| | 範例測試 | 性質測試 |
|---|---|---|
| 輸入 | 自己挑 | 工具產生，一輪上百組 |
| 期望 | 具體答案 | 一條規則 |
| 失敗時 | 告訴你哪組輸入錯了 | 自動縮成最小的反例 |

這招來自 Haskell 的 QuickCheck，Koen Claessen 與 John Hughes 在 ICFP 2000 發表，十年後拿下這個會議的[最具影響力論文獎](https://sigplan.org/Awards/ICFP/)。

後來各語言都有自己的版本，Python 有 Hypothesis，Java 有 jqwik，JavaScript 與 TypeScript 則是 [fast-check](https://fast-check.dev/)。

## 把上次的退款 bug 丟給它

先安裝 fast-check，搭配 Vitest 的話再加上官方的整合套件。

```bash
npm install -D fast-check @fast-check/vitest
```

::: tip 還在用 Vitest 3？
`@fast-check/vitest` 0.4 之後要求 Vitest 4.1 以上，Vitest 3 請改裝 `@fast-check/vitest@0.3`。
:::

退款邏輯沿用上一篇的 `checkRefund` 與 `submitRefund`，只把金流呼叫拿掉。

測試只寫一條規則，不管客服怎麼退，累計退款都不能超過訂單金額。

```ts
import { fc, test } from '@fast-check/vitest'
import { expect } from 'vitest'
import { createOrder, getRefundedAmount, submitRefund } from './refund'

test.prop([
  fc.integer({ min: 1, max: 100_000 }), // 訂單金額
  fc.array(fc.integer({ min: 1, max: 100_000 })), // 客服依序申請的退款金額
])('不管客服怎麼退，累計退款都不會超過訂單金額', (total, amountList) => {
  const order = createOrder({ total })

  for (const amount of amountList) {
    submitRefund(order, amount)
  }

  expect(getRefundedAmount(order)).toBeLessThanOrEqual(order.total)
})
```

`fc.integer`、`fc.array` 這類產生器叫做 arbitrary，負責描述輸入的範圍。這裡的意思是一筆 1 到 10 萬元的訂單，加上一串 1 到 10 萬元的退款申請，筆數不限。

跑下去，紅了。

```text
Error: Property failed after 2 tests
{ seed: 614164776, path: "1:1:1:4:0:2:0:1:0:2:3:0:0:2:1:0:0:3:0:0:1:0:2:2:2:2:2:2:2:2:2:2:2:2:2:2:2:2:3", endOnFailure: true }
Counterexample: [23558,[1,23558]]
Shrunk 38 time(s)

Caused by: AssertionError: expected 23559 to be less than or equal to 23558
```

才試到第 2 組輸入就抓到了。%Σ(ˊДˋ;)%

`Counterexample` 翻成人話，一筆 23558 元的訂單，先退 1 元，再退 23558 元，總共退了 23559 元。

每一筆單獨看都沒超過訂單金額，加起來就超過了，跟上一篇分三次退 400 元是同一個 bug。

差別在於這次沒有人想到「分次退款」，我只寫了一條規則，情境由機器自己找出來。%( •̀ ω •́ )✧%

### 縮小反例

`Shrunk 38 time(s)` 代表它把反例縮小了 38 次。

fast-check 第一次遇到失敗時，輸入通常亂七八糟。換個 seed（亂數種子）跑，第一次失敗的輸入長這樣。

```text
[99987, [99993, 69478, 74257]]
```

訂單 99987 元，三筆退款申請裡，第一筆超過訂單金額沒有通過，後兩筆加起來才超過，要看懂還得先心算一輪。%(°c＿,°`)%

找到失敗之後，fast-check 會一直嘗試把數字改小、把陣列改短，只要還是失敗就保留，最後縮成這樣。

```text
[74257, [1, 74257]]
```

這個過程叫做 shrinking。只看縮完的結果，一眼就知道問題出在「先退一點，再退全額」。

<br/>

為了確認不是運氣好，我用 1000 個不同的 seed 各跑一輪，每輪照預設試 100 組輸入。

- 1000 輪全部抓到
- 中位數試到第 3 組就失敗，最慢的一輪試到第 21 組
- 995 輪縮成「先退 1 元，再退全額」，另外 5 輪縮成「先退全額，再退 1 元」

不過縮小一次只動一個參數，所以停在 `[74257, [1, 74257]]`。最理想的反例是「1 元的訂單退兩次 1 元」，得同時縮小訂單金額與退款金額，它就到不了。%(´・ω・`)%

## 規則比情境好想

範例測試要你同時想兩件事，**情境**與**答案**。

「訂單 1000 元，分三次退 400 元，第三次要拒絕」，情境是分三次退，答案是第三次拒絕。

性質測試只要你想**規則**，「累計退款不能超過訂單金額」。

一條規則背後可能有上百種情境，bug 往往躲在你沒列出來的那一種。規則的數量少很多，也比較不會隨著需求變動。%(ゝ∀・)b%

<br/>

鱈魚：「好問題，接下來就一條一條質疑它。%(ง •̀_•́)ง%」

## 質疑一：這不就是亂數測試嗎？

自己寫個迴圈跑 `Math.random()`，一樣能丟一堆輸入進去，差別在哪？

差在三件事，而且都量得出來。

### 產生器會偏心

`fc.integer()` 預設的範圍是 -2147483648 到 2147483647，大約 43 億個整數。均勻亂數要剛好抽到 0，機率是 43 億分之一。

我照實際跑測試的設定，用 1000 個 seed 各跑 100 次，收集 10 萬個 `fc.integer()` 產生的值來數。

| 產生的值 | fast-check 實際出現率 | 均勻亂數 |
|---|---|---|
| 剛好是 0 | 0.38% | 43 億分之 1 |
| 絕對值不超過 10 | 7.85% | 約 2 億分之 1 |
| 絕對值不超過 1000 | 23.08% | 約 215 萬分之 1 |
| 離最大值或最小值 10 以內 | 4.05% | 約 2 億分之 1 |

fast-check 刻意偏向 0、小數字與範圍兩端，bug 最常躲在這幾區。%(≖‿ゝ≖)✧%

### 會自己縮小反例

前面看過了，`[99987, [99993, 69478, 74257]]` 會縮成 `[74257, [1, 74257]]`。自己寫的亂數迴圈只會丟給你一坨數字，剩下自己想辦法。

### 失敗可以重播

錯誤訊息裡的 `seed` 與 `path` 可以用來重播，把它們填回測試的參數，就能直接重現同一個反例。

```ts
test.prop([
  fc.integer({ min: 1, max: 100_000 }),
  fc.array(fc.integer({ min: 1, max: 100_000 })),
], {
  seed: 614164776,
  path: '1:1:1:4:0:2:0:1:0:2:3:0:0:2:1:0:0:3:0:0:1:0:2:2:2:2:2:2:2:2:2:2:2:2:2:2:2:2:3',
  endOnFailure: true,
})('重播上次失敗的輸入', (total, amountList) => {
  // ...同上
})
```

實際跑一次，第 1 組輸入就失敗，縮小 0 次，反例一樣是 `[23558,[1,23558]]`。

修好之後，可以把反例放進 `examples`，之後每一輪都會先跑它，再跑隨機輸入。

```ts
test.prop([
  fc.integer({ min: 1, max: 100_000 }),
  fc.array(fc.integer({ min: 1, max: 100_000 })),
], {
  examples: [[23558, [1, 23558]]],
})('不管客服怎麼退，累計退款都不會超過訂單金額', (total, amountList) => {
  // ...同上
})
```

這樣修好的 bug 就不會在哪天悄悄回來。%(ゝ∀・)b%

## 質疑二：輸入每次都不一樣，會不會今天綠明天紅？

會。%(´・ω・`)%

偏心歸偏心，產生器並沒有保證一定會試到哪個值。

我寫了幾個只在特定條件出錯的假 bug，一樣用 1000 個 seed 各跑一輪，看每一輪抓到的機率。

| bug 在什麼時候出現 | 一輪抓到的機率 |
|---|---|
| `x` 剛好是 0 | 31.3% |
| `x` 剛好是最大值 2147483647 | 17.8% |
| `x` 剛好是 123456 | 0% |
| 兩個整數剛好相等 | 10.9% |
| 陣列裡有重複的值 | 33.4% |
| `x` 小於等於 0 | 100% |

第一列最意外。大家都說性質測試會自動測邊界值，可是只在 0 出錯的 bug，每三輪 CI 只有一輪抓得到。%(°ㅂ°)%

123456 這種魔術數字更不用說，1000 輪一次都沒碰過。反過來，只要 bug 涵蓋一整段範圍，例如「小於等於 0 就出錯」，幾乎第一輪就會現形。

<br/>

範圍訂得窄一點，情況會好很多。

| 寫法 | 抓到「剛好是 0」的機率 |
|---|---|
| `fc.integer()` | 31.3% |
| `fc.nat()`，只產生非負整數 | 54.0% |
| `fc.integer({ min: 0, max: 1000 })` | 91.5% |
| `fc.integer()` 跑 1000 次 | 94.3% |

範圍越貼近真實的資料，越容易抽中邊界值，所以產生器不要偷懶，訂單金額就寫訂單金額的範圍。

### 預設值的盲區

預設值更要小心，有些輸入它幾乎不會產生。

| bug 在什麼時候出現 | 一輪抓到的機率 |
|---|---|
| 陣列超過 10 個元素 | 0% |
| 字串含逗號，預設 `fc.string()` | 97.9% |
| 字串含 emoji，預設 `fc.string()` | 0% |
| 字串含 emoji，`unit: 'grapheme'` | 100% |
| 字串含中文，`unit: 'grapheme'` | 2.7% |
| 字串含中文，`unit: 'binary'` | 100% |

fast-check 預設產生的陣列與字串最長 10 個，預設的 `fc.string()` 只有可列印的 ASCII 字元。

`maxLength` 最容易讓人誤會。寫了 `fc.array(fc.integer(), { maxLength: 50 })`，產生的陣列照樣最長 10 個，因為長度還受 `size` 控制，要加上 `size: 'max'` 才會用到 50。不設 `maxLength` 的話，改成 `size: 'medium'` 最長可到 100。

所以分頁這種「超過 20 筆才出錯」的 bug，用預設值跑到天荒地老也抓不到。

字串也一樣，要測 emoji 得指定 `unit`，偏偏 `'grapheme'` 很少產生中文，`'binary'` 則幾乎不產生逗號、反斜線這類符號。最穩的做法是用 `fc.constantFrom` 列出想測的字元，再跟一般的字串產生器混在一起。%(◞‸◟ )%

**產生器產不出來的輸入，性質測試永遠測不到**。它省下你想情境的力氣，輸入長什麼樣子還是得自己想。

### 那到底算不算 flaky？

一般說的 flaky test，指程式沒問題、測試卻亂紅，例如時間差、網路不穩。

性質測試的紅燈不一樣，每一次紅都附上一組真實的反例，重播就能重現，代表程式真的有 bug，只是這一輪才碰到。

實務上可以這樣處理：

- 紅燈的時候，複製錯誤訊息裡的 `seed` 與 `path` 重播
- 修好之後，把反例加進 `examples`，或另外寫成一條範例測試，之後每次都會檢查
- 產生器的範圍貼近真實資料，才容易抽中邊界值
- CI 可以固定 seed 求穩定，代價是永遠只測同樣那 100 組輸入。我比較喜歡讓 seed 隨機，多跑一次就多探索一點

## 質疑三：規則要怎麼想？比寫範例還難吧？

老實說，比較難。%(´ー`)%

Harrison Goldstein 等人在 ICSE 2024 發表的[〈Property-Based Testing in Practice〉](https://harrisongoldste.in/papers/icse24-pbt-in-practice.pdf)，訪談了 Jane Street 的 31 位工程師。30 場訪談裡有 16 場提到寫規格拖慢了進度，有位受訪者講得很直接，最常見的失敗是根本不知道要測什麼性質。

好在前人整理過套路。Scott Wlaschin 在 2014 年寫的[〈Choosing properties for property-based testing〉](https://fsharpforfunandprofit.com/posts/property-based-testing-2/)列了七種，我挑六種，全部套在實驗會用到的函式上。

| 套路 | 意思 | 範例 |
|---|---|---|
| 來回轉換 | 做一次再反做一次，要回到原點 | 標籤編碼再解碼，拿回同一份清單 |
| 不變量 | 轉換前後有東西不會變 | 金額拆完加回去，不多一分也不少一分 |
| 冪等 | 做兩次跟做一次一樣 | 合併過的時段再合併一次，結果不變 |
| 殊途同歸 | 換個順序做，結果一樣 | 時段輸入順序顛倒，合併結果一樣 |
| 對照組 | 拿笨但一定對的方法比對 | 一分鐘一分鐘數，合併前後涵蓋的時間一樣 |
| 難算易驗 | 答案難算，驗證卻很簡單 | 合併結果照順序排好，段與段之間有空檔 |

來回轉換最好寫，核心只有一行。

```ts
test.prop([fc.array(fc.string({ minLength: 1 }))])('編碼再解碼，要拿回一模一樣的清單', (tagList) => {
  expect(decodeTagList(encodeTagList(tagList))).toEqual(tagList)
})
```

對照組則是把「怎麼算」換成「怎麼驗」。合併時段的演算法要排序、要處理包含與相接，驗證卻只要把每一分鐘數出來。

```ts
const timeRangeArbitrary = fc
  .tuple(fc.integer({ min: 0, max: 1440 }), fc.integer({ min: 1, max: 180 }))
  .map(([start, duration]): TimeRange => [start, start + duration])

function toMinuteSet(rangeList: TimeRange[]) {
  const minuteSet = new Set<number>()
  for (const [start, end] of rangeList) {
    for (let minute = start; minute < end; minute++) {
      minuteSet.add(minute)
    }
  }
  return minuteSet
}

test.prop([fc.array(timeRangeArbitrary)])('合併前後涵蓋的分鐘一模一樣', (rangeList) => {
  expect(toMinuteSet(mergeTimeRanges(rangeList))).toEqual(toMinuteSet(rangeList))
})
```

笨方法慢歸慢，笨到不可能寫錯，拿來當標準答案剛剛好。%(ゝ∀・)b%

Goldstein 的訪談也發現，業界最常用這種跟另一份實作比對的性質，30 場訪談裡有 17 場提到，例如拿舊版系統當對照組，驗證重寫的新版。

### 別把實作抄一遍

新手很容易把實作再寫一次，拿來當期望值。

```ts
// 別這樣寫
test.prop([totalArbitrary, countArbitrary])('跟實作算的一樣', (total, count) => {
  const totalCents = Math.round(total * 100)
  const baseCents = Math.floor(totalCents / count)
  const remainderCents = totalCents % count
  const expectedList = Array.from({ length: count }, (_, index) =>
    (index < remainderCents ? baseCents + 1 : baseCents) / 100)

  expect(splitPayment(total, count)).toEqual(expectedList)
})
```

實作怎麼錯，測試就跟著怎麼錯，這條測試永遠都會過。%(´_ゝ`)%

對照組要比實作更笨、更直白，笨到一眼就能確認沒寫錯才有意義。

## 質疑四：AI 一秒寫一百條範例，還需要性質測試嗎？

路人：「現在叫 AI 寫測試，邊界值它比我還會想，範例一口氣生一百條，性質測試還有必要嗎？%(´・ω・`)%」

鱈魚：「我也不知道，所以來做個實驗。%( •̀ ω •́ )✧%」

### 實驗設計

準備四支常見的商業邏輯函式，每支都附 JSDoc 規格與正確實作。

| 函式 | 規格重點 |
|---|---|
| `splitPayment` | 金額拆成多筆，加總不差一分，任兩筆相差不超過 0.01，大的排前面 |
| `truncateText` | 以 Unicode code point 計算字數，emoji 也算一個字，超過就截斷並接上「…」 |
| `mergeTimeRanges` | 合併重疊或相接的時段，不可修改傳入的陣列 |
| `encodeTagList`、`decodeTagList` | 標籤清單與逗號分隔字串互轉，必須完整還原 |

接著請另一個 AI 扮演「之後來改程式的人」，替每支函式寫 4 個常見的錯誤版本，共 16 個。每個錯誤版本都通過 JSDoc 裡的範例，例如：

- 轉換成「分」時把 `Math.round` 寫成 `Math.floor`，`19.99 * 100` 會變成 `1998.9999999999998`，平白少一分
- 用 `.length` 與 `.slice()` 算字數，會把 emoji 切成一半
- 合併時段時忘了取 `Math.max`，包在前一段裡面的時段會把範圍縮小
- 跳脫字元只跳脫逗號，忘了先跳脫反斜線本身

這 16 個版本在任何測試寫出來之前就定案，寫測試的 AI 看不到。

受試者是 6 個各自獨立的 Claude Sonnet 5，3 個只准寫範例測試（E 組），3 個只准寫性質測試（P 組），除了這條限制以外，指示一字不差。它們看得到規格與正確實作，測試必須在正確實作上全綠。

最後比三件事：

- **擋下幾個錯誤版本**：把錯誤版本換進去跑，至少一條測試失敗就算擋下。性質測試每次輸入不同，所以每個版本跑 20 次取平均
- **突變分數**：Stryker 在正確實作上的分數
- **成本**：測試數量與執行時間

開跑前我先把預測寫下來，其中一條是「P 組擋下的錯誤版本比較多」，信心六成。

### 結果：平手

| | E1 | E2 | E3 | P1 | P2 | P3 |
|---|---|---|---|---|---|---|
| 測試數 | 52 | 57 | 51 | 15 | 19 | 16 |
| 擋下的錯誤版本（共 16 個） | 14 | 15 | 15 | 15.95 | 11.2 | 15.95 |
| 突變分數 | 100% | 98.7% | 100% | 98.7% | 87.3% | 98.7% |

15.95 代表 16 個版本裡有 15 個每次都擋下，剩下那個 20 次擋下 19 次。

E 組平均擋下 14.67 個，P 組 14.37 個。照事先訂的規則，差距不超過 1 個版本就算量不出差別，我賭的「P 組擋下比較多」不成立。%(´;ω;`)%

AI 寫的範例測試比我想像的強很多。emoji 切一半、時段互相包含、跳脫字元這些經典邊界，三位 E 組受試者全部都有測。

### 漏掉的地方幾乎不重疊

平手歸平手，兩組漏掉的東西幾乎沒有重疊。

| 錯誤版本 | 誰漏掉 |
|---|---|
| 分帳：`Math.round` 寫成 `Math.floor` | E1、E2 全漏；P1、P3 二十次各漏一次 |
| 分帳：餘數平均散開，破壞「大的排前面」 | E1、E3 |
| 標籤：四個跟跳脫有關的錯誤 | P2 全漏 |
| 時段：相接判斷用 `<` 取代 `<=` | P2 二十次只抓到四次 |

**範例測試漏掉的錯，全都要剛好挑中某些值才會出現。**

`Math.floor` 那個版本，大約 6.56% 的兩位小數金額會出錯，0.29、0.57、1.13、19.99 都會，而且看不出規律。範例測試多半挑 100、0.01、1999.99 這種漂亮的數字，一個都沒踩中。

E1 最好笑。它特地寫了一條測試防浮點數誤差，註解寫著 `29.99 * 100 !== 2999`，可是在 JavaScript 裡 `29.99 * 100` 剛好等於 2999，這條測試對 `Math.floor` 完全無感。%(╯°Д°)╯︵ ┻━┻%

E3 抓到了，也是誤打誤撞。它刻意用 `0.3 / 3` 那條防浮點數，偏偏擋不住，最後靠另一條拿 19.99 測「餘數給第一筆」的案例擋下來。

性質測試一輪試 100 個隨機金額，照機率算幾乎一定會踩到。這個版本 P 組總共跑了 60 次，只漏 2 次。

**性質測試的漏網之魚，幾乎全來自 P2，問題都出在產生器。**

P2 的測試看起來最用心。它在註解說，字串用 `unit: 'binary'` 涵蓋完整 Unicode，逗號、反斜線這類需要跳脫的字元也會驗到；時段起點則用 `fc.integer()` 開到正負 21 億，驗證大數值與負數。

結果這兩個決定都弄巧成拙。

`unit: 'binary'` 從一百多萬個 code point 裡抽字元。我實際產生 10 萬個字串，找不到任何反斜線，含逗號的也只有 1 個；預設只產生 ASCII 的 `fc.string()`，反而各有約 5%。P2 的標籤清單產生器，一輪 100 次裡出現反斜線的機率只有 0.3%，四個跟跳脫有關的錯誤版本當然全漏。

時段也一樣。起點開到正負 21 億，兩段剛好首尾相接的機率趨近於零。我把 P2 那條「段與段之間要有空檔」的性質單獨拿出來，只換值域，各跑 1000 輪：

| 起點範圍 | 抓到相接錯誤的機率 |
|---|---|
| P2 的寫法，正負 21 億 | 6.7% |
| 一天的分鐘數，0 到 1440 | 76.5% |
| 0 到 30 | 100% |

P1 與 P3 剛好相反，兩個都刻意提高逗號與反斜線的出現機率，時段範圍也只有幾十到一百多分鐘，所以都接近滿分。

同樣是性質測試，差別全在產生器。**範圍開越大，特定的值越稀有**，看起來涵蓋更多，實際上測到的更少。%(╬☉д⊙)%

### 各配一份就幾乎全抓

既然漏的地方幾乎不重疊，把 E1 配 P1、E2 配 P2、E3 配 P3，看兩份測試加起來擋下幾個。

| 組合 | 擋下的錯誤版本（共 16 個） |
|---|---|
| E1 加 P1 | 15.95 |
| E2 加 P2 | 16 |
| E3 加 P3 | 16 |

最弱的 P2 配上 E2，一樣拿到滿分。範例測試負責經典邊界，性質測試負責那些要剛好挑中的值。

### 成本

| | E 組 | P 組 |
|---|---|---|
| 測試數 | 51 到 57 | 15 到 19 |
| 測試程式碼（非空白行） | 239 到 352 | 157 到 245 |
| 跑一次 `vitest run`（10 次中位數） | 0.67 到 0.69 秒 | 1.5 到 2.9 秒 |
| 其中純測試時間 | 19 到 23 毫秒 | 0.53 到 1.7 秒 |
| 跑一輪 Stryker | 約 9 秒 | 54 到 75 秒 |

性質測試的程式碼比較少，跑起來比較慢。時間多半花在 `splitPayment`，P 組把筆數開到 500 或 1000，每條性質都要把金額拆成上百筆、重複 100 次。

另外，三位 P 組受試者寫出的 `splitPayment` 性質幾乎一模一樣，就是把 JSDoc 的五條規格逐條翻成五條性質。規格寫成條列時，性質測試幾乎可以照抄。%(´,,•ω•,,)%

### 讀結論前先打折

這個實驗有幾個地方要先講清楚。%(´・ω・`)%

- **樣本很小。** 4 支函式、16 個錯誤版本、每組 3 位受試者，差一兩個版本就會改變結論。
- **錯誤版本由 AI 產生。** 類型偏向 AI 想得到的錯，真實專案的 bug 可能更刁鑽。
- **受試者看得到正確實作。** 範例測試可以直接執行實作拿期望值，E1 與 E2 都這樣做過。
- **受試者都是 Claude Sonnet 5。** 換模型或換人寫，結果可能不同。
- **P3 自己驗證過。** 它寫了四個故意改壞的版本檢查自己的測試，類型跟實驗的錯誤版本有部分重疊，這在指示允許的範圍內，但可能讓 P3 的成績偏高。

完整的設計、預測、每個錯誤版本的程式碼差異與原始數據，都在[實驗報告](https://github.com/Codfisher/cod-aquarium/blob/main/docs/property-based-testing-experiment.md)。

## 突變測試與性質測試差在哪

看過[突變測試](/blog-program/what-is-mutation-testing-and-stryker)那篇的朋友，可能會覺得兩個很像，都是讓工具自動產生一大堆東西來測程式。

兩者改動的對象剛好相反。%(ゝ∀・)b%

- **突變測試**固定測試，改動程式碼，看測試會不會發現程式改壞了
- **性質測試**固定程式碼，改動輸入，看程式在沒想到的輸入下還守不守得住規則

| | 突變測試 | 性質測試 |
|---|---|---|
| 自動產生什麼 | 改壞的程式碼，也就是突變體 | 輸入資料 |
| 回答的問題 | 測試夠不夠嚴 | 程式在沒想到的輸入下對不對 |
| 產出 | 突變分數、存活的突變體 | 縮小過的反例 |
| 身分 | 替測試打分數的工具 | 一種寫測試的方法 |
| 人要想什麼 | 幾乎不用想 | 規則與輸入範圍 |
| 貴在哪 | 突變體數量乘上整套測試的時間 | 每條性質跑上百次 |

兩者不在同一層，所以可以一起用。

### 突變分數 100%，照樣漏掉 bug

回到實驗。E1 的範例測試在 Stryker 拿到 100%，79 個突變體全數擊殺，可是 16 個錯誤版本它漏了 2 個。

打開 Stryker 替 `splitPayment` 產生的 12 個突變體，沒有一個會把 `Math.round` 換成 `Math.floor`。它只會用固定的招式改程式，例如 `*` 換成 `/`、`<` 換成 `<=`、整段清空，招式表裡沒有的錯，分數再高也沒驗到。

E1 另外漏掉「把餘數平均散開」這個版本。這種錯換掉了整套演算法，跟[上一篇](/blog-program/bdd-with-vitest-cucumber)說的「少寫的那一行」一樣，都不在突變測試產生得出來的範圍裡。

性質測試只看結果有沒有守住規則，改一個符號或整支重寫都一樣。

### 存活的突變體，剛好指出產生器的盲點

反過來看 P2，突變分數 87.3%，六組裡最低，10 個存活的突變體分布如下：

- 9 個在 `tag-list` 處理反斜線與逗號的那幾行
- 1 個在 `mergeTimeRanges` 的相接判斷，把 `<=` 改成 `<`，跟錯誤版本 bug2 一模一樣

這正好是 P2 的兩個盲點。它如果寫完測試順手跑一次 Stryker，就會看到跳脫邏輯那幾行全都沒驗到，回頭檢查產生器，發現 `unit: 'binary'` 幾乎不會產生反斜線。

**突變測試幫你檢查性質寫得夠不夠嚴、產生器夠不夠廣；性質測試幫你拿沒想到的輸入檢驗規則。** 兩個剛好各補對方一塊。%( •̀ ω •́ )✧%

## 兩者怎麼配合

### 先避開兩個坑

我第一次拿 Stryker 跑性質測試，分數是 0%。%((((；ﾟДﾟ)))%

測試檔只有兩條 `test.prop`，一條檢查加總，一條檢查相差不超過 0.01。Stryker 產生 12 個突變體，連「整個函式清空」這種必死的突變體都活了下來。

追下去發現是兩個獨立的坑。

**坑一：seed 寫在測試名稱裡。** `@fast-check/vitest` 會把這一輪用的 seed 接在測試名稱後面，沒指定 seed 的話，每次都是新的亂數。

```text
✓ 加總剛好等於總額 (with seed=442508060)
```

Stryker 會先完整跑一次測試，記下每條測試的名稱與它涵蓋的突變體。之後測每個突變體時，它把記下的名稱組成 Vitest 的 `testNamePattern`，只跑相關的測試。

問題是每跑一次，seed 就重抽一次，名稱跟著變，舊名稱一條測試都對不上。Vitest 一條測試都沒跑，沒有失敗，突變體就算存活。報告裡的 `Tests ran` 還會列出那兩條測試，看起來就像真的跑過。

**坑二：Vitest 5 換了名稱的串接符號。** Vitest 5 比對 `testNamePattern` 時，會把 `describe` 與測試名稱用 `>` 串起來，Stryker 10.0.0 還在用空白串接，只要測試包在 `describe` 裡就對不上。這個問題已經有人回報（[stryker-js #6210](https://github.com/stryker-mutator/stryker-js/issues/6210)），修正的 PR 還沒合併。

這個坑跟性質測試無關，純範例測試一樣中招。

我在 Vitest 4.1.11 與 5.0.1 各跑一輪，同一支 `splitPayment`、同樣 12 個突變體。

| 寫法 | Vitest 4.1.11 | Vitest 5.0.1 |
|---|---|---|
| `test.prop`，seed 隨機 | 0% | 0% |
| `test.prop`，固定 seed | 100% | 100% |
| 原生 `it` 包 `fc.assert` | 100% | 100% |
| 名稱固定，但包在 `describe` 裡 | 100% | 0% |

坑一的解法，是替 Stryker 另外準備一份 Vitest 設定，在 setup 檔固定 seed，平常跑測試時 seed 照樣隨機。

```ts
// vitest.stryker.setup.ts
import { fc } from '@fast-check/vitest'

fc.configureGlobal({ seed: 20260924 })
```

接著讓 Stryker 專用的 Vitest 設定載入這支 setup 檔。

```ts
// vitest.stryker.config.ts
import { defineConfig } from 'vitest/config'

export default defineConfig({
  test: {
    include: ['test/**/*.test.ts'],
    setupFiles: ['./vitest.stryker.setup.ts'],
  },
})
```

最後在 Stryker 的設定裡指定這份 Vitest 設定。

```json
// stryker.config.json
{
  "testRunner": "vitest",
  "vitest": { "configFile": "vitest.stryker.config.ts" }
}
```

或者乾脆不用 `test.prop`，改用原生的 `it` 包 `fc.assert`，名稱就固定了。

```ts
import fc from 'fast-check'
import { expect, it } from 'vitest'

it('拆完加回去，不多一分也不少一分', () => {
  fc.assert(fc.property(totalArbitrary, countArbitrary, (total, count) => {
    // ...同前
  }))
})
```

坑二目前只能等 Stryker 修正，或是先留在 Vitest 4。實驗裡的突變分數，就是在 Vitest 4.1.11 加上固定 seed 跑出來的。

兩個坑最麻煩的地方在於它們很安靜。只要專案裡還有其他測試殺得死那些突變體，分數看起來就很合理，很難察覺有一批測試根本沒跑。

看到分數異常低，或是整輪突變測試跑得異常快，先懷疑工具，再懷疑自己。

### 配合的流程

1. **先寫性質。** 規格裡的條列，大多可以直接翻成性質
2. **產生器貼近真實資料，再刻意加重特殊值。** 例如時段用一天的分鐘數，標籤刻意多放逗號與反斜線
3. **用固定 seed 跑 Stryker。** 存活的突變體會告訴你哪條規則太鬆、哪個產生器太窄
4. **關鍵案例寫成範例測試。** 規格裡的範例、踩過的反例、經典邊界，用範例測試釘住，讀的人也最好懂

至於成本，性質測試會讓 Stryker 變慢，因為每個突變體都要把性質重跑上百次。實驗裡 E 組跑一輪 Stryker 約 9 秒，P 組要 54 到 75 秒，慢了六到八倍。跟突變測試那篇的建議一樣，只有核心邏輯值得兩種一起上。

## 別人的研究怎麼說

我的實驗規模很小，所以回頭找了幾篇論文對照。%(´・ω・`)%

**工業界的戰績。** QuickCheck 作者 John Hughes 在 2016 年的[〈Experiences with QuickCheck〉](http://publications.lib.chalmers.se/records/fulltext/232550/local_232550.pdf)整理了幾個案例。替 Volvo 測汽車軟體標準 AUTOSAR 時，他們讀了約 3000 頁規格，寫成 2 萬行的 QuickCheck 模型，測了 6 家供應商共 100 萬行 C 程式碼，找出 200 多個問題，其中超過 100 個是標準本身的模糊或矛盾。

另一個案例是 Klarna 的資料庫，每兩個月就壞一次，工程師花了六週都找不到原因。QuickCheck 測了大約 10 分鐘就抓到，最後發現只要一筆資料加上五、六次 API 呼叫就能重現。

**業界怎麼用。** 前面提過的 Goldstein 等人訪談 Jane Street，受訪者 P9 的一句話很傳神，當抽象很清楚、實作卻很複雜，性質測試最有用。

**一條性質測試抵幾條範例？** Savitha Ravi 與 Michael Coblenz 在 OOPSLA 2025 發表的[〈An Empirical Evaluation of Property-Based Testing in Python〉](https://cseweb.ucsd.edu/~mcoblenz/assets/pdf/OOPSLA_2025_PBT.pdf)，分析了 426 個使用 Hypothesis 的專案，並對其中 40 個跑突變測試，結論是平均每條性質測試抓到的突變，約是一般單元測試的 50 倍。

這個數字要打折看。一條性質測試本來就會跑上百組輸入，逐條比較先天佔便宜；作者自己也說這是相關性研究，關聯強度偏弱。而且這些專案裡 98.4% 的測試仍是單元測試。

同一篇還有個發現，55% 的突變只要一組輸入就抓到，76% 在前 20 組之內。這跟我的實驗對得上，預設 100 次大多夠用，會漏掉通常是因為產生器很少產出那種輸入。

**讓 AI 寫性質測試。** Muhammad Maaz、Nicholas Carlini 等人在 2025 年的[〈Agentic Property-Based Testing〉](https://arxiv.org/abs/2510.09907)（作者多半來自 Anthropic）讓 Claude Code 自己替 100 個熱門 Python 套件寫性質測試，一共產出 984 份 bug 報告。人工抽查之後，56% 確實是 bug，32% 值得回報給維護者，每抓到一個有效 bug 的成本不到 10 美元。其中一個是 NumPy 的 Wald 分布會回傳負數，修正已經合併。

2026 年的 [PBT-Bench](https://arxiv.org/abs/2605.15229) 則專門出難題，植入的 bug 刻意設計成預設產生器幾乎碰不到。AI 得先讀文件找出規則，再寫出能把輸入集中到觸發範圍的產生器，表現最好的模型也只抓到 83.4%。P2 正好栽在這一點上。

| 我的發現 | 研究 | 對照 |
|---|---|---|
| 性質測試能自己找出沒想到的情境 | Klarna 的資料庫 bug，10 分鐘找到六週找不到的原因 | 一致 |
| 規則寫得出來才用得上 | Jane Street 訪談，最常見的失敗是不知道要測什麼 | 一致 |
| 多數 bug 很快就被抓到 | 76% 的突變在前 20 組輸入內抓到 | 一致 |
| 產生器決定抓不抓得到 | PBT-Bench 刻意讓預設產生器碰不到 bug | 一致 |
| 性質測試沒有擋下比較多 | 每條性質測試抓到的突變是單元測試的 50 倍 | 比較單位不同，逐條比與整套比 |

最後一列看似矛盾，其實在量不同的東西。Ravi 與 Coblenz 逐條比，一條性質抵很多條範例；我拿整套測試比，E 組用 50 幾條範例，擋下的數量跟 15 條性質差不多。

## 總結 🐟

AI 一秒寫一百條範例，還需要性質測試嗎？需要，但別期待它單打獨鬥。%(´・ω・`)%

- **性質測試只要你寫規則，情境交給機器找。** 上一篇靠人想到「分三次退」才抓到的 bug，一條規則加上 fast-check，1000 輪全部抓到，還自動縮成「先退 1 元，再退全額」。
- **它只是抽樣，邊界值也不一定抽得到。** 只在 0 出錯的 bug，每三輪只抓到一輪；陣列預設最長 10 個，只把 `maxLength` 設大也沒用；紅燈都是真 bug，綠燈只代表這一輪的輸入沒出事。
- **產生器決定它看得到什麼。** 實驗裡 P2 用 `unit: 'binary'` 想涵蓋所有字元，10 萬個字串裡卻找不到任何反斜線；時段開到正負 21 億，相接的情況幾乎不會發生。範圍要貼近真實資料，特殊值要刻意加重。
- **跟 AI 寫的範例測試互補。** 兩組平均擋下的數量打平，漏掉的地方卻幾乎沒有重疊；範例測試會漏掉要剛好挑中的值，性質測試會漏掉產生器的盲區，各配一份幾乎全抓。
- **突變測試替性質測試健檢。** 突變分數 100% 照樣漏掉浮點數錯誤，性質測試補得上；P2 存活的突變體剛好指出它的盲點。搭配時記得固定 seed，Vitest 5 則要等 Stryker 修正。
