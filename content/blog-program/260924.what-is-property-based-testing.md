路人當時吐槽「是有多少故事」，今天就來講其中一個。%(σﾟ∀ﾟ)σ%

<br/>

回想一下那筆退款比營業額還高的 bug。單元測試、整合測試、突變測試全部綠燈，最後有人想到「客服可能分三次退」，才靠流程測試抓到。

問題是想得到的才寫得出來，bug 偏偏躲在沒想到的地方。%( ´•̥̥̥ ω •̥̥̥` )%

有沒有辦法不列情境，只寫規則，剩下交給機器找反例？

有喔，這就是 Property-Based Testing。%( •̀ ω •́ )✧%

## 什麼是 Property-Based Testing

平常寫的測試叫做範例測試（Example-Based Testing），自己挑輸入、自己算答案，再拿函式輸出跟答案比對。

```ts
it('100 元拆成 3 期', () => {
  expect(splitPayment(100, 3)).toEqual([33.34, 33.33, 33.33])
})
```

Property-Based Testing 反過來，不寫答案，只寫「不管輸入是什麼都要成立」的規則，再由工具產生上百組輸入，想辦法打破規則。

```ts
import { fc, test } from '@fast-check/vitest'

// 金額用「分」產生再除以 100，保證最多兩位小數
const totalArbitrary = fc.integer({ min: 0, max: 10_000_000 }).map((cents) => cents / 100)
const countArbitrary = fc.integer({ min: 1, max: 36 })

test.prop([totalArbitrary, countArbitrary])('拆完加回去，不多一分也不少一分', (total, count) => {
  const centsList = splitPayment(total, count).map((value) => Math.round(value * 100))

  expect(centsList.reduce((sum, cents) => sum + cents, 0)).toBe(Math.round(total * 100))
})
```

property 指數學上的「性質」，例如加法交換律，所以我習慣叫它**性質測試**，免得跟物件屬性搞混。

| | 範例測試 | 性質測試 |
|---|---|---|
| 輸入 | 自己挑 | 工具產生，一輪上百組 |
| 期望 | 具體答案 | 一條規則 |
| 失敗時 | 告訴你哪組輸入錯了 | 縮小過的反例 |

這招源自 Haskell 的 QuickCheck，JavaScript 與 TypeScript 則有 [fast-check](https://fast-check.dev/)。

## 把上次的退款 bug 丟給它

先安裝 fast-check 與官方的 Vitest 整合套件。

```bash
npm install -D fast-check @fast-check/vitest
```

退款邏輯沿用上一篇，測試只寫一條規則，不管客服怎麼退，累計退款都不能超過訂單金額。

```ts
import { fc, test } from '@fast-check/vitest'
import { expect } from 'vitest'
import { createOrder, getRefundedAmount, submitRefund } from './refund'

test.prop([
  fc.integer({ min: 1, max: 100_000 }), // 訂單金額
  fc.array(fc.integer({ min: 1, max: 100_000 })), // 客服依序申請的退款金額
])('不管客服怎麼退，累計退款都不會超過訂單金額', (total, amountList) => {
  const order = createOrder({ total })

  for (const amount of amountList) {
    submitRefund(order, amount)
  }

  expect(getRefundedAmount(order)).toBeLessThanOrEqual(order.total)
})
```

`fc.integer`、`fc.array` 這類產生器叫做 arbitrary，負責描述輸入範圍。這裡代表一筆 1 到 10 萬元的訂單，加上一串 1 到 10 萬元的退款申請，筆數不限。

跑下去，紅了。

```text
Error: Property failed after 2 tests
{ seed: 614164776, path: "1:1:1:4:0:2:0:1:0:2:3:0:0:2:1:0:0:3:0:0:1:0:2:2:2:2:2:2:2:2:2:2:2:2:2:2:2:2:3", endOnFailure: true }
Counterexample: [23558,[1,23558]]
Shrunk 38 time(s)

Caused by: AssertionError: expected 23559 to be less than or equal to 23558
```

才試到第 2 組輸入就抓到了。%Σ(ˊДˋ;)%

`Counterexample` 翻成人話，23558 元的訂單先退 1 元、再退 23558 元，總共退了 23559 元。每一筆單獨檢查都沒超過，加起來就超過，跟上一篇分三次退 400 元是同一個 bug。

這次沒有人想到「分次退款」，我只寫了一條規則，情境由機器自己找出來。%( •̀ ω •́ )✧%

<br/>

`Shrunk 38 time(s)` 代表反例縮小了 38 次。換個 seed（亂數種子）跑，第一次失敗的輸入長這樣。

```text
[99987, [99993, 69478, 74257]]
```

要看懂還得先心算一輪。%(°c＿,°`)%

fast-check 會持續把數字改小、陣列改短，只要還是失敗就保留，最後縮成 `[74257, [1, 74257]]`，一眼就看出問題在「先退一點，再退全額」。這個過程叫做 shrinking。

為了確認不是運氣好，我換 1000 個 seed 各跑一輪，1000 輪全部抓到，中位數試到第 3 組就失敗。

路人：「說得那麼好聽，還不是丟亂數進去？%(´・ω・`)%」

鱈魚：「好問題，接下來就一條一條質疑它。%(ง •̀_•́)ง%」

## 質疑一：這不就是亂數測試嗎？

跟自己寫迴圈跑 `Math.random()` 比，差在兩件事。

第一，取值不平均。`fc.integer()` 預設範圍約 43 億個整數，我收集 10 萬個產生的值來數：

| 產生的值 | fast-check 實際出現率 | 均勻亂數 |
|---|---|---|
| 剛好是 0 | 0.38% | 43 億分之 1 |
| 絕對值不超過 10 | 7.85% | 約 2 億分之 1 |
| 離最大值或最小值 10 以內 | 4.05% | 約 2 億分之 1 |

fast-check 刻意偏向 0、小數字與範圍兩端，bug 最常躲在這幾區。%(≖‿ゝ≖)✧%

第二，反例可以縮小、重播。錯誤訊息附上 `seed` 與 `path`，填回測試參數就能重現同一組反例。修好之後把反例放進 `examples` 參數，之後每一輪都會先跑它，bug 就不會悄悄回來。

## 質疑二：輸入每次都不一樣，會不會今天綠明天紅？

會。%(´・ω・`)%

取值再怎麼偏向邊界，產生器也不保證一定試到哪個值。我寫了幾個只在特定條件出錯的假 bug，用 1000 個 seed 各跑一輪：

| bug 在什麼時候出現 | 一輪抓到的機率 |
|---|---|
| `x` 剛好是 0 | 31.3% |
| `x` 剛好是最大值 2147483647 | 17.8% |
| `x` 剛好是 123456 | 0% |
| 兩個整數剛好相等 | 10.9% |
| `x` 小於等於 0 | 100% |

只在 0 出錯的 bug，每三輪 CI 只抓到一輪；bug 只要涵蓋一整段範圍，例如「小於等於 0」，幾乎第一輪就現形。

範圍訂窄一點，情況好很多：

| 寫法 | 抓到「剛好是 0」的機率 |
|---|---|
| `fc.integer()` | 31.3% |
| `fc.nat()`，只產生非負整數 | 54.0% |
| `fc.integer({ min: 0, max: 1000 })` | 91.5% |

預設值也有盲區。fast-check 預設產生的陣列與字串最長 10 個，`fc.string()` 只產生可列印的 ASCII 字元，所以「超過 20 筆才出錯」的分頁、含 emoji 的字串，用預設值永遠測不到。要測特定字元，就用 `fc.constantFrom` 列出來，再跟一般的字串產生器混用。

**產生器產不出來的輸入，性質測試永遠測不到。** 它省下想情境的力氣，輸入長什麼樣子還是得自己想。

那算不算 flaky test？flaky 指程式沒問題、測試卻亂紅。性質測試每次紅燈都附上能重播的反例，代表程式真的有 bug，只是這一輪才碰到。

## 質疑三：規則要怎麼想？比寫範例還難吧？

老實說，比較難。%(´ー`)%

Harrison Goldstein 等人在 ICSE 2024 發表的[〈Property-Based Testing in Practice〉](https://harrisongoldste.in/papers/icse24-pbt-in-practice.pdf)訪談了 Jane Street 的工程師，30 場訪談裡有 16 場提到寫規格拖慢進度，很多人卡在根本不知道要測什麼性質。

好在前人整理過套路。Scott Wlaschin 的[〈Choosing properties for property-based testing〉](https://fsharpforfunandprofit.com/posts/property-based-testing-2/)列了七種，我挑六種，套在實驗會用到的函式上。

| 套路 | 意思 | 範例 |
|---|---|---|
| 來回轉換 | 轉過去再轉回來，要回到原點 | 標籤編碼再解碼，拿回同一份清單 |
| 不變量 | 轉換前後有東西不會變 | 金額拆完加回去，不多一分也不少一分 |
| 冪等 | 執行兩次跟執行一次一樣 | 合併過的時段再合併一次，結果不變 |
| 殊途同歸 | 換個順序執行，結果一樣 | 時段輸入順序顛倒，合併結果一樣 |
| 對照組 | 拿笨但一定對的方法比對 | 一分鐘一分鐘數，合併前後涵蓋的時間一樣 |
| 難算易驗 | 答案難算，驗證卻很簡單 | 合併結果照順序排好，段與段之間有空檔 |

來回轉換最好寫，核心只有一行。

```ts
test.prop([fc.array(fc.string({ minLength: 1 }))])('編碼再解碼，要拿回一模一樣的清單', (tagList) => {
  expect(decodeTagList(encodeTagList(tagList))).toEqual(tagList)
})
```

千萬別把實作再寫一次當期望值。實作怎麼錯，測試就跟著錯，永遠都會過。%(´_ゝ`)%

## 質疑四：AI 一秒寫一百條範例，還需要性質測試嗎？

路人：「現在叫 AI 寫測試，邊界值它比我還會想，範例一口氣生一百條，性質測試還有必要嗎？%(´・ω・`)%」

鱈魚：「我也不知道，所以來做個實驗。%( •̀ ω •́ )✧%」

### 實驗設計

準備四支常見的商業邏輯函式，每支都附 JSDoc 規格與正確實作：

| 函式 | 規格重點 |
|---|---|
| `splitPayment` | 金額拆成多筆，加總不差一分，任兩筆相差不超過 0.01，大的排前面 |
| `truncateText` | 以 Unicode code point 計算字數，emoji 也算一個字，超過就截斷並接上「…」 |
| `mergeTimeRanges` | 合併重疊或相接的時段，不可修改傳入的陣列 |
| `encodeTagList`、`decodeTagList` | 標籤清單與逗號分隔字串互轉，必須完整還原 |

再請另一個 AI 替每支函式寫 4 個常見的錯誤版本，共 16 個，每個都通過 JSDoc 裡的範例，例如：

- 換算成「分」時把 `Math.round` 寫成 `Math.floor`，`19.99 * 100` 會變成 `1998.9999999999998`，平白少一分
- 用 `.length` 算字數，會把 emoji 切成一半
- 合併時段忘了取 `Math.max`，前一段包住後一段時範圍會縮小
- 跳脫字元只處理逗號，忘了先跳脫反斜線

這 16 個版本在測試寫好之前就定案，寫測試的 AI 看不到。

接著找 6 個各自獨立的 Claude Sonnet 5 寫測試，以下稱為受試者，分成兩組，每組 3 位：

- **範例組**：只准寫範例測試
- **性質組**：只准寫性質測試

其餘指示一字不差。受試者看得到規格與正確實作，測試必須在正確實作上全綠。

最後把錯誤版本換進去跑，至少一條測試失敗就算擋下。性質測試每次輸入不同，所以每個版本跑 20 次取平均。

### 結果：兩組打平，漏的地方不同

| | 範例組 | 性質組 |
|---|---|---|
| 每位寫的測試數 | 51 到 57 | 15 到 19 |
| 三位各擋下幾個錯誤版本（共 16 個） | 14、15、15 | 15.95、15.95、11.2 |
| 平均 | 14.67 | 14.37 |

15.95 代表 15 個版本每次都擋下，剩下那個 20 次擋下 19 次。

開跑前我賭性質組會擋下比較多，結果差距不到 1 個版本，賭輸了。%(´;ω;`)%

AI 寫的範例測試比想像中強，emoji 切一半、時段互相包含、跳脫字元這些經典邊界，範例組三位全都有測。

可是逐一比對漏掉的版本，兩組幾乎沒有重疊：

| 錯誤版本 | 誰漏掉 |
|---|---|
| `Math.round` 寫成 `Math.floor` | 範例組三位漏掉兩位；性質組有兩位二十次各漏一次 |
| 餘數平均散開，破壞「大的排前面」 | 範例組三位漏掉兩位 |
| 四個跟跳脫有關的錯誤 | 性質組一位全漏 |
| 時段相接判斷用 `<` 取代 `<=` | 性質組同一位，二十次只抓到四次 |

**範例測試漏掉的，都要剛好挑中某些值才會出錯。**

`Math.floor` 版本大約 6.56% 的兩位小數金額會出錯，0.29、0.57、19.99 都會，看不出規律。範例測試多半挑 100、0.01、1999.99 這種漂亮數字，一個都沒踩中。

範例組有一位還特地寫了一條測試防浮點數誤差，註解寫著 `29.99 * 100 !== 2999`，偏偏在 JavaScript 裡 `29.99 * 100` 剛好等於 2999。%(╯°Д°)╯︵ ┻━┻%

唯一擋下的那位，也只是剛好拿 19.99 測別的規格。性質組一輪試 100 個隨機金額，三位幾乎每次都抓到。

**性質測試漏掉的，問題都出在產生器。**

漏掉的版本幾乎都來自只擋下 11.2 個的那位，它把範圍開得特別大：

- 字串用 `unit: 'binary'`，想涵蓋完整 Unicode，結果從一百多萬個 code point 裡抽，10 萬個字串找不到任何反斜線，四個跳脫錯誤全漏
- 時段起點開到正負 21 億，兩段剛好首尾相接的機率趨近於零

把它的時段性質單獨拿出來，只換起點範圍，各跑 1000 輪：

| 起點範圍 | 抓到相接錯誤的機率 |
|---|---|
| 原本的寫法，正負 21 億 | 6.7% |
| 一天的分鐘數，0 到 1440 | 76.5% |
| 0 到 30 | 100% |

**範圍開越大，特定的值越稀有**，看起來涵蓋更多，實際上測到更少。%(╬☉д⊙)%

另外兩位刻意多放逗號與反斜線，時段範圍只開到一百多分鐘，都接近滿分。

<br/>

把三份範例測試與三份性質測試兩兩配對，每一對加起來擋下 15.95、16、16 個。連範圍開最大的那位，配上範例測試也拿到滿分。

成本方面，性質組的測試程式碼約少三成，跑一次 `vitest run` 則從 0.7 秒變成 1.5 到 2.9 秒。

### 實驗的限制

- **樣本很小**：4 支函式、16 個錯誤版本、每組 3 位，差一兩個版本就會改變結論
- **錯誤版本由 AI 產生**：真實專案的 bug 可能更刁鑽
- **受試者都是 Claude Sonnet 5，且看得到正確實作**：換模型或換人寫，結果可能不同
- **性質組有一位自己寫了改壞的版本驗證測試**：成績可能偏高

完整數據都在[實驗報告](https://github.com/Codfisher/cod-aquarium/blob/main/docs/property-based-testing-experiment.md)。

## 所以性質測試到底有沒有用？

有用，只是用處跟我原本想的不一樣。

它擋下的 bug 沒有比較多，真正的價值在於擋下另一類，也就是範例挑不到的值，以及沒人想到的情境。

### 它擋得下範例測試擋不下的

不管人還是 AI，挑範例時都會挑漂亮的數字與教科書上的邊界。bug 只要藏在看不出規律的值裡，挑不到就是挑不到，範例再多寫一百條也一樣。

[突變測試](/blog-program/what-is-mutation-testing-and-stryker)也幫不上忙。那位防浮點數誤差卻防錯的受試者，突變分數 100%，照樣漏掉 `Math.floor`。Stryker 只會用固定的幾種招式改程式，例如 `*` 換成 `/`、`<` 換成 `<=`，這一招不在裡面。性質測試只檢查結果，程式不管怎麼改壞，只要違反規則就抓得到。

情境也是。開頭的退款 bug 靠人想到「分三次退」才抓到，性質測試只要一條規則。

QuickCheck 作者 John Hughes 在[〈Experiences with QuickCheck〉](http://publications.lib.chalmers.se/records/fulltext/232550/local_232550.pdf)提過更誇張的例子。Klarna 的資料庫每兩個月壞一次，工程師查了六週查不出原因，QuickCheck 測了約 10 分鐘就抓到。

### 它的極限在產生器

範圍開最大的那位寫了 19 條測試，四個跳脫錯誤一個都沒擋下，原因只有產生器太廣。

Ravi 與 Coblenz 在 OOPSLA 2025 發表的[研究](https://cseweb.ucsd.edu/~mcoblenz/assets/pdf/OOPSLA_2025_PBT.pdf)分析了 426 個使用 Hypothesis 的專案，55% 的突變第一組輸入就抓到，76% 在前 20 組之內。預設 100 次大多夠用，會漏掉通常因為產生器很少產出那種輸入。

::: tip 那「一條性質測試抵 50 條單元測試」呢？
大家常引用這篇論文的另一個數字，平均每條性質測試抓到的突變約是單元測試的 50 倍。這是逐條比較，一條性質本來就跑上百組輸入，跟我拿整套測試比的結果並不衝突。
:::

### 什麼時候該寫

質疑三提過，寫性質測試最難的地方在於想規則。實驗裡剛好相反，性質組三位寫出的 `splitPayment` 性質幾乎一模一樣，都是把 JSDoc 的五條規格逐條轉成性質。規格能條列，性質測試幾乎可以照抄。

| 情況 | 建議 |
|---|---|
| 規格能條列成規則，例如加總不變、編碼再解碼要還原 | 寫性質測試 |
| bug 可能藏在特定值，例如浮點數、Unicode、區間相接 | 寫性質測試，範圍貼近真實資料，特殊字元刻意多放 |
| 規格裡的範例、踩過的反例 | 寫範例測試，或放進 `examples` |
| 講不出規則，只有幾組固定對應 | 範例測試就夠了 |

核心邏輯兩種都寫，代價是每次跑測試多一到兩秒。

## 產生器夠不夠好，跑一次突變測試就知道

產生器窄不窄，光看程式碼很難判斷。範圍開最大的那位，註解寫得頭頭是道，產生器卻幾乎不產生反斜線。

它的突變分數 87.3%，六位裡最低。10 個存活的突變體有 9 個在標籤的跳脫邏輯、1 個在時段的相接判斷，剛好對上兩個盲點。寫完測試順手跑一次 Stryker，就會發現跳脫邏輯沒驗到，回頭就能找出產生器的問題。

代價是 Stryker 從約 9 秒變成 54 到 75 秒，因為每個突變體都要重跑上百次性質，所以只有核心邏輯值得兩種一起上。

::: warning 用 Stryker 跑性質測試要固定 seed
`@fast-check/vitest` 會把 seed 接在測試名稱後面，Stryker 靠名稱挑測試，seed 每次重抽就對不上，分數直接變成 0%，而且不會報錯。替 Stryker 另外準備一份 Vitest 設定，在 setup 檔呼叫 `fc.configureGlobal({ seed: 20260924 })` 即可。

Stryker 10.0.0 搭配 Vitest 5 時，包在 `describe` 裡的測試也會對不上（[stryker-js #6210](https://github.com/stryker-mutator/stryker-js/issues/6210)），修正前建議先留在 Vitest 4。
:::
