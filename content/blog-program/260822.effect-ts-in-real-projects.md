# Effect 接進真實專案是什麼感覺？Vue、NestJS、oRPC 通通試一遍 ( •̀ ω •́ )✧

大家好，我是鱈魚。%( ´ ▽ ` )ﾉ%

這篇是上下兩篇的**下篇**。

上篇[來認識 Effect](/blog-program/getting-to-know-effect-ts)講完了核心概念，用一句話複習就是，Effect 把「會怎麼失敗」跟「需要什麼」寫進 `Effect<A, E, R>` 的型別裡，而且後兩欄由編譯器自己算。

沒看過上篇的話建議先去看，這篇會直接用 `yield*`、`Layer` 這些詞，也會一直提到 `Effect<A, E, R>` 那三欄。

先複習一下那三欄各自代表什麼，免得後面看得霧煞煞。

| 欄位 | 意思 |
|---|---|
| `A` | 成功會拿到什麼 |
| `E` | 可能會怎麼失敗 |
| `R` | 需要哪些服務才跑得起來 |

<br/>

概念講完，接下來是真正會踩到的問題。

- 接進 Vue 元件是什麼感覺？值不值得？
- `@effect/platform` 跟 NestJS 差在哪？效能呢？
- 已經在用 oRPC 的話，兩者會不會打架？
- 從零開始寫一支 API，到底要多少行？

一個一個來。%( •̀ ω •́ )✧%

## Vue 要怎麼接

聊完後端邏輯，換個場景，Effect 寫的服務要怎麼接進 Vue 元件？

<br/>

先講 npm 上的現況，因為這件事最近剛翻盤。%(´,,•ω•,,)%

Effect v4 把響應式綁定收進核心，`@effect/atom-vue` 成了**官方套件**，跟 React、Solid 並列三個官方支援的前端框架。

不過有個現實問題，`@effect/atom-vue` **只支援 v4**，而 v4 目前還在 RC。

現在 `npm install effect` 裝到的是 v3，v3 時代的 Vue 綁定是 Effect 核心成員 tim-smart 個人維護的 [`@effect-atom/atom-vue`](https://github.com/tim-smart/effect-atom)。

<br/>

路人：「所以到底能不能用？%(´・ω・`)%」

鱈魚：「能，但你會是很前面的那批白老鼠。%(´_ゝ`)%」

<br/>

考量到版本還沒穩定，接下來還是示範怎麼自己接，反正就三十行，順便也看得懂官方套件在做什麼。

<br/>

第一步準備一個 app 層級的 runtime，把 Layer 組合起來，變成可重複使用的執行環境。

```ts
// runtime.ts
import { Layer, ManagedRuntime } from 'effect'
import { Database, EmailService } from './register-user'

const AppLayer = Layer.mergeAll(
  Database.Default,
  EmailService.Default,
)

export const appRuntime = ManagedRuntime.make(AppLayer)
```

<br/>

再包一層 composable，把 Effect 的執行結果接回 Vue 的 `ref`。

```ts
// useRegisterUser.ts
import { Effect, Fiber } from 'effect'
import { onUnmounted, ref } from 'vue'
import { registerUser, type User } from './register-user'
import { appRuntime } from './runtime'

export function useRegisterUser() {
  const user = ref<User | null>(null)
  const error = ref<unknown>(null)
  const loading = ref(false)

  let fiber: Fiber.RuntimeFiber<User, unknown> | undefined

  function submit(target: User) {
    loading.value = true
    error.value = null

    fiber = appRuntime.runFork(
      registerUser(target).pipe(
        Effect.tap((result) => Effect.sync(() => (user.value = result))),
        Effect.tapError((cause) => Effect.sync(() => (error.value = cause))),
        Effect.ensuring(Effect.sync(() => (loading.value = false))),
      ),
    )
  }

  onUnmounted(() => {
    if (fiber) {
      Effect.runFork(Fiber.interrupt(fiber))
    }
  })

  return { user, error, loading, submit }
}
```

還記得前面說 Effect 寫好了也不會跑嗎？`runFork` 就是把描述交出去執行的那一刻。

它不等結果，馬上回傳一個 `Fiber`，元件卸載時呼叫 `Fiber.interrupt` 就能中斷，跟原生用 `AbortController` 取消 `fetch` 是同一件事，只是換了個名字。

<br/>

路人：「一定要用 `ManagedRuntime` 嗎？直接 `Effect.runPromise` 不行嗎？%(´・ω・`)%」

鱈魚：「單次呼叫用 `Effect.runPromise` 完全沒問題，只是每次都要重新 provide 一次 Layer，跟全 app 共用一個 runtime 比起來浪費資源，服務也沒辦法重複使用。%( •̀ ω •́ )%」

<br/>

元件測試或 Storybook 想塞一顆假的 `EmailService`，就別直接 import 那個單例 runtime，改用 `provide`/`inject` 傳下去。

```ts
// runtime-provider.ts
import type { ManagedRuntime } from 'effect'
import type { Database, EmailService } from './register-user'
import { inject, type InjectionKey, provide } from 'vue'

type AppRuntime = ManagedRuntime.ManagedRuntime<Database | EmailService, never>

const runtimeKey: InjectionKey<AppRuntime> = Symbol('effect-runtime')

export function provideRuntime(runtime: AppRuntime) {
  provide(runtimeKey, runtime)
}

export function useRuntime() {
  const runtime = inject(runtimeKey)
  if (!runtime) {
    throw new Error('找不到 runtime，記得先 provideRuntime')
  }
  return runtime
}
```

測試時在最外層塞一顆帶測試 Layer 的 runtime，底下所有 composable 拿到的就是測試版本，元件本身完全不用改，跟後端替換 Layer 是同一套心智模型。%(´,,•ω•,,)%

### 那前端到底該不該用？

教完怎麼接，還是得講一下該不該接。

先講我的看法，**多數 Vue 專案不值得**。%(´_ゝ`)%

<br/>

上面那個 composable 就是證據，三十行的膠水，做的事情 `useMutation` 大概三行就交代完了。

原因有這幾個。

**一、`R`（依賴服務）在前端沒什麼用武之地**

`Effect<A, E, R>` 的第三欄，記錄這段程式需要哪些服務才跑得起來。它最大的價值是測試時可以換掉那些服務，但前端測元件通常不從服務那層換。

主流做法是拿 [MSW](https://mswjs.io/) 在**網路那層**攔截，元件、composable、`fetch` 全部照原樣跑，攔的是 HTTP 請求本身。

這種測法更接近使用者的真實路徑，也不用為了好測而改生產程式碼的架構。Layer 替換的優勢，在這裡幾乎用不上。%( ˘•ω•˘ )%

**二、`E`（可能錯誤）到了畫面上會被壓扁**

第二欄，記錄這段程式可能失敗的所有原因。

後端區分 `UserNotFound` 跟 `NetworkError` 很有意義，因為要回不同的 status code。

前端呢？多數情況就三種反應，顯示錯誤訊息、重試、當作沒發生。

八種錯誤型別到了 UI 層常常被壓成同一個 `catch`，那份精細度就浪費了。

**三、該有的輪子早就有人造好了**

Effect 的 `retry`、`timeout`、Fiber 中斷聽起來很威，但這些正是 [TanStack Query](https://tanstack.com/query)、[Pinia Colada](https://pinia-colada.esm.dev/) 這類套件的本業。

而且它們還多做了 Effect 不管的事，快取、失效重取、視窗聚焦重新整理、devtools。

拿 Effect 從頭刻這些，其實是降級。

**四、bundle size 是真的成本**

後端多幾百 KB 沒人在意，前端每一 KB 都要使用者用流量跟載入時間去付。

官方的 [Myths 頁面](https://www.effect.website/docs/v3/additional-resources/myths)有一條就叫「The bundle size is HUGE!」，可見這個質疑常被提出。官方的回應是這樣。

> Effect 的最低成本大約是 25k 的 gzipped 程式碼，那個 chunk 包含 Effect Runtime，而且已經涵蓋一般 app 會用到的幾乎所有函數。
>
> 從那之後 Effect 對 tree-shaking 很友善，你只會打包到自己用到的部分。

這個說法有它的道理，關鍵字是 **tree-shaking**。25KB 是「起跳價」，不是整包的大小。

不過那個數字沒有附上量測方法，而且它比較的基準是「你也寫了同樣功能的程式碼」。官方另外提到採用 Effect 後自己的程式碼會變短，總成本被攤平，這點就得看專案實際情況了。%( ˘•ω•˘ )%

<br/>

務實的建議是別直接相信任何一方的數字，接上 bundle 分析工具實際量一次。

後端完全不用煩惱這件事，這一條是前端獨有的成本。

**五、官方綁定還沒進穩定版**

前面提過，`@effect/atom-vue` 只支援還在 RC 的 v4，文件頁也幾乎是空的。

自己接的話，那個 composable 沒有人幫你維護，Vue 改版、Effect 改版都是你自己的事。

<br/>

路人：「所以你剛剛教那一大段是白教的？%(´・ω・`)%」

鱈魚：「還是有值得用的時候，只是我想來想去只想到一種。%( ˘•ω•˘ )%」

<br/>

**那就是前端真的有很複雜的非同步流程。**

多步驟上傳佇列要重試跟退避、即時協作要處理競態、離線同步要對帳，這種場景拿 `AbortController` 配一堆 flag 硬拼會很痛苦，Fiber 的中斷模型確實舒服很多。

<br/>

不過老實說，這種情況比大家想像的少。

大部分畫面就是「拿資料、顯示、送出表單」，這種需求用不到 Effect 三成的能力，卻要付出全部的學習成本。%( ˘•ω•˘ )%

## `@effect/platform` 不只是 HTTP

Vue 那段是把服務接到畫面上，換個方向，`registerUser` 要變成一支 HTTP API 呢？

Effect 生態圈負責這塊的是 `@effect/platform`。

<br/>

不過先澄清一個常見誤解，很多人把它當成「Effect 版的 Express」，它真正的定位是**跨平台的系統能力抽象層**。

HTTP 只是其中一個模組，同一包裡面還有這些。

| 模組 | 管什麼 |
|---|---|
| `HttpApi`、`HttpServer`、`HttpClient` | REST API、發請求 |
| `Socket` | WebSocket 與 TCP socket |
| `FileSystem`、`Path` | 檔案讀寫、路徑處理 |
| `Command` | 開子行程、串接 stdin/stdout |
| `Worker` | Web Worker 與 `worker_threads` |
| `Terminal` | CLI 的終端機輸入輸出 |
| `KeyValueStore` | 鍵值儲存，可換成記憶體、檔案或其他後端 |

這些模組只定義**介面**，真正的實作放在各平台的套件裡。

```bash
npm install effect @effect/platform @effect/platform-node
```

<br/>

以 `Worker` 為例，同一份丟工作給背景執行緒的程式碼，在 Node 由 `@effect/platform-node` 接到 `worker_threads`，在瀏覽器由 `@effect/platform-browser` 接到 Web Worker，換的是最外層那顆 Layer。

看出來了嗎？這就是 `R`（依賴服務）那一欄的老把戲，只是這次被抽換的是**執行環境本身**。%( •̀ ω •́ )✧%

<br/>

::: tip 不是每個模組每個平台都有實作
`FileSystem` 跟 `Command` 這種東西，瀏覽器根本沒有對應的能力，自然就沒有 browser 版。

`@effect/platform-browser` 提供的是 `BrowserKeyValueStore`（背後是 localStorage）、`BrowserSocket`、`BrowserWorker` 這些瀏覽器真的做得到的事。

所以「跨平台」指的是**介面一致**，不是每個平台都通吃。
:::

<br/>

回到 HTTP，核心是 `HttpApi`。

<br/>

第一步先宣告這支 API 長什麼樣，`api.ts`

```ts
import { HttpApi, HttpApiEndpoint, HttpApiGroup } from '@effect/platform'
import { Schema } from 'effect'

export const UserSchema = Schema.Struct({
  id: Schema.String,
  name: Schema.String,
})

export class EmailSendFailed extends Schema.TaggedError<EmailSendFailed>()('EmailSendFailed', {
  email: Schema.String,
}) {}

export const UsersApi = HttpApi.make('UsersApi').add(
  HttpApiGroup.make('users').add(
    HttpApiEndpoint.post('register', '/users')
      .setPayload(UserSchema)
      .addSuccess(UserSchema)
      .addError(EmailSendFailed, { status: 502 }),
  ),
)
```

這個檔案沒有任何實作，純粹描述「收什麼、回什麼、可能出什麼錯」。

錯誤型別從 `Data.TaggedError` 換成 `Schema.TaggedError`，因為它要轉成 JSON 送給前端，得有 schema 才知道怎麼轉。

<br/>

第二步接上實作，`api-live.ts`

```ts
import { HttpApiBuilder } from '@effect/platform'
import { Layer } from 'effect'
import { UsersApi } from './api'
import { registerUser } from './register-user'

const UsersLive = HttpApiBuilder.group(UsersApi, 'users', (handlers) =>
  handlers.handle('register', ({ payload }) => registerUser(payload)))

export const ApiLive = HttpApiBuilder.api(UsersApi).pipe(
  Layer.provide(UsersLive),
)
```

請看 handler 那行，`registerUser(payload)` 直接回傳，**`registerUser` 一個字都沒改**。

也請注意這裡**沒有** provide 任何服務，`ApiLive` 到現在還缺著 `Database` 跟 `EmailService`，那份清單原封不動掛在型別上。

<br/>

第三步才把真的服務填進去，順便跑起來，`server.ts`

```ts
import { createServer } from 'node:http'
import { HttpApiBuilder, HttpApiSwagger } from '@effect/platform'
import { NodeHttpServer, NodeRuntime } from '@effect/platform-node'
import { Layer } from 'effect'
import { ApiLive } from './api-live'
import { Database, EmailService } from './register-user'

const ServerLive = HttpApiBuilder.serve().pipe(
  Layer.provide(HttpApiSwagger.layer()),
  Layer.provide(ApiLive),
  Layer.provide(Database.Default),
  Layer.provide(EmailService.Default),
  Layer.provide(NodeHttpServer.layer(createServer, { port: 3000 })),
)

Layer.launch(ServerLive).pipe(NodeRuntime.runMain)
```

`npx tsx server.ts` 跑下去，`POST /users` 就活了，打開 `/docs` 還有一份 Swagger 在等你。

那份文件不用另外寫，從 `api.ts` 的 `Schema` 長出來，同一份定義還能再產一支型別安全的前端 client。%( •̀ ω •́ )✧%

宣告、實作、組裝剛好三個檔案，一路上沒有裝飾器，也沒有「框架偷偷幫你做了什麼」的環節。

「什麼時候把依賴填進去」一路推到最外面那層，等一下講測試會再回來咬一口。%(´,,•ω•,,)%

### 換 NestJS 寫一次

同一支 API 用 NestJS 寫，大概長這樣。

```ts
// users.controller.ts
@Controller('users')
export class UsersController {
  constructor(
    private readonly database: Database,
    private readonly emailService: EmailService,
  ) {}

  @Post()
  async register(@Body() dto: RegisterUserDto) {
    await this.database.save(dto)
    await this.emailService.sendWelcomeEmail(dto.email)
    return dto
  }
}
```

```ts
// users.module.ts
@Module({
  controllers: [UsersController],
  providers: [Database, EmailService],
})
export class UsersModule {}
```

平心而論，NestJS 這段寫得很舒服，建構子把依賴列得清清楚楚，比前面那個直接 import 單例的版本好太多。%(´,,•ω•,,)%

<br/>

路人：「那不就一樣？依賴也是攤在明面上啊。%(・∀・)%」

鱈魚：「差在**保護範圍**跟**什麼時候發現**。%( ˘•ω•˘ )%」

<br/>

建構子注入只在 class 裡成立，`registerUser` 這種普通函數一旦搬出 controller，依賴又躲回 import 裡了。Effect 沒有這個限制，那份清單跟著 `Effect` 型別走，是函數是 class 都一樣。

至於什麼時候發現，`UsersModule` 的 `providers` 少填一個，TypeScript 完全不會有意見，因為那只是一個陣列，得等啟動時 Nest 組裝容器才會噴 `can't resolve dependencies`。

Effect 版本少 provide 一顆 Layer，紅的是編譯器。%(°ㅂ°)%

### 測試的時候差更多

回到前面那個問題，測這支 API 要怎麼換掉 `EmailService`？

NestJS 有一套測試專用的模組 API，得把模組重新宣告一次，再指定要蓋掉誰。

```ts
const moduleRef = await Test.createTestingModule({
  controllers: [UsersController],
  providers: [Database, EmailService],
})
  .overrideProvider(EmailService)
  .useValue({ sendWelcomeEmail: vi.fn() })
  .compile()

const controller = moduleRef.get(UsersController)
```

Effect 這邊沒有「測試專用 API」這種東西。

還記得剛剛把依賴推到最外層嗎？正式環境在 `server.ts` 填真的，測試就填假的，如此而已。

```ts
Layer.provide(EmailService.Default) // [!code --]
Layer.provide(EmailServiceTest) // [!code ++]
```

`api.ts`、`api-live.ts`、`registerUser` 三個檔案完全不用動，因為它們從頭到尾就沒決定過要用哪個實作。%(ゝ∀・)b%

<br/>

整理成表格比較好認。

| 比較項目 | NestJS | Effect Platform |
|---------|--------|------------------|
| 依賴注入 | 建構子加裝飾器，執行期組裝容器 | `Context`/`Layer`，清單寫在型別的 `R` 那一欄 |
| 漏了依賴 | 啟動時噴 `can't resolve dependencies` | 編譯器直接紅 |
| 保護範圍 | 只有 class 有 | 函數、class、endpoint 都一樣 |
| 資料驗證 | class-validator 寫 DTO | `Schema`，順便長出文件跟 client |
| 中介層 | `@UseGuards`、Interceptor，另一套機制 | `HttpApiMiddleware`，跟一般服務同一套 Layer |
| 測試替換 | `Test.createTestingModule().overrideProvider()` | `Effect.provide`，跟測普通函數同一招 |

<br/>

### 那效能呢？

路人：「講這麼多，跑起來到底快不快？%(・∀・)%」

鱈魚：「先講結論，這大概不是你該煩惱的事，不過數字還是值得看。%(´_ゝ`)%」

<br/>

資料來源是 [SaltyAom 的 HTTP 框架 benchmark](https://github.com/SaltyAom/bun-http-framework-benchmark)，目前唯一同時收錄 Effect 跟 NestJS 的公開測試。

**看數字之前，先講三個一定要知道的前提。**%( ˘•ω•˘ )%

- 表中的 Effect 是 **v4 beta 的 `effect/unstable/http`**，跟你現在 `npm install @effect/platform` 裝到的 v3 是兩套程式碼。v3 那條線沒有任何公開效能數據
- Effect 那組**關掉了 tracing 跟 request logging**，兩者都是框架預設開啟的。照預設寫的服務不會有這個表現
- NestJS 跑**預設的 Express adapter**，官方文件說換成 Fastify adapter 可以快將近一倍，那個組合沒人測過

所以底下的數字只能當**方向參考**，不能當結論。

底下只列 Node 的數字，Bun 那組跳過，畢竟多數人的正式環境還是跑 Node。

#### 一、吞吐量

| 框架 | 平均 req/s |
|---|---:|
| Fastify | 97,934 |
| Hono | 91,090 |
| **Effect** | **58,684** |
| Express | 42,226 |
| NestJS | 31,271 |

Effect 大約是 NestJS 的 1.9 倍、Express 的 1.4 倍，但只有 Fastify 的六成。

這張表能證明的只有一件事，**Effect 的 HTTP 層沒有大家想像中那麼肥**。%(´,,•ω•,,)%

#### 二、延遲

先講壞消息，**P99 這類百分位數字沒有**。

那份 benchmark 用 bombardier 壓測，而百分位要加 `-l` 參數才會輸出，他們沒加。想要 p99 就得自己 clone 下來重跑。%(´_ゝ`)%

<br/>

不過延遲資料本身是有的，只是不在 README 那張表上。

repo 裡有 commit 原始的壓測輸出（`results/node/*.txt`），bombardier 預設就會印**平均、標準差、最大值**這三項，下面的數字都是從那些檔案挖出來的。

標準差跟最大值其實更好玩，因為它們反映的正是**尾端延遲穩不穩**，跟 P99 想回答的是同一個問題。

以 `GET /` 這條路由、500 連線跑十秒來看。

| 框架 | 平均延遲 | 標準差 | 最大延遲 |
|---|---:|---:|---:|
| Fastify | 3.33 ms | 5.93 ms | 777 ms |
| **Effect** | **5.49 ms** | **15.04 ms** | **1.44 s** |
| Express | 7.68 ms | 23.55 ms | 1.90 s |
| NestJS | 10.32 ms | 42.07 ms | 3.20 s |

看最後兩欄，排序跟平均延遲一致，但差距被放大了。

NestJS 平均 10ms 看起來還好，標準差卻是 42ms、最壞情況 3.2 秒。這代表**有一小撮倒楣的請求等了非常久**，而那些人剛好就是 P99 會抓出來的族群。%(°ㅂ°)%

Effect 的尾端比 Express 跟 NestJS 收斂，但離 Fastify 還有一段距離。

所以只看平均延遲會少看很多東西，那幾個等到天荒地老的使用者，全都藏在後面兩欄裡。%( ˘•ω•˘ )%

#### 三、冷啟動與基準記憶體

| 框架 | 啟動時間 | 啟動後 RSS | Bundle |
|---|---:|---:|---:|
| Hono | 45.2 ms | 95.7 MB | 61.2 KB |
| Express | 50.2 ms | 86.6 MB | 603.6 KB |
| Fastify | 67.2 ms | 98.4 MB | 554.7 KB |
| **Effect** | **80.9 ms** | **90.7 MB** | 357.6 KB |
| NestJS | 110.3 ms | 119.0 MB | 1.3 MB |

啟動時間量的是「行程 spawn 到第一個請求成功回應」，Effect 比 NestJS 快約 27%，但輸給 Express 跟 Hono。

基準記憶體大家其實差不多，NestJS 的 119MB 稍微突出，bundle 也是唯一破 1MB 的。

<br/>

要注意的是**這不等於 serverless 冷啟動**。Lambda、Workers 那種環境還有 INIT、快照還原一整套流程，含 Effect 的冷啟動實測我完全找不到。

如果你要部署到 Cloudflare Workers，倒是有個數字要留意，`effect` 本身壓縮後約 293KB、`@effect/platform` 約 1.49MB（未 tree-shaking 的上限值），而 Workers 免費方案的限制是 1MB。%( ˘•ω•˘ )%

#### 四、高負載後的資源釋放

這欄我覺得最有意思。同一份表格記錄了壓測前後的 RSS 變化。

| 框架 | 壓測前 | 壓測後 | 成長 |
|---|---:|---:|---:|
| **Effect** | 90.7 MB | 114.6 MB | **+23.9 MB（+26%）** |
| Fastify | 98.4 MB | 162.3 MB | +63.9 MB（+65%） |
| NestJS | 119.0 MB | 224.8 MB | +105.8 MB（+89%） |
| Hono | 95.7 MB | 217.1 MB | +121.4 MB（+127%） |
| Express | 86.6 MB | 223.8 MB | +137.2 MB（+158%） |

Effect 的記憶體成長是 Express 的六分之一、NestJS 的四分之一。

而且它的吞吐量還比這兩個高，照理說配置率應該更高才對，結果反而長最少。%(⊙ロ⊙)%

<br/>

路人：「是 Effect 的 Scope 在做資源回收嗎？%(・∀・)%」

鱈魚：「我一開始也這樣猜，但查完文件發現不能這樣講。%( ˘•ω•˘ )%」

<br/>

`Scope` 保證的是檔案、連線這類**明確取得的資源**會被確實釋放，但這份 benchmark 的路由根本沒開這些東西，機制等於沒出場。

所以合理的講法是，**Effect 在這次評測的設定下記憶體成長明顯較低，但別急著歸功給哪個機制**。%(´,,•ω•,,)%

<br/>

順帶一提，Effect 從來沒進過 [TechEmpower](https://www.techempower.com/benchmarks/) 那套主流框架 benchmark，NestJS 有。想找更權威的對照，目前找不到。

### 但這真的是你的瓶頸嗎

講完數字，還是要把話說回來。

Pydantic 團隊寫過一篇[實測文章](https://pydantic.dev/articles/web-framework-performance)，結論是「**框架本身很少會是瓶頸**」。他們把整個請求拆開看，資料庫查詢跟序列化吃掉絕大多數時間，框架路由只佔中間那幾條細縫。

那篇講的是 Python，但道理跨語言通用。

<br/>

Effect 官方的 [Myths 頁面](https://www.effect.website/docs/v3/additional-resources/myths)也很坦白。

> 前端有跑到 120fps 還重度使用 Effect 的應用，所以 Effect 大概不會是你的效能問題。

一支 API 只要碰了資料庫，那幾毫秒的 IO 就足以淹沒框架層的差距。

真的在意每秒幾萬個請求，該問的是「要不要用 Bun」跟「資料庫查詢有沒有寫爛」，而不是「該用哪個框架」。%(ゝ∀・)b%

## 那 oRPC 呢？

看過[前一篇 oRPC 的文章](/blog-ocean-world/orpc-vs-ts-rest)的朋友可能會想，這兩個是不是打架？

答案是不會，而且**合約優先的人有一條特別順的路**。%(ﾉ>ω<)ﾉ%

### 把 oRPC 掛在 Effect 的 HTTP server 上

關鍵在於契約優先本來就把**契約**跟**HTTP 傳輸**拆開了。

契約是一份獨立的東西，放在私有 npm 或 monorepo 裡，前後端各自拿去對照。

```ts
// @project-code/shared
export const todoContract = {
  create: oc.input(/* ... */).output(/* ... */),
}
```

後端用 `implement(todoContract)` 實作，前端用 `ContractRouterClient` 推型別。至於這些東西**用什麼跑起來**，是另一件事。

所以可以讓 oRPC 出契約跟路由，HTTP server 交給 Effect。%( •̀ ω •́ )✧%

<br/>

橋接方式意外地簡單，因為兩邊剛好在同一個介面上會合。

- oRPC 的 fetch adapter 是 `(Request) => Promise<Response>`
- `@effect/platform` 有個 `HttpApp.fromWebHandler`，收的正好就是這種函數

```ts
const orpcApp = HttpApp.fromWebHandler(async (request) => {
  const result = await rpcHandler.handle(request, { prefix: '/rpc', context: {} })
  return result.matched ? result.response : new Response('Not Found', { status: 404 })
})

const app = HttpRouter.empty.pipe(
  HttpRouter.get('/health', HttpServerResponse.text('ok')),
  HttpRouter.mountApp('/rpc', orpcApp, { includePrefix: true }),
)
```

契約優先全程保留，`oc` 定契約、`implement` 實作、前端照樣 `ContractRouterClient`，連 event iterator 串流都能正常穿透。

<br/>

**最棒的是這條路全部用穩定版就能跑。**

```bash
npm install @orpc/server @orpc/contract effect @effect/platform @effect/platform-node
```

`@orpc/server` 對 `effect` 零依賴，所以裝起來完全沒有 peer 衝突。%(´,,•ω•,,)%

::: warning `includePrefix` 一定要設 `true`
預設的 `false` 會改寫請求 URL 來剝除前綴，但 `toWeb` 有個 fast-path 會直接回傳原始 request。

在 Node 上剛好沒事，在 Bun、Deno、Workers 上那個改寫會被無聲忽略，oRPC 會收到沒剝除前綴的路徑。
:::

<br/>

不過動手之前先想清楚**你到底想換到什麼**。

| | 內容 |
|---|---|
| 拿得到 | 單一 port、Effect 的 logger／CORS／OTel 包住 RPC、Layer 生命週期與優雅關機 |
| 拿不到 | procedure 內部仍是普通 async function，沒有型別化的錯誤，也沒有服務清單 |

想在 handler 裡跑 Effect，還是得 `ManagedRuntime.runPromise`，而那一步會把型別化錯誤打回 rejected promise。

所以這條路只買到**傳輸層**的 Effect。%( ˘•ω•˘ )%

<br/>

務實的建議是這樣。

- oRPC 是你唯一的 HTTP 出口 → 用 `@orpc/server/node` 配 `ManagedRuntime` 更單純，找到的唯一一個真實 oRPC + Effect 專案就是這樣做
- 已經有其他 Effect 路由、想統一成同一個 server → 橋接才划算

<br/>

順帶一提，`@effect/platform` 不只是 HTTP，`FileSystem`、`Command`、`Worker` 那些模組跟 HTTP 無關，走這條路的話也一起拿到了。%(´,,•ω•,,)%

### 補充：oRPC v2 的官方 Effect 整合

上面那條路的 procedure 還是普通 async function。想讓型別化錯誤跟服務清單進到業務邏輯裡，oRPC v2 有**官方的 Effect 整合**。

```ts
os.create.handler(async ({ input }) => { // [!code --]
  await database.save(input) // [!code --]
}) // [!code --]
os.create.handler(handlerGen(function* ({ input }) { // [!code ++]
  const database = yield* Database // [!code ++]
  yield* database.save(input) // [!code ++]
})) // [!code ++]
```

`handlerGen` 會把執行跟錯誤處理包好，不用自己呼叫 `Effect.runPromise`。服務則走 oRPC 的 context，塞一個 `effect/context` 進去。

<br/>

好消息是**契約完全不用動**。

`handlerGen` 的型別裡沒有 schema 的位置，它對契約的要求只有「符合 Standard Schema」，Zod 本來就符合。所以整份 Zod 契約一行都不用改寫成 Effect Schema。%( •̀ ω •́ )✧%

::: danger 這條路現在全線都是 beta
以 **2026 年 8 月 21 日**的狀態為準。

| 套件 | 穩定版 | 這條路要用的版本 |
|---|---|---|
| `effect` | 3.22.1 | **4.0.0-beta**（v4 已進 RC） |
| `@orpc/server`、`@orpc/contract` | 1.15.0 | **2.0.0-beta.29** |
| `@orpc/experimental-effect` | 無穩定版 | **2.0.0-beta.29** |

Effect 跟 oRPC 都得押在 beta 上，套件名還掛著 `experimental`。side project 玩玩沒問題，正式產品建議等兩邊都出正式版。

還有三個坑：npm 的 `latest` 標籤指到誤發布的舊版，一定要加 `@beta`；三個 oRPC 套件版號必須完全一致，否則 npm 會裝出巢狀的第二份 `@orpc/server`，讓 prototype 擴充打到錯的 class，執行期噴 `os.xxx.effect is not a function`；最後，它的 peer 寫死 Effect v4 beta，跟 `@effect/platform` 裝不進同一棵樹，**等於放棄前面那個橋接**。
:::

### 那 `HttpApi` 什麼時候才輪得到

其實你早就看過 `HttpApi` 的合約優先了，就是前面那兩個檔案，`api.ts` 只有宣告，`api-live.ts` 才是實作。

概念跟 oRPC 一模一樣，差別在合約的**形狀**跟**流通範圍**。

| | oRPC 合約 | `HttpApi` |
|---|---|---|
| 合約長相 | 函式簽章（input、output、errors） | HTTP 端點（method、path、schema） |
| 驗證庫 | 任何 Standard Schema，Zod 直接可用 | 只吃 Effect `Schema` |
| 前端要不要碰 Effect | 完全不用 | 產 client 就會拉進 Effect |
| 前端查詢整合 | TanStack Query、Pinia Colada、SWR | 沒有 |
| 部署目標 | 二十幾種，含 Hono、Next、SvelteKit、Cloudflare | Node、Bun、Deno、瀏覽器 |

判斷標準不是「哪個比較好」，而是看**合約要給誰看**。

合約要跨團隊、前端不想碰 Effect，就留在 oRPC。整個後端都是 Effect、前端也吃得下，`HttpApi` 才有登場的理由。

<br/>

要注意的是，**已經用 Zod 寫好的合約沒辦法搬去 `HttpApi`**。

`HttpApiEndpoint` 的 `setPayload` 型別上只收 `Schema.Schema.Any`，而 Effect Schema 的識別靠一個 `unique symbol`，Zod 結構上無法冒充。轉換也只有 Effect Schema → Standard Schema 這個方向，反過來沒有。

所以那不是「改個 import 就好」，是整份重寫。%( ˘•ω•˘ )%

<br/>

補充一下，Effect 圈內還有個 `@effect/rpc`，走 RPC 形狀而非 REST 形狀，定位比較接近 oRPC，同一份 `Schema` 可以共用，不過它還在 0.x，暫時不用急著看。

## 動手做一個最小的 todo server

講了一整篇，最後把東西湊起來，做一支真的跑得動的 todo API。

不用登入、資料用 [Drizzle](https://orm.drizzle.team/) 存進 PostgreSQL，而且照 feature 拆好資料夾。

```text
src/
├── todos/
│   ├── todo.table.ts      # Drizzle 的資料表定義
│   ├── todo.api.ts        # 這個 feature 的 endpoint 宣告
│   ├── todo.store.ts      # 服務與 Layer
│   └── todo.handlers.ts   # handler 實作
├── api.ts                 # 把各 feature 的宣告併起來
└── server.ts              # 組裝所有 Layer 並啟動
```

熟悉 NestJS 的話，`todo.api.ts` 大致等於 controller 的路由表、`todo.store.ts` 等於 provider、`api.ts` 等於 `AppModule`。%(´,,•ω•,,)%

::: tip 為什麼檔名用點號分隔
`實體.型別.ts` 這種寫法源自 Angular Style Guide，NestJS 沿用至今。

有趣的是 Angular 自己在 v20 已經不這樣產生檔案了，理由是他們認為 `Service` 這類後綴沒有傳達實質資訊，`UserDataClient` 比 `UserService` 有用得多，細節可以看[那份 RFC 討論](https://github.com/angular/angular/discussions/58412)。不過這個寫法在後端圈還是很通行。

選它有兩個實際理由。

- **模糊搜尋好用**，在編輯器打 `todo tab` 就能直達資料表定義，這也是 Angular 當年列的理由之一
- **glob 抓得精準**，Drizzle 的 `schema: './src/**/*.table.ts'` 不會誤中 `lookup-table.ts` 這種檔案，換成連字號的 `*-table.ts` 就會

不喜歡點號的話，換成 `todo-table.ts` 或 feature 資料夾內用裸名 `table.ts` 都行，只要整個專案一致就好。
:::

### 一、資料表長什麼樣

`todos/todo.table.ts` 就是一般的 Drizzle 寫法，跟 Effect 沒有關係。

```ts
import { boolean, pgTable, serial, text } from 'drizzle-orm/pg-core'

export const todoTable = pgTable('todos', {
  id: serial('id').primaryKey(),
  title: text('title').notNull(),
  done: boolean('done').notNull().default(false),
})
```

建表就照 Drizzle 的常規流程，`npx drizzle-kit push` 或跑 migration 都行。

### 二、宣告這個 feature 的 API

`todos/todo.api.ts` 只描述形狀，沒有任何實作。

```ts
import { HttpApiEndpoint, HttpApiGroup } from '@effect/platform'
import { Schema } from 'effect'

export const Todo = Schema.Struct({
  id: Schema.Number,
  title: Schema.String,
  done: Schema.Boolean,
})

export type Todo = typeof Todo.Type

export class DatabaseError extends Schema.TaggedError<DatabaseError>()('DatabaseError', {
  message: Schema.String,
}) {}

export const TodoGroup = HttpApiGroup.make('todos')
  .add(
    HttpApiEndpoint.get('list', '/todos')
      .addSuccess(Schema.Array(Todo))
      .addError(DatabaseError, { status: 500 }),
  )
  .add(
    HttpApiEndpoint.post('create', '/todos')
      .setPayload(Schema.Struct({ title: Schema.String }))
      .addSuccess(Todo)
      .addError(DatabaseError, { status: 500 }),
  )
```

錯誤型別用 `Schema.TaggedError` 而不是 `Data.TaggedError`，理由跟前面一樣，它要轉成 JSON 送給前端。

而且**每個 endpoint 都要用 `.addError` 掛上去**，沒掛的話 handler 回傳這個錯誤會編譯失敗，因為 endpoint 宣告的錯誤通道裡根本沒有它。%( ˘•ω•˘ )%

### 三、服務與說明書

`todos/todo.store.ts` 分成兩半，名牌跟說明書。

```ts
import { drizzle } from 'drizzle-orm/node-postgres'
import { Context, Effect, Layer } from 'effect'
import { DatabaseError, type Todo } from './todo.api'
import { todoTable } from './todo.table'

// 名牌，只講有哪些能力
export class TodoStore extends Context.Tag('TodoStore')<TodoStore, {
  readonly list: Effect.Effect<ReadonlyArray<Todo>, DatabaseError>;
  readonly create: (title: string) => Effect.Effect<Todo, DatabaseError>;
}>() {}

// 說明書，連線字串由外面決定
export const TodoStorePostgres = (connectionUri: string) =>
  Layer.sync(TodoStore, () => {
    const db = drizzle(connectionUri)

    return {
      list: Effect.tryPromise({
        try: () => db.select().from(todoTable),
        catch: (cause) => new DatabaseError({ message: String(cause) }),
      }),
      create: (title: string) =>
        Effect.tryPromise({
          try: () => db.insert(todoTable).values({ title, done: false }).returning(),
          catch: (cause) => new DatabaseError({ message: String(cause) }),
        }).pipe(Effect.map((rowList) => rowList[0]!)),
    }
  })
```

這裡用 `Context.Tag` 而不是 `Effect.Service`，因為連線字串要由外面給。

`TodoStorePostgres` 是一台生產說明書的機器，餵不同的連線字串會吐出不同的 Layer，等一下測試就靠這件事。%( •̀ ω •́ )✧%

### 四、把宣告併起來

`api.ts` 就是 `AppModule` 的角色。

```ts
import { HttpApi } from '@effect/platform'
import { TodoGroup } from './todos/todo.api'

export const Api = HttpApi.make('Api').add(TodoGroup)
```

以後多一個 feature 就多一行 `.add(UserGroup)`。

### 五、實作 handler

`todos/todo.handlers.ts` 才碰到真正的邏輯。

```ts
import { HttpApiBuilder } from '@effect/platform'
import { Effect } from 'effect'
import { Api } from '../api'
import { TodoStore } from './todo.store'

export const TodoLive = HttpApiBuilder.group(Api, 'todos', (handlers) =>
  handlers
    .handle('list', () =>
      Effect.gen(function* () {
        const store = yield* TodoStore
        return yield* store.list
      }))
    .handle('create', ({ payload }) =>
      Effect.gen(function* () {
        const store = yield* TodoStore
        return yield* store.create(payload.title)
      })))
```

注意第一個參數收的是**整份 `Api`**，不是單一個 group，所以這個檔案要回頭 import 根目錄的 `api.ts`。

也就是說 feature 資料夾沒辦法像 NestJS 的 module 那樣完全自給自足。好在宣告跟實作是分開的檔案，依賴方向是 `todo.api` → `api` → `todo.handlers`，不會繞成循環。%( ˘•ω•˘ )%

### 六、組裝並啟動

`server.ts` 是唯一決定「用哪個實作」的地方。

```ts
import { createServer } from 'node:http'
import { HttpApiBuilder, HttpApiSwagger } from '@effect/platform'
import { NodeHttpServer, NodeRuntime } from '@effect/platform-node'
import { Layer } from 'effect'
import { Api } from './api'
import { TodoLive } from './todos/todo.handlers'
import { TodoStorePostgres } from './todos/todo.store'

const ServerLive = HttpApiBuilder.serve().pipe(
  Layer.provide(HttpApiSwagger.layer()),
  Layer.provide(HttpApiBuilder.api(Api).pipe(Layer.provide(TodoLive))),
  Layer.provide(TodoStorePostgres(process.env.DATABASE_URL!)),
  Layer.provide(NodeHttpServer.layer(createServer, { port: 3000 })),
)

Layer.launch(ServerLive).pipe(NodeRuntime.runMain)
```

跑起來。

```bash
DATABASE_URL=postgres://... npx tsx src/server.ts
```

```bash
curl -X POST localhost:3000/todos -H 'content-type: application/json' -d '{"title":"買鱈魚"}'
# {"id":1,"title":"買鱈魚","done":false}

curl localhost:3000/todos
# [{"id":1,"title":"買鱈魚","done":false}]
```

打開 `localhost:3000/docs` 還有一份 Swagger。%( •̀ ω •́ )✧%

<br/>

加起來一百行左右，但你已經拿到這些東西。

- 請求跟回應都經過 `Schema` 驗證，型別錯了直接擋在門口
- Swagger 文件自動生成，沒有另外寫
- 資料庫錯誤掛在 `E`（可能錯誤）那一欄，呼叫端看型別就知道會噴 `DatabaseError`
- 換資料庫只要改 `server.ts` 那一行，其他檔案動都不用動

<br/>

路人：「用 Express 寫可能更短欸。%(・∀・)%」

鱈魚：「對，但那一百行裡面有一半是型別跟文件在幫你做事。%( ˘•ω•˘ )%」

## 測試接上真的 PostgreSQL

`TodoStore` 現在寫進 PostgreSQL，測試就不能靠假物件混過去了。

拿假的 client 來 mock 意義不大，因為 SQL 有沒有寫對它驗不出來。比較實在的做法是用 [Testcontainers](https://node.testcontainers.org/) 開一個真的資料庫。

<br/>

先把容器包成服務，`test/pg-container.ts`

```ts
import { PostgreSqlContainer } from '@testcontainers/postgresql'
import { Effect } from 'effect'

export class PgContainer extends Effect.Service<PgContainer>()('PgContainer', {
  scoped: Effect.acquireRelease(
    Effect.promise(() => new PostgreSqlContainer('postgres:17-alpine').start()),
    (container) => Effect.promise(() => container.stop()),
  ),
}) {}
```

`Effect.acquireRelease` 收兩個東西，怎麼開跟怎麼關。只要宣告一次，之後不管測試成功、失敗還是被中斷，容器都保證會關掉。%( •̀ ω •́ )✧%

<br/>

接著把連線字串餵給**正式環境那份** `TodoStorePostgres`。

```ts
const TodoStoreTest = Layer.unwrapEffect(
  Effect.gen(function* () {
    const container = yield* PgContainer
    return TodoStorePostgres(container.getConnectionUri())
  }),
).pipe(Layer.provide(PgContainer.Default))
```

前面那台「生產說明書的機器」在這裡派上用場了。測到的是真的 SQL，不是假的替身。

<br/>

測試本體，`test/todo.test.ts`

```ts
import { expect, layer } from '@effect/vitest'
import { Effect } from 'effect'

layer(TodoStoreTest, { timeout: '60 seconds' })('TodoStore', (it) => {
  it.effect('新增之後應該查得到', () =>
    Effect.gen(function* () {
      const store = yield* TodoStore

      const created = yield* store.create('買鱈魚')
      const todoList = yield* store.list

      expect(created.title).toBe('買鱈魚')
      expect(todoList).toHaveLength(1)
    }))
})
```

用 `layer(...)` 包起來，容器**整個區塊只開一次**，區塊結束才關，裡面每個 `it.effect` 共用同一個資料庫。

如果改成在每條測試各自 `Effect.provide(TodoStoreTest)`，那就會每跑一條就開關一次容器，慢到懷疑人生。%(´_ゝ`)%

::: tip 這段的版本
`@effect/vitest@0.30`（peer 是 `effect ^3.22`）搭 `@testcontainers/postgresql@12`，後者要求 Node 22.22 以上。

另外 Effect v4 把 `it.scoped` 拿掉了，`it.effect` 自帶 `Scope`，升級時要注意。
:::

## 同一支 API 換 NestJS 寫

有了對照才知道差在哪，同樣的功能用 NestJS 寫大概是這樣。

```text
src/
├── todos/
│   ├── dto/create-todo.dto.ts
│   ├── todo.controller.ts
│   ├── todo.service.ts
│   └── todo.module.ts
├── app.module.ts
└── main.ts
```

資料夾切法幾乎一樣，差別在 NestJS 多了一個 `todo.module.ts` 把整包收起來。

<br/>

先是資料驗證，NestJS 這邊靠 class-validator。

```ts
// todos/dto/create-todo.dto.ts
import { IsString } from 'class-validator'

export class CreateTodoDto {
  @IsString()
  title: string
}
```

接著是服務。

```ts
// todos/todo.service.ts
@Injectable()
export class TodoService {
  constructor(@Inject(DATABASE) private readonly db: Database) {}

  list() {
    return this.db.select().from(todoTable)
  }

  create(title: string) {
    return this.db.insert(todoTable).values({ title, done: false }).returning()
  }
}
```

再來是 controller 跟 module。

```ts
// todos/todo.controller.ts
@Controller('todos')
export class TodoController {
  constructor(private readonly todoService: TodoService) {}

  @Get()
  list() {
    return this.todoService.list()
  }

  @Post()
  create(@Body() dto: CreateTodoDto) {
    return this.todoService.create(dto.title)
  }
}
```

```ts
// todos/todo.module.ts
@Module({
  controllers: [TodoController],
  providers: [TodoService],
})
export class TodoModule {}
```

老實說 NestJS 這版讀起來相當舒服，裝飾器把路由跟依賴標得清清楚楚，行數也差不多。%(´,,•ω•,,)%

### NestJS 這邊怎麼測

同樣接真的 PostgreSQL。

```ts
describe('TodoService', () => {
  let container: StartedPostgreSqlContainer
  let app: INestApplication

  beforeAll(async () => {
    container = await new PostgreSqlContainer('postgres:17-alpine').start()
    const db = createDatabase(container.getConnectionUri())

    const moduleRef = await Test.createTestingModule({ imports: [AppModule] })
      .overrideProvider(DATABASE)
      .useValue(db)
      .compile()

    app = moduleRef.createNestApplication()
    await app.init()
  }, 180_000)

  afterAll(async () => {
    await app?.close()
    await container?.stop()
  })

  it('新增之後應該查得到', async () => {
    // ⋯⋯
  })
})
```

功能上完全等價，差別在**收尾這件事得自己顧**。

- `beforeAll` 跟 `afterAll` 要自己配對
- 關閉順序要自己排對，先關 app 再關容器
- timeout 要自己記得加，不然抓映像檔那次會逾時
- `app?.` 那個問號是因為 `beforeAll` 可能中途失敗，變數還是 `undefined`

<br/>

我翻了幾個 GitHub 上的真實專案，**忘記寫 `container.stop()` 的比例高得驚人**，測試跑完容器就留在那邊。%(°ㅂ°)%

Effect 那邊不用擔心這件事，因為「怎麼開」跟「怎麼關」在 `Effect.acquireRelease` 是綁在一起宣告的，`layer(...)` 負責在正確的時機關掉，順序由 `Scope` 保證。

### 整理一下差別

| | Effect | NestJS |
|---|---|---|
| 組合單位 | Layer | `@Module` |
| API 文件 | `HttpApiSwagger.layer()` 一行 | 要另外裝 `@nestjs/swagger`，並在 DTO 補 `@ApiProperty` |
| 回應驗證 | `addSuccess` 會驗 | 不驗，回傳什麼就送什麼 |
| 漏了依賴 | 編譯器直接紅 | 啟動時才噴 `can't resolve dependencies` |
| 測試替換 | `Layer.provide`，跟正式環境同一招 | `Test.createTestingModule().overrideProvider()` |
| 測試資源收尾 | `acquireRelease` 綁在一起宣告 | 自己寫 `afterAll`，順序自己排 |
| 型別安全的前端 client | 從同一份定義產出 | 沒有，要自己寫或另接工具 |

<br/>

最值得注意的是**回應驗證**那列。

NestJS 的 `ValidationPipe` 只擋進來的請求，回傳的東西沒人檢查。`TodoService` 哪天多回傳一個欄位、或少了 `done`，前端才會發現。

Effect 版本的 `addSuccess(Todo)` 是雙向的，回傳值對不上 schema 當場就爆。%( ˘•ω•˘ )%

<br/>

至於資料夾，兩邊都拆得開，差別在**邊界的形狀**。

NestJS 的邊界是 module，一個 class 把 controller 跟 provider 都包住。Effect 的邊界是 Layer，而路由宣告跟路由實作被拆到兩層去了。

代價是 feature 資料夾沒那麼獨立，換到的是那份宣告可以獨立拿去產 client 跟文件。%( ˘•ω•˘ )%

<br/>

這其實就是整篇文章的縮影，Effect 前期一定寫得比較多，換到的是後面改動時編譯器會擋住你。

專案越小越不划算，越大越值得。%(´,,•ω•,,)%

## 那 Effect 是不是萬靈丹

一路看下來好像 Effect 完勝，該說的壞話還是要說一下。%(｢･ω･)｢%

- **學習曲線真的陡**，`Effect.gen`、`pipe`、`Layer`、`Context` 一次要吃下好幾個新概念，團隊要有人願意帶
- **小工具不值得**，十行的 CLI script 用 Effect 包起來，樣板程式碼比原本邏輯還多
- **生態圈小很多**，遇到問題能查到的資料，跟 Node.js 原生寫法差一大截
- **跟現有程式碼混用有摩擦**，專案裡一半 Promise 一半 Effect，來回轉換的樣板碼會讓人很煩躁

<br/>

務實一點的判斷方式，看**那三欄有沒有東西可填**。

錯誤只有一種、要用的服務只有一兩個、流程直來直去，原生 TypeScript 配上好好設計的參數傳遞就很夠用。

錯誤分支很多、服務一堆、還要重試跟併發，那三欄填滿的價值就出來了，很值得那份學習成本。%( ˘•ω•˘ )%

## 總結 🐟

- 前端先別急著跟進。元件測試多半用 MSW 在網路那層攔，替換服務那套優勢用不上，官方 Vue 綁定也還卡在還沒發正式版的 v4
- `@effect/platform` 不只是 HTTP，WebSocket、檔案系統、子行程、Worker 都在裡面，換平台等於換一顆 Layer
- 跟 NestJS 最大的差別在**什麼時候發現漏了依賴**，NestJS 要等啟動時容器組裝才噴錯，Effect 是編譯器直接紅
- 效能方面 Effect 的 HTTP 層沒想像中肥，但那份 benchmark 有一堆前提要看清楚，而且框架通常不是你的瓶頸
- 已經在用 oRPC 的話兩者不衝突，合約留給 oRPC、Effect 進 handler，Zod 契約一行都不用改

<br/>

寫到這裡大概可以回答那個老問題了。

Effect 沒打算取代 TypeScript，也未必適合每個專案。但如果你也常常在翻「這函數到底會噴什麼錯、到底需要什麼」，它把答案寫進型別的做法，現在真的值得重新評估一次。%(ゝ∀・)b%
