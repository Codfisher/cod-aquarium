# 手動改壞與 Stryker：實驗報告

本文是文章〈AI 會自己把程式改壞來驗證測試，那還需要 Stryker 嗎？〉的完整資料。實驗日期：2026-11-02 至 2026-11-03。

這是第二版實驗。第一版用 es-toolkit 的真實 bug 當題目，以 bug 偵測為主要指標；看過第一版的結果後，決定在自己的專案從零重做，放棄全部舊內容，並且不再量測 bug。因此第二版的設計並非完全不受第一版結果影響（見偏離紀錄 D14）。

實驗分四段。A、B 兩組各 3 位先做完；看過結果後，又追加 C 組 3 位（先 Stryker、再手動改壞），回答「兩者並用有沒有比單用 Stryker 更好」。C 組是事後追加的，見 D15。接著追加 D 組 3 位（手動改壞，但不要求逐筆記錄），用來量測記錄要求對成本的影響，見 D23。最後發現 B、C 階段二、D 的受試者全部用腳本批次套用改壞，沒有一位直接編輯原始碼，於是再追加 E 組 3 位（禁止腳本，每次改壞都直接編輯原始碼），見 D24。

## 結論

**這個實驗不找 bug，只比較驗證做法的價值。** 五組各 3 位受試者，同一個專案、同樣的 5 個檔案、同一個模型與推理強度。樣本數只有各 3 位，全部是觀察，不是統計檢定。

- **用 Stryker 的突變分數評分，Stryker 流程最高。** 885 個突變體，A 組平均 97.48 分，C 組階段一與最終都是 97.18 分，B 組（手動）91.79 分，D 組（手動，不要求記錄）91.37 分，E 組（逐筆直接編輯）90.55 分。Stryker 組補測試時就在看這份清單，這項差距對 Stryker 組有利。
- **用手動改壞版本評分，Stryker 組沒有輸給手動組，但差距不穩。** 只有 C 組寫過的 103 個改壞版本（不等價 97 個），A、B 都不是作者，是 Stryker 組和手動組唯一能正面比較的一批：A 沒擋住 12.37%（36/291，三位各 11、15、10），B 沒擋住 14.78%（43/291，三位各 13、16、14）。A2 漏的 15 個比 B 漏的 13 個還多，組內三位的差距比兩組之間的差距大。D 組在這批沒擋住 13.75%（40/291，三位各 14、13、13），落在 A 與 B 之間；E 組沒擋住 17.18%（50/291，三位各 16、16、18），三位都比 A 組任何一位漏得多。這批偏向 Stryker 流程的弱點寫成，但 97 個裡 85 個本來就被作者階段一的測試擋住，六套 Stryker 流程全漏的只有 6 個。只有 B 組寫過的 619 個（不等價 610 個）沒有手動組參與，只能比 Stryker 流程內部：A 1.53%（28/1830），C 階段一與最終都是 1.64%（30/1830）。
- **Stryker 之後再手動改壞，Stryker 分數沒有變。** C 組三位的階段一與最終，Stryker 結果逐一突變體比對完全相同（858、858、864 個擋住）。
- **階段二補的測試，幾乎只擋得住自己想到的改壞。** 三位共新增 15 條測試（7、6、2）。自己寫的（非等價）改壞版本沒擋住的，從 20 個降到 2 個；別人寫的，只多擋住 2 個（C2 的 U0277、U0839）。
- **手動改壞確實想到 Stryker 沒有的改法。** 有 10 個不等價的改壞版本，Stryker 流程的六套測試（A 三位加 C 階段一三位）全部擋不住。其中 9 個有人擋得住，6 個只有想到它的人自己的測試擋得住，另外 3 個（U0383、U0851、U0852）在作者之外，只有事後追加的 D 組擋住；7 個是在既有程式上多加東西（3 個 `.trim()`、1 個排序、`.min(1)`、`.int()`、多一個列舉值），1 個拿掉排序鍵，2 個換掉判斷或取值來源。剩下 1 個（U0829）十二套測試全部擋不住，兩位作者還認為等價，實際上不等價。6 個只有 C 組寫過，依 C 組的設計（階段二專找自己階段一測試的漏洞）被六套漏掉是意料中的事。
- **反方向也存在，不能說比較少。** 對稱版本（A 三套對 B 三套）：A 三套全漏、B 有人擋住的有 6 個（其中 5 個只有 B 組作者擋得住，偏向手動組）；B 三套全漏、A 有人擋住的有 10 個，其中 U0266、U0586 若改判等價則為 8 個，U0107、U0430、U0431 的互斥檢查在輸入 schema 已被擋下，上線時到不了，依上線條件算會再縮小。只看第二批（97 個）是 0 對 5。上表缺口的 10 個算法不同（要六套全漏），見「缺口」。
- **要求逐筆記錄時，手動改壞比較貴；D 組不要求記錄，成本就和 Stryker 差不多。** B 組平均輸出 token 16.2 萬、耗時 52.7 分鐘，A 組 11.4 萬、45.1 分鐘，C 組合計 15.1 萬、59.1 分鐘（階段二本身平均 3.6 萬、16.4 分鐘）。事後追加的 D 組做法與 B 組相同，只是沒有記錄要求：輸出 token 12.2 萬（A 的 1.07 倍）、耗時 36.5 分鐘（A 的 0.81 倍）。D 組的改壞版本也寫得比較少（輸出檔顯示平均約 334 個，B 組 441 個），記錄要求與改壞版本數各占多少，這次分不開。事後用紀錄檔估算的記錄開銷上限是 B 組輸出 token 的 14%，比實際差距小。
- **B、C 階段二、D 的「手動改壞」其實是腳本批次執行。** 九位受試者直接編輯目標檔案的次數都是 0，全部把改壞版本寫成清單，再用自己寫的腳本逐筆套用、跑測試、還原。提示詞准許「寫腳本協助」，B、C 組又要求 find／replace 格式的紀錄；D 組沒有格式要求，提示詞明寫可以直接編輯原始碼，三位仍然全選腳本。資料能支持的是「准用腳本時，AI 會選腳本」。這和 AI 日常直接改原始碼、跑測試、改回來不同（D24）。
- **逐筆直接編輯的手動改壞（E 組）最快，輸出 token 與 Stryker 組相近，但改壞之後幾乎沒補測試。** 禁止腳本後，三位自述改壞 31、約 33、約 38 次就自己收手（B 組 302 到 517 個）。輸出 token 平均 108,656（A 組的 0.95 倍），耗時 19.6 分鐘（0.43 倍）；API 回合數平均 71（A 組 42），讀取快取的 token 1,114 萬（1.98 倍）。三位自己挑的改壞幾乎全被自己的測試擋住（自述 29/31、33/33、37/38；對話紀錄裡 E 有 3 次改壞後測試全過），E 與 E3 開始改壞後沒有修改任何測試，E2 只改了一次，交出的測試幾乎就是改壞之前的測試。嚴格度：Stryker 突變分數平均 90.55%，個別分數與 B、D 重疊（見第一項）；交叉檢驗明顯較鬆，三位在只有 C 組寫過的 97 個上都比 A 組任何一位漏得多（見第二項），在 909 個上漏 51 到 58 個，D 組 35 到 41 個。E 組禁止腳本是人為限制，結果只代表「AI 逐筆手動改壞、改幾次由它決定」這個情境。

## 設計

### 問題

AI 寫測試時常會自己把程式改壞、跑測試看紅不紅，這等於手動版的突變測試。問題是：

1. 用手動改壞驗證和用 Stryker 驗證，最後寫出的測試一樣嚴嗎？
2. 手動改壞想到、Stryker 沒有的改壞有多少？有用嗎？
3. 手動改壞的成本是多少？
4. 用 Stryker 補到收斂之後，再做手動改壞，還能多補到什麼？多花多少？（C 組）
5. 手動改壞的成本，有多少來自逐筆記錄的要求？（D 組，事後追加）
6. AI 不寫腳本、逐筆直接修改原始碼時，手動改壞的成本與測試嚴格度如何？AI 自己會改壞幾次？（E 組，事後追加）

### 名詞

- 突變體：Stryker 自動產生的每個改壞版本。
- 改壞版本：手動改壞時，受試者自己寫的每個改壞。
- 擋住：改壞後至少一條測試失敗或逾時（Stryker 稱為殺死）。
- 存活：改壞後所有測試照樣通過。
- 等價：改了程式碼，行為卻完全沒變，沒有任何測試擋得住。判定規則見「評分方式」第 6 項。
- 作者：寫出某個改壞版本的受試者。同一個改壞版本可以有多位作者。

選這個專案，是因為它有真實的資料庫操作、資料驗證 schema 與權限判斷，比工具函式更接近日常業務程式。service 會連資料庫，測試用 mongodb-memory-server（每個測試檔各開一個記憶體資料庫）。原有的測試檔全部移除，受試者從頭寫。實作視為正確，沒有放任何 bug。

### 受試者與各組做法

- 受試者：Claude Sonnet 5.5 子代理，推理強度明確指定 high，每位獨立工作區（各自 `pnpm install`）。
- A 組（Stryker）：Stryker 10.1.1 加範例測試，三位編號 A、A2、A3。設定檔由實驗者提供（mutate 範圍是 5 個目標檔案；pnpm 環境需要 `plugins: ["@stryker-mutator/vitest-runner"]` 與 ignorePatterns 的 `!.nuxt`、`!.nuxt/tsconfig.server.json` 例外），所以架設 Stryker 的成本不在受試者的耗時內。針對存活突變體補測試，等價突變體需說明理由；禁止手動改壞原始碼。
- B 組（手動改壞）：三位編號 B、B2、B3。不得安裝或使用 Stryker。每個改壞必須在套用前，把 `{id, file, find, replace, note}` 附加到 `mutation-log.jsonl`，紀錄只增不減。這個逐筆紀錄的要求是為了事後取得改壞清單，會增加輸出 token。
- C 組（Stryker 加手動改壞，事後追加）：三位編號 C、C2、C3。同一位受試者依序做兩階段。階段一與 A 組完全相同，收斂並完整跑完 Stryker 後，把測試、Stryker 報告與完成時間存進 `scratch-me/`。階段二改用手動改壞（規則同 B 組，逐筆記錄），不准再執行 Stryker，也不准讀 Stryker 報告。
- D 組（手動改壞，不要求記錄，事後追加）：三位編號 D、D2、D3。與 B 組唯一的差別是沒有逐筆記錄的要求（不要求、也不禁止，受試者用自己認為有效率的方式做），其餘都相同。預先登記補充（sha256 26f9685e…）在 D 組開工前寫成。
- E 組（逐筆手動改壞，禁止腳本，事後追加）：三位編號 E、E2、E3。與 D 組唯一的差別是驗證方法：每次改壞都必須用編輯工具直接修改原始碼，一次只改壞一處，跑測試確認後立刻用編輯工具還原；禁止用腳本、程式或批次指令套用、執行或還原改壞，也禁止把改壞版本寫成清單或檔案；沒有記錄要求；改幾次、何時收手由受試者自己判斷。預先登記補充（sha256 13bf88dd…）在 E 組開工前寫成。

各組都只准寫範例測試，不准用 fast-check，也看不到別組的做法。A、B 的提示詞除了「驗證方法」一節外完全相同，C 組是 A 組提示詞加上兩階段驗證方法，D 組是 B 組提示詞拿掉記錄要求，E 組是 D 組提示詞改掉驗證方法的第二段，全文見附錄。

A、B 分三批啟動（先導 A、B；第一波 A2、B2；第二波 A3、B3），每批同時 2 位。C、C2 同時啟動，C3 在 C 結束時才啟動（與 C2 重疊約 11 分鐘），所以 C3 的執行條件與前兩位略有不同（D9）。D、D2 同時啟動，D2 結束時才啟動 D3（與 D 重疊約 10 分鐘），同時最多 2 位。E、E2 同時啟動，E2 結束時才啟動 E3；E 在 E3 啟動後約 30 秒結束，所以 E3 幾乎是單獨執行（D24）。

- 不量測 bug 偵測。
- 結果好壞都不重跑、不換目標檔案。
- 分析計畫共六項：Stryker 突變分數、交叉檢驗、重疊分析、成本、稽核、存活突變體的等價性驗證。

C 組的預先登記補充（sha256 c533531a…）是在 A、B 結果全部出來之後、C 組結果出來之前寫的，所以整個 C 組的存在不是預先設計。D 組（sha256 26f9685e…）與 E 組（sha256 13bf88dd…）也一樣，各自在開工前寫成，但都是看過先前各組結果才追加。全文見附錄。

### 評分方式

1. **Stryker 重跑。** 十二套測試（A、A2、A3、B、B2、B3、C 與 C2 與 C3 各自的階段一快照和最終版），都在乾淨的工作區用同一份設定重跑 Stryker（885 個突變體，perTest 覆蓋率，並行度 3，沒有排除任何突變器）。C 組階段一的測試是受試者自己保存的快照，Stryker 分數不採用受試者自報，一律重跑。事後追加的 D、E 組六套測試也用同一份設定重跑，交叉檢驗同樣補跑，合計十八套。
2. **交叉檢驗。** 手動改壞的紀錄（B 組三位加 C 組三位），依「套用後的原始碼雜湊（去註解、壓縮空白與分號）」去重，聯集 925 個（B 組 821 個，C 組新增 104 個）。其中 1 個（C3 的 M032，U0894）套用後語法錯誤，十二套測試都載入失敗，排除，有效改壞版本 924 個。每個改壞版本套用到原始碼後，用十二套測試各跑一次，測試失敗或逾時（240 秒）算擋住。為了縮短時間，只跑會匯入被改檔案的測試（`vitest related`）。先導 A、B 兩套測試與 39 個改壞版本驗證過，擋住與否與完整執行 0 筆不同，其餘十套測試沒有另外驗證。
3. **重疊分析。** 925 個改壞版本與 Stryker 的 885 個突變體比對：套用後原始碼完全相同；改動範圍與某個突變體重疊；只和整個物件、陣列、區塊或函式被清空這類大範圍突變體重疊；該處沒有任何突變體。
4. **成本。** 取自子代理對話紀錄，依訊息 id 去重。耗時是子代理從開始到結束，包含它自己跑的 Stryker，不含評分時我重跑的 Stryker。C 組以受試者自己寫入的 `stage1-done.txt` 時間為界，拆成階段一與階段二；同一個訊息 id 只歸入第一次出現的階段，避免跨界的訊息重複計算。
5. **稽核。** 掃描所有指令，找資料夾外存取、網路、安裝套件、dev server 或 build、Stryker、fast-check；交付時以 `sha256sum -c baseline.sha256` 檢查五個目標檔案沒被改動。C 組另檢查階段二有沒有執行 Stryker、階段一有沒有寫入原始碼。沒有檢查 Stryker 組有沒有在過程中手動改壞再還原（交付時雜湊相同，且 A 沒有 `mutation-log.jsonl`，但這不能證明沒做過）。
6. **等價性。** 判定規則：沒有任何一套測試擋得住的突變體與改壞版本，才交給另一位 Opus high 子代理驗證；只要有任何一套測試擋得住，就不當成等價。驗證方式是套用後寫能區分的探針測試，原程式通過、突變體失敗才算非等價；找不到差異且有清楚理由才算等價。等價以回傳值、拋出的錯誤、資料庫最終狀態為準，物件鍵的順序不算。

#### 逐筆記錄的影響：先估算（事後分析，D22）

手動組被要求逐筆記錄改壞版本，這可能讓輸出 token 偏高。估算方式如下。

- 三位 B 組受試者實際的做法，都是把改壞版本寫進一個檔案，再由自己寫的腳本逐筆套用，並自動寫入 `mutation-log.jsonl`（B 用 `mutants-N.txt` 加 `run-mutants.mjs`，B2 用 `mutants*.cjs` 加 `runner.cjs`，B3 用 `muts*.mjs` 加 `runner.mjs`）。「改哪裡、改成什麼」（find、replace）無論有沒有記錄要求，手動改壞都得寫出來，不算記錄開銷。記錄要求多出來的，只有 id、檔名、備註這幾個欄位，加上記錄用的腳本。
- 從 `mutation-log.jsonl` 算出每筆的 id、file、note 欄位字元數（含欄位名稱與標點），加上整支 runner 腳本的字元數，再乘上該受試者的「輸出 token 除以可見輸出字元數（文字加上工具輸入）」換算成 token。這個比例把看不到的思考 token 也攤進去，會高估，所以結果是上限。

| | B | B2 | B3 | B 組平均 | C 階段二平均 |
|---|---|---|---|---|---|
| 輸出 token | 143,235 | 162,476 | 181,540 | 162,417 | 35,803 |
| 記錄開銷上限 | 19,813 | 25,532 | 23,984 | 23,110 | 9,850 |
| 占輸出 token | 13.8% | 15.7% | 13.2% | 14.2% | 27.5% |
| 扣除後 | 123,422 | 136,944 | 157,556 | 139,307 | 25,953 |

扣除後，B 組平均是 A 組（114,045）的 1.22 倍（扣除前 1.42 倍）。C 組合計（階段一 115,198 加扣除後的階段二）為 141,151，是 A 組的 1.24 倍（扣除前 1.32 倍）。C 階段二的記錄開銷上限依序為 7,227、11,122、11,200；C2 的可見字元少、換算比例偏高（每字元 1.14 token，B 組約 0.58 到 0.61），上限因此偏大。

敏感度參考：連改壞檔與腳本整份扣掉（包含 find、replace），B 組平均剩 119,529，是 A 組的 1.05 倍。這等於把手動改壞的核心工作也扣掉，不算記錄開銷，只用來看差距有多依賴這個設定。

耗時無法用 token 反推。若耗時與輸出 token 等比例縮短，B 組平均會從 52.7 分鐘變成 45.2 分鐘，與 A 組的 45.1 分鐘相同。這是極端假設（耗時還包含跑測試與等待 Stryker），只能說明 B 組比 A 組多出的 1.17 倍耗時，有可能全部來自記錄開銷，這次的資料分不出來。

估算的結論：輸出 token 的差距，扣掉記錄開銷上限後仍有 1.22 倍；耗時差距則無法排除全由記錄要求造成。要確認，需要另一組不要求記錄的手動組，於是追加了 D 組。

#### 逐筆記錄的影響：D 組實測（事後追加，D23）

D 組做法與 B 組相同，只是沒有記錄要求。三位的輸出 token 平均 121,616，是 A 組（114,045）的 1.07 倍、B 組（162,417）的 0.75 倍；耗時平均 36.5 分鐘，是 A 組（45.1）的 0.81 倍、B 組（52.7）的 0.69 倍。B 與 D 的輸出 token 差 40,801（25%），其中記錄開銷上限約 23,110，剩下約 17,700 與「D 組改壞版本寫得比較少」的方向一致。

改壞版本數（來自受試者腳本的輸出檔，D 約 252，D2 約 377，D3 約 373，平均約 334；B 組去重後 302、505、517，平均 441）：輸出 token 除以改壞版本數，B 組約 368，D 組約 364，兩組接近。這顯示輸出 token 可能大致隨改壞版本數增加，但只有各 3 位，且 D 組的數字是概數，不能據此分離「記錄要求」與「改壞版本數」兩個因素。

D 組的測試嚴格度與 B 組接近：Stryker 突變分數平均 91.37%（B 組 91.79%）；在只有 C 組寫過的 97 個上沒擋住 13.75%（B 組 14.78%，A 組 12.37%）；在只有 B 組寫過的 610 個上沒擋住 3.28%（A 組 1.53%、C 組 1.64%）。所以「不要求記錄」沒有讓測試變得更嚴，也沒有更鬆。

**為什麼免記錄組耗時比 A 組短（事後檢查，D23）。** 從對話紀錄把耗時拆成工具等待與模型自己的時間（`why-cheaper.mjs`）：A 組等 Stryker 的時間是 5.3、32.0、25.9 分鐘（平均 21.1，占總耗時 47%）；D 組沒有 Stryker，但 D 與 D3 自述改壞腳本各跑約 25 與 30 分鐘（放在背景執行，工具等待的統計抓不到）。兩邊的測試迴圈成本相近，耗時範圍也重疊（A 33.4 到 54.6，D 30.1 到 40.6），0.81 倍不能解讀成手動改壞比較快。寫測試的字元數三組接近（A 平均 147 千，B 146 千，D 149 千），輸出 token 的大宗是寫測試，驗證方法只占邊際，所以 D 與 A 的 token 接近。另外 D 組停在較低的嚴格度（突變分數 91.37% 對 97.48%），花差不多的 token 換到比較鬆的測試，不能說手動改壞比較划算。

結論：要求逐筆記錄時，手動改壞比 Stryker 貴 1.42 倍（輸出 token）、慢 1.17 倍；不要求記錄，輸出 token 降到 1.07 倍，耗時 0.81 倍但範圍重疊。成本差距主要來自實驗設計（記錄要求，以及隨之而來較多的改壞版本），不是手動改壞本身。

D 組的成本與 A 組接近，我回頭檢查各組怎麼套用改壞。從對話紀錄統計每位受試者用編輯工具（Edit、Write）寫入五個目標檔案的次數：

| A（三位） | 0、0、0 | 只用 Stryker |

| C 階段二（三位） | 0、0、0 | 改壞腳本（C 的 `mut.mjs`，C2 的 `runmut.mjs` 加 `batch*.mjs`，C3 的 `mut-runner.mjs`） |
| D（三位） | 0、0、0 | 改壞清單加執行腳本（D 的 `muts*.cjs`，D2 的 `muts.py`，D3 的 `mutate.mjs`） |

九位手動改壞的受試者，全部把改壞版本寫成清單，再由腳本逐筆套用、跑測試、還原，每位 103 到 517 個。這比較像自己做一個簡易版 Stryker。B、C、D 的提示詞都准許「寫腳本協助套用改壞、跑測試與還原」，B、C 又要求每筆用 find／replace 的 JSON 記錄，等於先替受試者準備好資料格式。D 組沒有任何格式要求，提示詞明寫「可以直接編輯原始碼，也可以寫腳本」，三位仍然全選腳本。所以資料能支持的是「准用腳本時，AI 會選腳本」，不能說提示詞叫它寫。AI 平常寫測試時的手動改壞，通常是直接改原始碼、跑測試、改回來，前四組都沒有量到這種情境，於是追加 E 組。

預先登記補充（附錄）寫「六位受試者直接編輯原始碼的次數都是 0」，當時只檢查了 B、D；之後才補查 C 組階段二，所以這裡是九位。

#### 逐筆手動改壞：E 組實測（事後追加，D24）

E 組禁止腳本，每次改壞都用編輯工具直接修改原始碼，改幾次由受試者決定。改壞次數有兩種算法，一是受試者最終回報的自述次數，二是對話紀錄裡成功的原始碼編輯數除以 2（一次改壞、一次還原）。後者每位多 5 次左右，可能來自一次改壞分兩處編輯、改錯位置重做、還原失敗後重做；部分還原用的字串範圍與改壞時不同，無法逐筆配對，所以兩者都是概數（E 自述的 31 也是），本報告與文章都以自述為準。

API 回合數的對照：A 組 51、44、30（平均 41.7），B 組 45、55、56（52.0），D 組 33、38、29（33.3）。E2、E3 各有 2 次編輯失敗（要取代的字串在檔案裡出現兩次，或找不到），之後重新編輯成功，交付時雜湊都與基準一致。

成本相對 A 組：輸出 token 0.95 倍（108,656 對 114,045），耗時 0.43 倍（19.6 對 45.1 分鐘），讀取快取 token 1.98 倍（1,114 萬對 563 萬），新輸入 token 0.33 倍。三位的耗時 18.7 到 20.6 分鐘，與 A（33.4 到 54.6）、D（30.1 到 40.6）都不重疊。E 組沒有 Stryker 要等，也沒有在背景跑數百個改壞，開工約 8 分鐘就開始改壞（A、B、D 完整驗證的開始時間是 8 到 11 分鐘；A3 在 3.1 分鐘先對 schema 跑過一次 `--mutate`，所以寫測試的時間沒有比較短），改三十幾次後收手。讀取快取 token 偏高，是因為改壞、跑測試、還原要分成多個回合（E2、E3 多半把「還原上一處、改壞下一處、跑測試」放在同一個回合，每次改壞約 1 個回合；E 約 2 個回合），每個回合都會把整段對話再讀一次。新輸入 token 只有 0.33 倍，一個可能的解釋是 E 組從沒有長時間閒置，快取一直沒過期；A 組等 Stryker 時快取可能過期，回來後要重新寫入。這點沒有驗證。

**改壞之後的測試修改（獨立審查時發現）。** 從對話紀錄找出開始改壞之後對測試檔的寫入：E 與 E3 是 0 次，E2 只有 1 次（08:00:50 在 crossMatch 的測試加干擾場次，是預判會漏而先補，不是改壞後測試全過才補）。E 的測試在第一次改壞前 12 秒寫完，之後測試數一直是 326；E2 一直是 297；E3 開始改壞前已經是 312 條，最後也是 312 條。對照組在開始驗證之後都有修改測試：寫入測試檔的次數 A 組 2、10、9（A3 以 9.6 分鐘完整驗證開始算；從 3.1 分鐘只跑 schema 的 `--mutate` 算起是 14，含初次寫成的測試檔），B 組 6、3、12，D 組 2、3、2（D 組測試數多了 3、5、3 條）；C 組階段二改算新增條數，是 7、6、2 條。

三位自述的改壞，自己的測試幾乎都擋住（E 31 次擋住 29 次、E2 約 33 次全擋、E3 約 38 次擋住 37 次）。對話紀錄裡 E 實際有 3 次改壞後測試全過（`if (false && owned)`、拿掉 `!id`、create 的 `note: input.note`），E 的回報把後兩次併成一點；E2 回報裡「全部變紅」與「有一次沒變紅」自相矛盾，對話紀錄裡沒有任何一次全過。所以 E 組合計沒擋住 4 次，受試者都判為等價，其中至少 2 次依「評分方式」第 6 項規則應屬非等價：E3 的 `{ appearanceCount: -1 }`（與 U0555 逐字相同，B2、C 的測試擋得住），以及 E 拿掉 claim 的預先檢查（與 U0586 行為相同；有唯一索引時行為相同，依上線條件可改判等價，見 U0266、U0586 的討論）。確定判錯的是前者。E 組交出的測試，幾乎等於寫完就交出的測試，改壞驗證沒有帶來修改；被改壞的地方，多半已有測試涵蓋。

測試嚴格度：Stryker 突變分數平均 90.55%（A 97.48%、B 91.79%、D 91.37%），個別分數 90.40 到 90.85，與 B2（90.62%）重疊；交叉檢驗明顯較鬆：只有 C 組寫過的 97 個沒擋住 17.18%，三位 16、16、18 個，都比 A 組三位（11、15、10）多；只有 B 組寫過的 610 個沒擋住 5.08%（A 1.53%、D 3.28%），三位 30 到 33 個，D 組 18 到 21 個，不重疊。E 組比 D 組低的部分，與「D 組批次改壞後有補測試、E 組沒有」方向一致，但只有 3 位，不能當成因果證據。

結論：三種手動改壞的成本，取決於 AI 用什麼方式改壞。准用腳本時，AI 會寫出數百個改壞版本批次執行，輸出 token 是 A 組的 1.07（D）到 1.42 倍（B）；禁止腳本時，AI 改三十幾次就收手，輸出 token 0.95 倍、耗時 0.43 倍，但它挑的改壞幾乎全被自己的測試擋住，改完也幾乎沒補測試。B、D、E 九位個別的原始 Stryker 突變分數都在 90.4% 到 93.0% 之間，都低於 Stryker 組。

### 稽核

- 十五位受試者的推理強度都是 high，模型都是 claude-sonnet-5-5。
- A 組：只有 A 違規：列了家目錄的 `.cache/mongodb-binaries` 資料夾名稱、列了上一層資料夾名稱、對 `node_modules/@stryker-mutator/core` 的原始碼做過 grep（自述沒有命中）。沒有寫入任何資料夾外的檔案。
- A2、A3、B、B2、B3 沒有資料夾外存取、沒有網路、沒有安裝套件、沒有 dev server 或 build、沒有 fast-check；B 組沒有任何指令提到 Stryker。A3 的「網路」命中只是測試字串裡的圖片網址，不是連線。
- C 組：三位的階段一都跑了 Stryker，階段二沒有任何 Stryker 指令；階段一只寫入測試檔，沒有寫入原始碼；沒有資料夾外存取、沒有安裝套件、沒有 dev server 或 build、沒有 fast-check。腳本的「網路、dev」命中經檢視全是 `/dev/null`、用 `ping` 當 sleep 之類的誤判。階段二三位都用自己寫的腳本批次套用改壞（見「手動改壞的實際做法」），仍逐筆寫入日誌。
- D 組：三位都沒有使用 Stryker、沒有網路、沒有安裝套件、沒有 dev server 或 build、沒有 fast-check、沒有碰其他工作區。稽核腳本的「家目錄、上層」命中經檢視，是 `scratch-me/` 底下用 `../server/...` 指回自己的工作區，以及測試檔裡的 `import` 相對路徑。三位都沒有建立 `mutation-log.jsonl`，但都在 `scratch-me/` 自己寫了改壞腳本與結果檔（D 的 `muts*.cjs`、`out*.txt`，D2 的 `muts.py`、`result*.txt`，D3 的 `mutate.mjs`、`mut1.log`）。

## 偏離紀錄

- D1：A 的工作區少了 stryker.config.json（建立工作區的指令串在寫入設定檔之前失敗，我沒有發現就啟動了 A，任務說明卻寫「設定檔已備妥」）。A 自己寫了等效設定；評分一律用統一設定重跑。
- D2：A 的違規，內容見上方稽核。
- D3：A 自述的 Stryker 完整執行 9 分 37 秒、97.63%，與評分重跑的結果一致。

## 限制

- 樣本只有各 3 位，只有一個專案、一個模型（Sonnet 5.5）、一個推理強度（high），所有數字都是觀察。
- B、C 階段二、D 的受試者都用腳本批次套用改壞，每位寫了 103 到 517 個（D 組約 252 到 377 個），遠比 AI 日常隨手改壞的幾次多，這三組的結論不能直接套到日常情境。E 組逐筆直接編輯，每位自述 31 到約 38 次，較接近日常，但「禁止腳本」本身是人為限制，而且 E 組晚於其他組執行，E3 幾乎單獨執行。
- 925 個改壞版本全由手動改壞的受試者（B 組與 C 階段二）提出，拿來評分會偏向他們的想法。Stryker 的 885 個突變體正是 Stryker 流程補測試時對照的清單，用它評分對 Stryker 流程有利。兩邊的資料都用，也把作者對自己改壞版本的成績拿掉；不過這個處理對手動改壞偏嚴格，且沒有獨立來源的改壞版本可以對照。
- C 組寫改壞版本時，看的是自己已通過 Stryker 的測試，所以那批改壞版本偏向 Stryker 流程的弱點，但 97 個裡 85 個本來就被作者階段一的測試擋住，A 沒擋住 12.37%、B 沒擋住 14.78%，遠高於第一批 A 的 1.53%，只能說這批比較難，兩批的分母與難度不能直接比。
- C 組階段二的受試者已經看過 Stryker 的清單，所以階段二能補的比獨立的手動組更少，也可能因為知道自己已通過 Stryker 而提早收手。C 組的數字不能解讀為「手動改壞的獨立價值」，只是「Stryker 之後再做」的增量。
- 等價判定由一位子代理完成，除了探針測試的證據，仍有判斷成分。#662、#663 以及對應的 U0266、U0586 在「資料庫有唯一索引」的前提下行為相同，我依規則算成非等價。U0917 在鍵順序上不同，我判等價。另有 6 個只差多送一次無作用資料庫指令的突變體，我算等價，若連這種也算差異，每套測試的非等價存活各多 6 個。
- 「缺口」兩節的分析是事後探索，其中 6 個只有作者自己的測試擋得住（只看十二套時是 9 個）。
- A、C 階段一的突變分數是它們補測試時就在看的指標，所以分數高不意外，值得看的是它們在另一邊（手動改壞版本）的表現。
- 成本不含架設 Stryker 的工夫；手動改壞的逐筆紀錄要求會墊高成本：D 組不要求記錄，輸出 token 降到 A 組的 1.07 倍、耗時 0.81 倍（見「逐筆記錄的影響」，D22、D23），但記錄要求與改壞版本數兩個因素分不開；耗時範圍重疊，且同時執行的受試者會搶 CPU。E 組的輸出 token 是 A 組的 0.95 倍、耗時 0.43 倍，但讀取快取 token 是 1.98 倍；各種 token 的單價不同，這份報告沒有換算成金額。
- 沒有量測 bug 偵測，所以這份報告不能回答「哪一組的測試能抓到更多真的 bug」。
