# 手動改壞與 Stryker：實驗報告

本文是文章〈AI 會自己把程式改壞來驗證測試，那還需要 Stryker 嗎？〉的完整資料。實驗日期：2026-11-02 至 2026-11-03。

這是第二版實驗。第一版用 es-toolkit 的真實 bug 當題目，以 bug 偵測為主要指標；看過第一版的結果後，決定在自己的專案從零重做，放棄全部舊內容，並且不再量測 bug。因此第二版的設計並非完全不受第一版結果影響（見偏離紀錄 D14）。

實驗分兩段。A、B 兩組各 3 位先做完；看過結果後，又追加 C 組 3 位（先 Stryker、再手動改壞），回答「兩者並用有沒有比單用 Stryker 更好」。C 組是事後追加的，見 D15。

## 結論

**這個實驗不找 bug，只比較驗證做法的價值。** 三組各 3 位受試者，同一個專案、同樣的 5 個檔案、同一個模型與推理強度。樣本數只有各 3 位，全部是觀察，不是統計檢定。

- **用 Stryker 的突變分數評分，Stryker 流程最高。** 885 個突變體，A 組平均 97.48 分，C 組階段一與最終都是 97.18 分，B 組（手動）91.79 分。Stryker 組補測試時就在看這份清單，這項差距對 Stryker 組有利。
- **用手動改壞版本評分，Stryker 組沒有輸給手動組，但差距不穩。** 只有 C 組寫過的 103 個改壞版本（不等價 97 個），A、B 都不是作者，是 Stryker 組和手動組唯一能正面比較的一批：A 沒擋住 12.37%（36/291，三位各 11、15、10），B 沒擋住 14.78%（43/291，三位各 13、16、14）。A2 漏的 15 個比 B 漏的 13 個還多，組內三位的差距比兩組之間的差距大。這批偏向 Stryker 流程的弱點寫成，但 97 個裡 85 個本來就被作者階段一的測試擋住，六套 Stryker 流程全漏的只有 6 個。只有 B 組寫過的 619 個（不等價 610 個）沒有手動組參與，只能比 Stryker 流程內部：A 1.53%（28/1830），C 階段一與最終都是 1.64%（30/1830）。
- **Stryker 之後再手動改壞，Stryker 分數沒有變。** C 組三位的階段一與最終，Stryker 結果逐一突變體比對完全相同（858、858、864 個擋住）。
- **階段二補的測試，幾乎只擋得住自己想到的改壞。** 三位共新增 15 條測試（7、6、2）。自己寫的（非等價）改壞版本沒擋住的，從 20 個降到 2 個；別人寫的，只多擋住 2 個（C2 的 U0277、U0839）。
- **手動改壞確實想到 Stryker 沒有的改法。** 有 10 個不等價的改壞版本，Stryker 流程的六套測試（A 三位加 C 階段一三位）全部擋不住。其中 9 個有人擋得住，全是想到它的人自己的測試；7 個是在既有程式上多加東西（3 個 `.trim()`、1 個排序、`.min(1)`、`.int()`、多一個列舉值），1 個拿掉排序鍵，2 個換掉判斷或取值來源。剩下 1 個（U0829）十二套測試全部擋不住，兩位作者還認為等價，實際上不等價。6 個只有 C 組寫過，依 C 組的設計（階段二專找自己階段一測試的漏洞）被六套漏掉是意料中的事。
- **反方向也存在，不能說比較少。** 對稱版本（A 三套對 B 三套）：A 三套全漏、B 有人擋住的有 6 個（其中 5 個只有 B 組作者擋得住，偏向手動組）；B 三套全漏、A 有人擋住的有 10 個，其中 U0266、U0586 若改判等價則為 8 個，U0107、U0430、U0431 的互斥檢查在輸入 schema 已被擋下，上線時到不了，依上線條件算會再縮小。只看第二批（97 個）是 0 對 5。上表缺口的 10 個算法不同（要六套全漏），見「缺口」。
- **階段二不便宜。** C 組平均輸出 token 15.1 萬，A 組 11.4 萬，B 組 16.2 萬；耗時 59.1 分鐘對 45.1 分鐘、52.7 分鐘。階段二本身平均 3.6 萬輸出 token、16.4 分鐘。

## 設計

### 問題

AI 寫測試時常會自己把程式改壞、跑測試看紅不紅，這等於手動版的突變測試。問題是：

1. 用手動改壞驗證和用 Stryker 驗證，最後寫出的測試一樣嚴嗎？
2. 手動改壞想到、Stryker 沒有的改壞有多少？有用嗎？
3. 手動改壞的成本是多少？
4. 用 Stryker 補到收斂之後，再做手動改壞，還能多補到什麼？多花多少？（C 組）

### 名詞

- 突變體：Stryker 自動產生的每個改壞版本。
- 改壞版本：手動改壞時，受試者自己寫的每個改壞。
- 擋住：改壞後至少一條測試失敗或逾時（Stryker 稱為殺死）。
- 存活：改壞後所有測試照樣通過。
- 等價：改了程式碼，行為卻完全沒變，沒有任何測試擋得住。判定規則見「評分方式」第 6 項。
- 作者：寫出某個改壞版本的受試者。同一個改壞版本可以有多位作者。

### 目標

桌球比賽紀錄系統 ttmatch-v2（Nuxt 4、oRPC、Mongoose），commit 2079e89。目標檔案 5 個：

| 檔案 | 行數 |
|---|---|
| server/domains/match/service.ts | 449 |
| server/domains/player/service.ts | 415 |
| shared/match/schema.ts | 193 |
| shared/permissions.ts | 67 |
| server/utils/serialize.ts | 116 |

選這個專案，是因為它有真實的資料庫操作、資料驗證 schema 與權限判斷，比工具函式更接近日常業務程式。service 會連資料庫，測試用 mongodb-memory-server（每個測試檔各開一個記憶體資料庫）。原有的測試檔全部移除，受試者從頭寫。實作視為正確，沒有放任何 bug。

### 受試者與三種做法

- 受試者：Claude Sonnet 5.5 子代理，推理強度明確指定 high，每位獨立工作區（各自 `pnpm install`）。
- A 組（Stryker）：Stryker 10.1.1 加範例測試，三位編號 A、A2、A3。設定檔由實驗者提供（mutate 範圍是 5 個目標檔案；pnpm 環境需要 `plugins: ["@stryker-mutator/vitest-runner"]` 與 ignorePatterns 的 `!.nuxt`、`!.nuxt/tsconfig.server.json` 例外），所以架設 Stryker 的成本不在受試者的耗時內。針對存活突變體補測試，等價突變體需說明理由；禁止手動改壞原始碼。
- B 組（手動改壞）：三位編號 B、B2、B3。不得安裝或使用 Stryker。每個改壞必須在套用前，把 `{id, file, find, replace, note}` 附加到 `mutation-log.jsonl`，紀錄只增不減。這個逐筆紀錄的要求是為了事後取得改壞清單，會增加輸出 token。
- C 組（Stryker 加手動改壞，事後追加）：三位編號 C、C2、C3。同一位受試者依序做兩階段。階段一與 A 組完全相同，收斂並完整跑完 Stryker 後，把測試、Stryker 報告與完成時間存進 `scratch-me/`。階段二改用手動改壞（規則同 B 組，逐筆記錄），不准再執行 Stryker，也不准讀 Stryker 報告。

各組都只准寫範例測試，不准用 fast-check，也看不到別組的做法。A、B 的提示詞除了「驗證方法」一節外完全相同，C 組是 A 組提示詞加上兩階段驗證方法，全文見附錄。

A、B 分三批啟動（先導 A、B；第一波 A2、B2；第二波 A3、B3），每批同時 2 位。C、C2 同時啟動，C3 在 C 結束時才啟動（與 C2 重疊約 11 分鐘），所以 C3 的執行條件與前兩位略有不同（D9）。

- 結果好壞都不重跑、不換目標檔案。
- 分析計畫共六項：Stryker 突變分數、交叉檢驗、重疊分析、成本、稽核、存活突變體的等價性驗證。

C 組的預先登記補充（sha256 c533531a…）是在 A、B 結果全部出來之後、C 組結果出來之前寫的，所以整個 C 組的存在不是預先設計。兩份全文見附錄。

### 評分方式

1. **Stryker 重跑。** 十二套測試（A、A2、A3、B、B2、B3、C 與 C2 與 C3 各自的階段一快照和最終版），都在乾淨的工作區用同一份設定重跑 Stryker（885 個突變體，perTest 覆蓋率，並行度 3，沒有排除任何突變器）。C 組階段一的測試是受試者自己保存的快照，Stryker 分數不採用受試者自報，一律重跑。
2. **交叉檢驗。** 手動改壞的紀錄（B 組三位加 C 組三位），依「套用後的原始碼雜湊（去註解、壓縮空白與分號）」去重，聯集 925 個（B 組 821 個，C 組新增 104 個）。其中 1 個（C3 的 M032，U0894）套用後語法錯誤，十二套測試都載入失敗，排除，有效改壞版本 924 個。每個改壞版本套用到原始碼後，用十二套測試各跑一次，測試失敗或逾時（240 秒）算擋住。為了縮短時間，只跑會匯入被改檔案的測試（`vitest related`）。先導 A、B 兩套測試與 39 個改壞版本驗證過，擋住與否與完整執行 0 筆不同，其餘十套測試沒有另外驗證。
3. **重疊分析。** 925 個改壞版本與 Stryker 的 885 個突變體比對：套用後原始碼完全相同；改動範圍與某個突變體重疊；只和整個物件、陣列、區塊或函式被清空這類大範圍突變體重疊；該處沒有任何突變體。
4. **成本。** 取自子代理對話紀錄，依訊息 id 去重。耗時是子代理從開始到結束，包含它自己跑的 Stryker，不含評分時我重跑的 Stryker。C 組以受試者自己寫入的 `stage1-done.txt` 時間為界，拆成階段一與階段二；同一個訊息 id 只歸入第一次出現的階段，避免跨界的訊息重複計算。
5. **稽核。** 掃描所有指令，找資料夾外存取、網路、安裝套件、dev server 或 build、Stryker、fast-check；交付時以 `sha256sum -c baseline.sha256` 檢查五個目標檔案沒被改動。C 組另檢查階段二有沒有執行 Stryker、階段一有沒有寫入原始碼。沒有檢查 Stryker 組有沒有在過程中手動改壞再還原（交付時雜湊相同，且 A 沒有 `mutation-log.jsonl`，但這不能證明沒做過）。
6. **等價性。** 判定規則：沒有任何一套測試擋得住的突變體與改壞版本，才交給另一位 Opus high 子代理驗證；只要有任何一套測試擋得住，就不當成等價。驗證方式是套用後寫能區分的探針測試，原程式通過、突變體失敗才算非等價；找不到差異且有清楚理由才算等價。等價以回傳值、拋出的錯誤、資料庫最終狀態為準，物件鍵的順序不算。

### 手動改壞套用到各套測試

改壞版本 925 個（有效 924 個）。B 組三位分別寫了 302、505、517 個，C 組三位分別寫了 135、103、172 個（去重後）。作者數分布（有效 924 個）：1 位 506 個、2 位 202 個、3 位 110 個、4 位 57 個、5 位 28 個、6 位 21 個。只有 B 組寫過的 619 個，只有 C 組寫過的 103 個，兩組都寫過的 202 個。

沒有任何一套測試擋得住的有 16 個。子代理驗證：

- 15 個等價：U0126、U0299、U0429、U0436、U0454、U0530、U0607、U0683、U0821（先前已驗證）與 U0836、U0882、U0889、U0914、U0917、U0924。例如 `ObjectId.isValid` 本來就會拒絕空值，所以拿掉 `!id` 沒有影響。U0917 把展開順序對調，物件的鍵順序不同，經過 oRPC 輸出後順序與原本相同，依第 6 項規則（鍵順序不算）判等價；若直接呼叫函式又在意鍵順序，則不等價。

## 限制

- 樣本只有各 3 位，只有一個專案、一個模型（Sonnet 5.5）、一個推理強度（high），所有數字都是觀察。
- 手動組被要求系統化地逐筆記錄改壞，每位寫了 103 到 517 個，遠比 AI 日常隨手改壞的幾次多，結論不能直接套到日常情境。
- 925 個改壞版本全由手動改壞的受試者（B 組與 C 階段二）提出，拿來評分會偏向他們的想法。Stryker 的 885 個突變體正是 Stryker 流程補測試時對照的清單，用它評分對 Stryker 流程有利。兩邊的資料都用，也把作者對自己改壞版本的成績拿掉；不過這個處理對手動改壞偏嚴格，且沒有獨立來源的改壞版本可以對照。
- C 組寫改壞版本時，看的是自己已通過 Stryker 的測試，所以那批改壞版本偏向 Stryker 流程的弱點，但 97 個裡 85 個本來就被作者階段一的測試擋住，A 沒擋住 12.37%、B 沒擋住 14.78%，遠高於第一批 A 的 1.53%，只能說這批比較難，兩批的分母與難度不能直接比。
- C 組階段二的受試者已經看過 Stryker 的清單，所以階段二能補的比獨立的手動組更少，也可能因為知道自己已通過 Stryker 而提早收手。C 組的數字不能解讀為「手動改壞的獨立價值」，只是「Stryker 之後再做」的增量。
- 等價判定由一位子代理完成，除了探針測試的證據，仍有判斷成分。#662、#663 以及對應的 U0266、U0586 在「資料庫有唯一索引」的前提下行為相同，我依規則算成非等價。U0917 在鍵順序上不同，我判等價。另有 6 個只差多送一次無作用資料庫指令的突變體，我算等價，若連這種也算差異，每套測試的非等價存活各多 6 個。
- 「缺口」兩節的分析是事後探索，其中 9 個只有作者自己的測試擋得住。
- A、C 階段一的突變分數是它們補測試時就在看的指標，所以分數高不意外，值得看的是它們在另一邊（手動改壞版本）的表現。
- 成本不含架設 Stryker 的工夫；手動改壞的逐筆紀錄要求可能墊高輸出 token；耗時範圍重疊，且同時執行的受試者會搶 CPU。
- 沒有量測 bug 偵測，所以這份報告不能回答「哪一組的測試能抓到更多真的 bug」。
