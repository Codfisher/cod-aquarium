# 全由 AI 開發時，複雜度守門員有沒有用：實驗報告

本文是文章〈AI 都幫我寫好了，還需要管複雜度嗎？〉最後一節的完整資料。實驗於 2026-09-04 一天內設計、預先登記、執行、裁定完畢，實驗資料夾在主持人的本機 `c:\tmp\stance-experiment`（含 git 紀錄），沒有放進本專案。

## 一句話結論

三個立場的 AI 開發者各跑六條軌跡、連續 21 個需求，合計 1 億零 787 萬組窮舉比對，一組都沒錯。複雜度指標當守門員有沒有用，在這個難度、這個模型下**測不到**。真正測得出來的只有三件事：沒有任何數字門檻、只被告知「整理到自己滿意」的 AI，從頭到尾沒有一週會被門檻擋下；門檻把最大複雜度壓低，卻把複雜度總量推高；門檻的成本比預期低很多，比「叫它自己整理」便宜得多。

## 要回答的問題

文章前面的案例都建立在「人讀不動」這個前提上。這個實驗把前提拿掉：程式完全由 AI 寫、沒有人會讀、沒有 code review、產出直接上線。此時圈複雜度與認知複雜度當 CI 守門員，還有沒有用處？

「有用」定義成可量測的四件事：

1. 長序列裡的失誤（含改壞既有行為的迴歸）比較少。
2. 接手的 AI 讀得比較懂。
3. 接手的 AI 改得比較對。
4. 上述收益值得它的 token 與時間成本。

## 三個立場，三份開發準則

實驗用三種 `GUIDE.md`（等同 CLAUDE.md）代表三種立場，其餘條件完全相同。共同部分：

> 這個專案完全由 AI 開發。沒有人會閱讀程式碼，也沒有 code review，你的產出直接上線。每次任務只會給你一條新需求。先前所有需求都已經實作在程式碼與測試裡，程式碼與測試就是規格。需求沒提到的行為一律維持不變。每條需求都要補上對應的測試。完成的定義：`npm run ci` 通過。

| 組 | 名稱 | 立場段落 |
|---|---|---|
| A | 最小改動派 | 本專案不採用任何程式碼品質指標。測試全綠就是好程式碼。最小改動原則：只做需求要求的事。不重構、不整理與需求無關的程式碼。 |
| B | 自律派 | 本專案不採用任何靜態指標。程式碼是否好維護，由你自己的工程判斷決定。每次完成需求後，必須檢視整份 `src/`，把你認為難以維護的地方整理到你自己滿意為止。要不要動、動多少，由你判斷，沒有數字門檻。 |
| C | 指標派 | 本專案用複雜度指標當守門員。`eslint.config.mjs` 設定了 `complexity` 上限 10（modified 模式）與 `sonarjs/cognitive-complexity` 上限 15，任何函式超標，CI 就會失敗。超標時必須重構到通過為止。禁止調高門檻、禁止用 `eslint-disable` 略過。 |

C 組的門檻就是文章推薦的值。A 組對應文章開頭「一週加一個 `if`」的情境；廢除派的主張由 B 組代表，主要對比是 C 對 B。

## 評分方式

**窮舉差分。** 主持人另外維護一份 22 個週次都能算的參考實作（受試者永遠看不到），每週把所有欄位的取值集合做笛卡兒積，逐組比對受試者的 `calcShippingFee(order)` 與參考實作。格點在開跑前寫死，例如金額取 0、300、499、500、501、999、1000、1001、1499、1500、1501、1999、2000、2999、3000、3001，重量取 0.5、5、5.5、20、21.5、40 公斤，全部落在門檻兩側。每週格點大小從 256 組（第 1 週）成長到 663,552 組（第 21 週），18 條軌跡 21 週合計 107,868,672 組比對。

**參考實作的驗證。** 另請一位只讀需求文件的 Opus 從零實作一份，77 個範例全過，與參考實作在 22 個週次、5,542,528 組輸入上零不符。它另外找出四處需求歧義，開跑前都改掉了。

**錯誤分三類。** 每組不符依「這週答案有沒有變」拆成新規則錯（沒讀懂本週需求）、迴歸（改壞先前正確的組合）、沿用（上週就錯了）。

**假想守門。** 三組每週都量圈複雜度（modified 與 classic）、認知複雜度、巢狀深度、函式數、行數、地區字面值比較次數，並對 A、B 組也套用 C 的門檻算「如果有守門員會不會被擋」。

**繞過偵測。** 每週掃 `eslint-disable`、ignore 檔，比對三個受保護檔案的雜湊。

**成本。** 每個 subagent 完成時的通知帶有精確 token、工具呼叫次數、耗時，不靠受試者自報。

**接手理解測驗。** 第 21 週結束後，每條軌跡的 `src/` 交給全新的 Sonnet，只准用一次 Read 工具讀一份含程式碼與 28 組固定輸入的檔案，之後禁止任何工具，用腦推算 28 個運費。每條軌跡獨立跑 3 輪，共 54 次。合規與否用 subagent 通知的工具呼叫次數與轉錄檔逐一核對。

## 預先登記的判準

- H1 指標守門降低長序列失誤：看首次失誤週分佈、錯誤佔比、迴歸錯誤。三組全部零失誤時記錄為「在 21 週、這個難度、這個模型下測不到」，不延長。
- H2 沒有指標時 AI 只會往上加：A 的斜率與倍數；A、B 第 20 週中位數皆 ≥ 15 且差 < 3 代表「憑感覺不會自己整理」；B ≤ 12 代表「叫它整理就夠」；C 最大值降但總和與散落數沒降，標註「門檻只造成搬家」。
- H3 守門有成本：C 對 A、B 的 token 與耗時比值；後期對前期的成本比值。
- H4 形狀影響理解：28 題心算，C 比 A、B 多 4 題以上算有用，差 ≤ 2 題算無用。
- H5 形狀影響接手修改：第 21 週東部子集錯誤佔比與非東部迴歸。

結論規則事先寫死：H1、H5、H4 都無差，指標在這個情境下對結果沒有用，只改變形狀，就算 H2 成立也一樣；B 與 C 相當，有用的是「叫它整理」而非那個數字；C 有兩條以上軌跡繞過守門而仍未勝出，這種守門員在無人監督的全 AI 迴圈裡不可執行。

### 接手修改：全部零錯

第 21 週東部相關 165,888 組輸入，18 條全對；非東部輸入零迴歸。擁護派開跑前點名的錯法（寫出 `region === 'main' || region === 'east'` 而繼承本島超重費率）整場只出現一次，在 B 組的 t15，而且是一個有註解、有邊界說明、663,552 組全對的正確抽象。

套用結論規則：H1、H4、H5 都無差，指標對結果沒有用，只改變形狀。但這一格是在天花板上觸發的，「對結果沒有用」那半句實際上是**沒測到**而非**被否證**，只有「只改變形狀」那半句有資料支撐。B 在 H1、H4、H5 上與 C 相當，且 H2 也追平，落在「有用的是叫它整理，不是那個數字」。繞過守門 0 次，「不可執行」那條沒有觸發。

範圍限縮：以上只對 `complexity ≤ 10`（modified）加認知複雜度 ≤ 15 這組門檻、這 21 條需求、單一檔案的純函式、Claude Sonnet、每週補測試的迴圈成立。

## 兩位審查者的判決

兩份判決全文在實驗資料夾的 `debate/verdict-advocate.md` 與 `debate/verdict-abolitionist.md`。

**擁護派**逐條清算自己的十條認輸條件，九條成立（天花板、B 追平 C、搬家不算整理、理解沒差四條是嚴格成立），依自己開跑前的條文認輸。它的一句話：「這道守門員很便宜、很守規矩，但在這個難度、這個模型、這種每週補測試的迴圈裡，它保護的是一個沒有發生的問題。」它另外指出真正擋住迴歸的很可能是每一組自己寫的一百多個測試，而非形狀或數字。

**廢除派**的四條認輸條件全部不成立，但它拒絕宣稱勝利，因為它開跑前寫過「三組全部零失誤是天花板，什麼都沒證明」，這句話對自己同樣適用。它承認在成本那一題輸了：門檻的重構稅只有 +20%，而它推薦的「叫 AI 自己整理到滿意」是 +68%。它認為真正被動搖的是「一週加一個 if 最後變成巢狀 if 地獄」這個前提：378 個快照最深巢狀只有 1 或 2。

## 裁判裁定

全文在實驗資料夾的 `debate/ruling.md`。裁判從原始檔重算兩份判決引用的關鍵數字（總比對組數、失誤數、第 20 與 21 週各組圈複雜度中位數與總和、假想守門次數、三組 token 與耗時、54 次心算、繞過次數），全部相符，只挑出兩處不影響結論的計數瑕疵。

機械套用結論規則後，DESIGN 的第 1 條（只改變形狀）與第 3 條（有用的是叫它整理）字面上同時觸發，但兩者都建立在天花板上的零差距，所以只能寫成：

> 在本實驗條件下，這道複雜度守門員只被證實改變了程式碼的形狀與成本；它對正確率、迴歸、接手理解、接手修改的影響量不到，既未被證實有用，也未被證實無用。同時，達成該形狀不需要那個數字。

裁判補了一個兩份判決都沒算的數字：C 的圈複雜度總和高，一部分只是函式多，每多一個函式基線就加 1。改看每函式平均圈複雜度（第 21 週中位數），A 11.58、B 2.61、C 3.37。「搬家」的正確讀法是門檻買到「每一塊都低於門檻」，既非總量下降，也不該讀成 C 比 A 更複雜；真正與函式數無關的副作用是地區判斷散落到 15 處。

對兩位審查者：擁護派九條認輸條件成立、已誠實認輸、沒有事後改口；廢除派四條主條件全不成立、依規則不認輸，但拒絕把零失誤記成自己的勝利，並自行縮限了一條開跑前寫得過寬的條文。兩份判決在程序上都合格。

可信度：預先登記、盲化、窮舉差分、整理紀錄屬高標，五類異常沒有任何一項改變結論。內部效度的致命傷在設計本身：沒有難度校準，加上每組自己補了厚測試，兩者合力把四項主要依變數推上天花板。裁判的原話：「這場實驗最貴的一筆支出，是用 33.31M token 與 24.7 小時買到一句『測不到』。」

## 異常與誠實揭露

- **第一次正式跑作廢。** 跑到第 3 週時使用者以為資料夾不再需要，把整個 `c:\tmp` 刪掉。主持人從對話紀錄原樣重建所有檔案，參考實作重新委託獨立審查者驗證（零不符），從第 1 週重跑。廢除派審查報告的後半段只剩摘要還原，是誠實條款的實質破口。作廢那次的第 1、2 週也是全部零失誤。
- **三次代理人卡住。** 第 12 週 t11、第 19 週 t05 與 t11 寫完檔案後停在「準備跑 CI」或「準備檢視 src」超過 40 分鐘，主持人確認 `npm run ci` 通過後手動終止，以當下狀態評分，用量以缺值處理。
- **暫存檔互相覆寫。** 18 個 subagent 共用主持人的 scratchpad，第 20 週四條、第 21 週一條回報草稿檔被其他軌跡的內容覆寫。五條都聲明未採信，交付物不在 scratchpad，窮舉差分零不符。前面幾週是否也發生過無法回溯。
- **第 20 週評分表的秒欄失真。** 需求發出後主持人等使用者回覆才啟動代理人，中間空了約 40 分鐘。成本分析一律改用 subagent 通知的精確耗時。
- **接手理解測驗改成讀檔。** DESIGN 寫「程式碼貼在提示詞裡」，實作改成受試者只准用一次 Read 讀一份檔案，理由是 18 份程式碼合計約 19 萬字元，54 份提示詞會撐爆主持人的上下文。合規以轉錄檔逐一核對。
- **A 組兩條軌跡自行拆函式**，與「不重構」的準則不符，削弱了 A 作為劣化對照的力道。
- **中途 lint 失敗沒有記錄。** 只留每週最終狀態，C 組被門檻退貨幾次無法得知，只能用 A 組的假想判決反推。
- **卡住代理人的處理規則是臨場定的**，開跑前沒寫進 DESIGN。
- **獨立性靠結構，沒有沙箱。** 每條軌跡一個資料夾、每週全新的 subagent、提示詞只提自己的資料夾，但工具沒有被限制在資料夾內。事後掃了全部轉錄檔，結果與偏差評估見下一小節。

### 獨立性稽核與偏差評估

掃描對象是本次 session 全部 496 份 subagent 轉錄檔（432 份開發代理人，含作廢那次的 54 份；54 份接手理解；10 份審查者、裁判與驗證者），只看工具呼叫的輸入，腳本在實驗資料夾的 `tools/audit-isolation*.mjs`。正式跑的 378 份裡，讀取別條軌跡檔案的是 0 份，開啟參考實作、需求檔、模板、快照的也是 0 份。有洩漏的管道與三組的暴露量如下（每組 126 個軌跡週）：

| 洩漏管道 | A | B | C | 看到什麼 |
|---|---|---|---|---|
| 在自己資料夾跑 `git status` 或 `git diff` | 70 | 96 | 72 | 上層 repo 的狀態，多半只有 `runs/` 未追蹤，沒有程式碼與分組資訊 |
| 指令碰到上層路徑 | 6 | 6 | 5 | 只有兩次有實質內容（t02 第 5 週在根目錄 `find`、t13 第 1 週在根目錄 `git status`），都只看到目錄名稱 |
| 看到主持人筆記 | 0 | 1 | 0 | t17 第 21 週用 `git diff` 看到尚未 commit 的 20 行 CHANGELOG，知道自己在被評分 |
| scratchpad 被別條軌跡覆寫 | 2 | 0 | 2 | 第 20、21 週 t03、t06、t07、t11 看到別人的草稿，函式名稱與自己的程式碼對不上 |

作廢那次跑的第 3 週，t18 在使用者刪除 `c:\tmp` 的當下發現檔案不見，四處搜尋時列出了 `runs/t10` 的檔名；那次結果已作廢。

偏差評估：

- 暴露量三組相近，只有 B 跑 git 略多，那是「檢視整份 src」的準則造成的，屬於處理本身。不分組的暴露做不出組間差異，最多讓三組一起更小心。
- 天花板與暴露無關。A 組有 56 個軌跡週從頭到尾沒碰 git，同樣零失誤；暴露過與沒暴露過的格子錯誤數都是零。
- 沒有人抄到別人的寫法，形狀也沒有靠攏：t03 看過別人的草稿後，第 21 週仍是單一函式、圈複雜度 38。
- 唯一實質的解盲只有 t17 第 21 週一格。該週產出全對，成本 15 萬 token 在 B 組同週的範圍內；第 21 週只餵 H5，而 H5 本來就三組全零。
- 受試者讀自己的準則不算解盲，準則就是處理；它不知道別組拿到什麼、自己屬於哪一組，這部分沒有破。
- 可能留下的痕跡有兩處：知道上層還有東西可能讓受試者更小心，方向是把本來就撞頂的正確率再往上壓，不改變「測不到」；成本量測含這些 git 呼叫，每週 1 到 2 次，三組都有，影響在幾個百分點以內。

## 限制與如果重做

- **難度沒有校準。** 378 次試驗、1 億多組比對只換到「測不到」。重做要先跑兩三條拋棄式軌跡，確認對照組會出錯（例如 21 週內至少三成軌跡失誤）才開跑；達不到就加難度、拉長序列、跨檔案、或換更弱的模型。
- **補測試消掉了主要依變數。** 要求每週補測試，等於每一組都裝了同一台迴歸偵測器。重做應改成三組共用一組主持人維護的、只覆蓋當週需求的驗收測試，禁止受試者自己補歷史迴歸測試，才真的是「弱測試條件下守門員有沒有用」。
- **缺測試面守門員對照組。** 沒有 D 組，「任何逼 AI 交件前重讀整份邏輯的關卡都有用」與「複雜度指標有用」分不開。
- **兩條規則綁在一起等於白測一條。** 認知複雜度規則 0 次獨立生效。
- **單一檔案、單一純函式。** 圈複雜度在這種形狀上量得最準，也最無關痛癢；現實中讓 AI 犯錯的跨檔案隱含耦合，正是它量不到的東西。
- **心算測驗太簡單。** 54 次全滿分，題目沒有解析度。
- **每個 subagent 要有獨立暫存目錄；`runs/` 要放到 git repo 外面或各自 `git init`，並用權限設定把讀取範圍限制在自己的資料夾；預先登記文件要存兩份並記雜湊；週內每次 CI 執行要留痕。**

## 實驗資料夾與重現方式

資料夾在主持人本機 `c:\tmp\stance-experiment`，git 紀錄從 `prereg` 標籤開始，之後每週一個 commit。

| 路徑 | 內容 |
|---|---|
| `DESIGN.md` | 預先登記的設計、格點、假說判準、結論規則、誠實條款 |
| `CHANGELOG.md` | 開跑前的修改與開跑後所有異常 |
| `debate/prereg-*.md`、`debate/verdict-*.md`、`debate/ruling.md` | 兩位審查者的預先登記與判決、裁判裁定 |
| `spec/requests/01.md` 到 `21.md` | 21 條需求全文與範例 |
| `reference/reference.mjs`、`reference/inputs.mjs` | 參考實作與窮舉格點 |
| `validation/independent.mjs` | 獨立審查者從需求文件重寫的實作 |
| `template/` | 三組的 GUIDE、eslint 設定、起點程式碼與測試 |
| `runs/t01` 到 `t18` | 18 條軌跡的最終狀態 |

| `tools/` | `setup`、`dispatch`、`score`、`record-usage`、`analyze`、`build-understanding-prompt`、`score-understanding` |

重跑一週的流程：

```bash
node tools/dispatch.mjs <week> runs        # 把需求發到 18 個資料夾

node tools/analyze.mjs runs                # 彙整成 data/analysis-runs.md
```

接手理解測驗：`node tools/build-understanding-prompt.mjs runs 21` 產生 18 份提示詞檔，每份交給全新的 Sonnet 讀一次並作答，答案用 `node tools/save-answer.mjs <id> <round> '<json>' tokens toolUses durationMs` 存檔，最後 `node tools/score-understanding.mjs runs 21`。
